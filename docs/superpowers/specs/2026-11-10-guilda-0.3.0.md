### X1 — Rule IDs, the full-file limit and the always-on context

Two limits, two texts (0.2.0 spec, section 3h, `@decided` 2026-11-10, the user):

- The full files. `tests/core-content.test.mjs` counts the non-blank lines of `core/rules.md` + `core/writing.md`.
  Each core rule adds 4 lines: its heading and three lines. Each release has one limit number, in the table.
- The always-on context. It is the whole text that the session start puts in each session. Its limit is 150
  non-blank lines, with a project rules file of 20 lines. The limit is a design invariant: no release raises it, and
  no release lowers the 20 lines. The test is 'context has 150 non-blank lines or fewer with a 20-line project rules
  file' of `tests/session-start.test.mjs`.
- The context has the short form of each core rule. `contextRules` of `scripts/lib/rules-context.mjs` (0.2.0) makes
  it from `core/rules.md`. A rule with the level `law` is one line: its heading, then ` (law — enforced by a hook)`.
  A rule with the level `gate` or `judgment` is two lines: its heading with the level, then its `Rule:` line. The
  full block of each rule stays in `core/rules.md`.
- So a new core rule needs no code change for the context. A `law` rule costs 1 context line, and each other rule
  costs 2. Each other new line of the session start costs 1.

| Release | New core rule IDs | `law` rules of them | Limit of the full files | Always-on context, at most (limit 150) | New ARC IDs |
|---|---|---|---|---|---|
| 0.2.0 | R26 to R30 | R28, R29, R30 | 142 | 103 | ARC7 to ARC10 |
| 0.3.0 | R31, R32 | R32 | 150 | 107 | none |
| 0.4.0 | R33, R34, R35 | R34 | 162 | 124 | none (ARC1 changes) |
| 0.5.0 | R36 to R41 | R37 to R41 | 186 | 131 | ARC11 to ARC13 |

### X2 — The writer of the queue (D14 `@decided`)

- Only the queue script writes the queue. The queue is the files `journal.jsonl`, `state.json`, `lock` and
  `writer.json` in `.guilda/queue/`. The queue script is `scripts/queue.mjs`. From 0.5.0, `scripts/tick.mjs` and
  `scripts/watch.mjs` write through the same functions of `scripts/lib/queue.mjs`, and they count as the queue script.
- A hook and a worker never write the queue. Each one writes only its own signal files (X3). The run wrapper also
  writes the log file of its own run, `.guilda/logs/<address>.jsonl` (section 4a).
- The writer role (D14 `@decided`: the Architect until the supervisor exists):

  | Release | Writer role | Role check on the hook input |
  |---|---|---|
  | 0.3.0 | the Architect, in the main session | no `agent_id` |
  | 0.4.0 | the Architect agent | `agent_type` is `guilda:architect`. On a NO-GO of L4-1 the 0.3.0 row stays |
  | 0.5.0 | the supervisor session while its claim is live; with no live claim, the 0.4.0 row | no `agent_id`, and `session_id` equals the `session` of `writer.json` |

- "The writer" has a mechanical meaning, in two parts:
  1. The lock for each command. Each run of the queue script creates `lock` with the exclusive flag, and removes it
     at its end. So two runs never write at the same time.
  2. The role check. The R32 hook (PreToolUse) reads each `Bash` call of the queue script. It refuses a call whose
     caller fails the role check of the table.
- `--session <id>`: each command of the queue script takes it. The script records the value in the lock and in the
  `dispatch` event. The R32 hook refuses a call whose `--session` value is not the `session_id` of the hook input.
  A script cannot see its session. So the session start hook gives each session its ID in one context line:
  `guilda session: <session_id>`.
- The claim (0.5.0 only): `writer.json` is
  `{ "role": "supervisor", "session": "<id>", "pid": <n or null>, "at": "<ISO>", "aliveAt": "<ISO>", "ttlSec": <n> }`.
  `queue claim` writes it. A claim is live while `aliveAt` + `ttlSec` is after now. Each run of the queue script, of
  `tick` and of `watch` with the session of the claim writes `aliveAt` again. `pid` is the last `watch` process. It
  is not part of the test. `queue claim` is the one queue command that passes for a session with no `agent_id`
  while no claim is live (0.5.0 spec, section 5a). 0.3.0 and 0.4.0 never write this file.
- R32 has one text in each release (section 3a). 0.4.0 and 0.5.0 change only the row of the role check.

### X3 — One identity path (D14 `@decided`, D12, D17)

- One generator. The function `makeAddress` of `scripts/lib/queue.mjs` makes each address. `queue dispatch` is the
  one command that makes the address of a dispatch, and it prints it. In 0.4.0, `bus.mjs join` calls the same
  function for a joined agent of another tool. It writes only a join signal.
- One prompt line. The controller puts the line `Address: <address>` in the prompt of each dispatch.
- One hook. `scripts/hooks/post-agent.mjs` (PostToolUse, matcher `Agent`) reads that line and
  `tool_response.agentId`. It writes `.guilda/queue/signals/agents/<agentId>/dispatch.json`. 0.4.0 adds the fields
  `agentType`, `parentSession` and `parentAgent` to that file. No other hook writes `dispatch.json`, and no other file binds an
  address to an agent ID. An audit line and a signal folder name an agent ID, and they bind nothing.
- One fold. `queue sync` turns each new signal file into one journal event. From 0.4.0 it also folds the join and
  session signals of `.guilda/bus/signals/`.
- One table. `state.json` holds the address and the agent ID of each run. From 0.4.0 its `bindings` key is the
  binding table. No other file stores a binding.
- Limit: a foreground dispatch returns its agent ID only at its end. So a foreground subagent has no `agent` event
  during its first run. `sync` folds the signals in the order of their `at` times, so the late join gives the same
  states. A background dispatch gets its `agent` event at the next `sync`.

### X4 — ID and address patterns

| Value | Pattern | Note |
|---|---|---|
| task ID | `^[A-Za-z0-9]{1,24}$` | not `main`, `architect`, `supervisor`, `council` or `ext`. With `init --part <N>` the task `T3` gets the ID `P<N>T3` |
| attempt | an integer from 1 to 3 | section 4a |
| agent ID | `^[A-Za-z0-9._-]{1,64}$`, not `.` or `..` | the host makes it |
| role code | `arc`, `exe`, `rev`, `qa`, `sec`, `vc`, `lab`, `dev`, `ai` | a new role gets its code in its spec: 2 to 4 lower-case letters |
| address of a dispatch | `<task ID>-<role code>-<4 hex>` | `T3-exe-7f2a` |
| address of a joined agent (0.4.0) | `ext-<tool>-<name>-<4 hex>` | `ext-codex-voice-4592`; `<tool>` is `[a-z0-9]{1,24}`, `<name>` is `[A-Za-z0-9]{1,24}` |
| fixed address | `main`, `architect`, `supervisor`, `council-<4 hex>` | reserved; `makeAddress` never makes the first three for a task |
| work ID | `w-<8 hex>` | one `queue init`: the tasks of one plan or one Part. A build is one work |
| run ID (0.4.0) | `r-<8 hex>` | one process of another tool |

- The full address pattern:
  `^(main|architect|supervisor|council-[0-9a-f]{4}|[A-Za-z0-9]{1,24}-[a-z]{2,4}-[0-9a-f]{4}|ext-[a-z0-9]{1,24}-[A-Za-z0-9]{1,24}-[0-9a-f]{4})$`.
- `main` is the main session (0.4.0). `architect` is the Architect agent (0.4.0). `supervisor` is the supervisor
  session (0.5.0). `council-<4 hex>` is the channel of one council (0.5.0). 0.3.0 reserves the four names and uses
  none of them.
- Each script refuses another value with exit 1 and the text `invalid ID`, and it writes no file. Code never parses
  an address for its task or its role. It reads them from `state.json`.
- The random part comes from `crypto.randomBytes`. On a match with a known address, `makeAddress` draws again, at
  most 10 times. Then the command exits 1 with `no free address`.

### X5 — One event vocabulary

- Each journal event has `seq`, `t` (ISO time) and `type`. No event uses the field name `time`.
- `cause` is a field of a `state` event. It is one word from code that says why the state changed.
  The values of 0.3.0: `deps-done`,
  `dispatch`, `started`, `done`, `failed`, `no-ack`, `no-heartbeat`, `heartbeat`, `late-done`, `approve`, `reject`,
  `retry`, `hold`, `release`.
  One more value: `attempts-used`. 0.5.0 adds `session-ended`, `stop`, `hold-all` and `release-all`.
- `reason` is a field of an end signal (`done` or `failed`). The worker says how it ended: `finished`, `error`,
  `limit` or `timeout`. No `state` event has a `reason`, and no signal has a `cause`.
- `held` has no `cause` text and no `reason` (D48 `@decided`). Its `state` event has the `cause` `hold` only.
- `hold` and `release` are values of the `decision` event, written by `queue hold` and `queue release`. Each one
  takes one or more task IDs. 0.5.0 uses the same event and adds the values `hold-all`, `release-all`, `slots`, `stop`,
  `save-ok` and `architect-ok`.
- Event types of each release. A reader ignores a type that it does not know (D40).

  | Release | `type` values |
  |---|---|
  | 0.3.0 | `plan`, `task`, `dispatch`, `agent`, `signal`, `state`, `decision`, `takeover` |
  | 0.4.0 | adds `join`, `session`, `unbind`. A second `agent` event for one address is a rebind. An `agent` event of a fixed address has `task: null` |
  | 0.5.0 | adds `claim`, `sleep`, `limit-stop`, `question`, `answer` |

- The `dispatch` event is the dispatch intent, and the `agent` event confirms it. No release adds another pair for
  this.
- Lock fields: `{ "pid": <n>, "session": "<id or null>", "at": "<ISO>" }`. The claim fields are in X2. Field names
  are in camel case in each queue file.
- A work ID names the build of the cost record (0.3.0) and the work of the resume record (0.5.0). A run ID names a
  process (0.4.0). An attempt is one work run of one task.

### X9 — Laws fail closed; one project hash

- A law hook refuses the call when it cannot do its check. The first case is a hook input that it cannot
  parse. The second case is a read error of a file that the check needs. Such files are `state.json`,
  `writer.json`, the config and a state file outside the project. A file that does not exist is not a read error. The refusal text is `<rule ID>: cannot read <what>`.
- With no `.guilda/` folder the laws do not run, as in 0.2.0 (R28).
- A record hook fails open: the audit lines, the heartbeats and the `Stop` branches. It exits 0 and writes nothing.
- A file that guilda keeps outside the project has the project hash in its name. The hash is the first 16 hex
  characters of SHA-256 of the real path of the main project root. The main root is the parent folder of the git
  common directory (`git rev-parse --path-format=absolute --git-common-dir`). So each worktree of one project gives
  the same hash. With no git repository, the root is the real path of the project folder. When the root cannot be
  found, the law that needs the file refuses the call.

## 1. Intent

The field use of guilda and the labs of 2026-11-09 showed four problems:

- The flow lives only in the context of one agent. A compaction or a `/clear` loses which task runs, who runs it and
  what is late (D14, D50).
- A change in a spec does not reach the plan and the briefs that used it. Each agent reads the whole spec again to
  find out (D27).
- After the work, nobody can ask an agent why it did something, or see what it did (D12, D13, D32).
- Nobody knows what a task, a block or a build costs in tokens or in money (D22, D35).

0.3.0 puts the state of the flow and its history in files that do not compact. The flow, the block index, the audit
log and the cost record are code and data. A model reads them by ID. A mod shows them to the user (D20, D24).

0.3.0 is a minor release: it adds two core rules, R31 and R32 (0.x rule of `RELEASING.md`). No core rule changes
meaning.

## 4a. Contract: the queue (D14)

Security zone: file paths from IDs

The files (D14 `@proposed`, with one addition):

```
.guilda/queue/journal.jsonl                     append-only, written only by the queue script (R32)
.guilda/queue/state.json                        derived from the journal, written by temp file and rename
.guilda/queue/lock                              the run of the queue script that writes now
.guilda/queue/writer.json                       the claim of the supervisor; 0.5.0 only (X2)
.guilda/queue/signals/<task>/<attempt>/<kind>   written by the worker of an external run
.guilda/queue/signals/agents/<agentId>/<kind>   written by the hooks of a Claude subagent (addition)
.guilda/queue/signals/agents/<agentId>/dispatch.json   written by the identity hook (section 4b)
```

- The addition (the Architect's choice): a hook inside a subagent knows its `agent_id`, not its task. So it writes its
  signals under the agent ID. The identity hook writes the task and the attempt of that agent in `dispatch.json`. The
  writer joins the two at `sync`. So no hook writes the journal (D14 `@decided`: one writer).
- `<kind>` is `started`, `heartbeat`, `done` or `failed`. Each signal file has one writer. `heartbeat` is written again
  by temp file and rename. The other kinds are written one time.
- IDs in paths: a task ID, an attempt number, an agent ID and an address match the patterns of X4. Each script
  refuses another value with exit 1 and `invalid ID`, and it writes no file (S17).

### Journal events

One JSON object on each line. Each event has `seq` (1, 2, 3 and so on), `t` (ISO time) and `type` (X5). A line that does not
end with a newline is a partial line: the reader skips it. A line that is not JSON is skipped and reported with its
line number.

| `type` | Fields | Written by the command |
|---|---|---|
| `plan` | `plan` (the plan file path), `part` (a number or `null`), `work` (the work ID, X4), `slots` (the number of tasks that can run at the same time) | `queue init` |
| `task` | `task`, `work`, `key` (the trace key of the plan task, section 4d), `title`, `deps` (task IDs), `uses` (the `Uses:` keys), `owns` | `queue init`, `queue add` |
| `dispatch` | `task`, `attempt`, `address`, `role` (a role code), `tool` (`claude` or `codex`), `inSession`, `check`, `tier`, `session`, `briefFile`, `baseCommit`, `uses` | `queue dispatch` |
| `agent` | `address`, `task`, `attempt`, `agentId` | `queue sync`, from a `dispatch.json` |
| `signal` | `address`, `task`, `attempt`, `kind`, `at`, `reason`, `usage`, `tokens` | `queue sync`, from a new signal file |
| `state` | `task`, `from`, `to`, `cause` (X5) | each command that changes a state |
| `decision` | `tasks`, `decision` (`approve`, `reject`, `retry`, `hold`, `release`), `by` | `queue approve`, `reject`, `retry`, `hold`, `release` |
| `takeover` | `oldPid`, `oldSession` | the first command after a stale lock |

- D14 `@decided`: the dispatch event records the address, the agent ID, the tool, the session and the `Uses:` line.
  The agent ID arrives later, in the `agent` event, because the host gives it after the dispatch. The address and
  the role codes have the form of X4, for example `T3-exe-7f2a`. `queue dispatch` is the one generator (X3).
- `inSession` comes from the builder check of 2026-11-09 (`@decided`). An agent from outside the conversation is any
  agent that is not in the native agent list. It is `true` for a subagent of the session. It is `false` for a run outside the
  conversation: a `codex exec` or a `claude -p` process under the run wrapper. `queue dispatch` writes `false` with
  `--external`, and for each `--tool` other than `claude`.
- `check` is `true` for a check run (below), and `false` for a work run.
- The journal keeps role codes. For display, code maps each code to a name. `arc` is architect, `exe` is
  executor, `rev` is reviewer and `qa` is qa. `sec` is security, `vc` is version-control and `lab` is lab. `dev` is
  devops, and `ai` is ai-lead.
- The `held` state has no reason field (D48 `@decided`). No event of the journal says why a task waits. The
  `decision` event of a hold has no text field.

### `state.json`

```
{ "generator": "guilda 0.3.0", "journalSeq": 41, "slots": 3,
  "works": { "w-5c1e9a02": { "plan": "docs/superpowers/specs/login.plan.md", "part": null } },
  "tasks": { "T3": { "work": "w-5c1e9a02", "state": "running", "attempt": 1, "address": "T3-exe-7f2a",
                     "agentId": "a1b2c3", "role": "exe", "tool": "claude", "inSession": true,
                     "title": "Login form", "deps": ["T1"], "uses": ["D14@3f2a9c1b"], "since": "<ISO>",
                     "lastHeartbeat": "<ISO>", "busyUntil": "<ISO>", "tokens": 41200, "agentSeconds": 720,
                     "checks": [ { "address": "T3-rev-a9f0", "role": "rev", "agentId": "d4e5f6", "attempt": 1 } ] } } }
```

- `slots` is the value of the last `plan` event. `tokens` is the sum of each token kind of the attempt so far.

- `journalSeq` is the `seq` of the last event in the fold. A reader with a journal whose last `seq` is higher folds the
  journal again in memory. It does not write the file; only the writer writes it.
- `agentSeconds` is the sum of the time in `running` of each attempt. The panel and `status` use it for the work hours
  (D20 `@decided`, U5).

### Work runs and check runs

- A work run moves its task. `queue dispatch <task>` of a `ready` task starts a work run. The state becomes
  `dispatched`, and the run gets the attempt number of the task.
- A check run is a Reviewer, QA or Security run on the work of a task. `queue dispatch <task> --check` with the role
  `rev`, `qa` or `sec` starts it. The task must be `running`, `review` or `stalled`. The command writes a `dispatch`
  event with `check: true`, the attempt of the task and a new address, for example `T3-rev-a9f0`. It writes no
  `state` event, and it uses no slot.
- A check run gets its `agent` event and its `signal` events through the same path as a work run (X3). A signal of a
  check run changes no state. The verdict moves the task only through `queue approve` or `queue reject` (R24).
- `state.json` lists the check runs of a task in its `checks` key. So `status --agent` and the cost record find
  each Reviewer, QA and Security run by its address.
- A lab run is a task of the plan. So it is a work run with the role `lab`.
- A dispatch with no `Address:` line is outside the queue. It gets no event.

### States and transitions

D14 has the table, and the register says that the plan states who sets each state and when. Here is that table. The
plan copies it. In 0.3.0 the writer is the `queue` script that the Architect runs.

| From | To | Who sets it | When |
|---|---|---|---|
| (new) | `pending` | writer, `queue init` or `queue add` | the task enters the queue |
| `pending` | `ready` | writer, `queue sync` | each dependency is `done` |
| `ready` | `dispatched` | writer, `queue dispatch <task>` | a slot is free; the command prints the address and the attempt |
| `dispatched` | `running` | writer, `queue sync` | a `started` signal of that attempt |
| `running` | `review` | writer, `queue sync` | a `done` signal of that attempt (D14 `@decided`: `review` when the agent delivers its report) |
| `review` | `done` | writer, `queue approve <task>` | the written approval of the Reviewer (R24) |
| `review` | `ready` | writer, `queue reject <task>` | a rejection; the attempt number plus one |
| `running` | `failed` | writer, `queue sync` | a `failed` signal |
| `dispatched` or `running` | `stalled` | writer, `queue sync` | no `started` in the ack timeout, or no heartbeat in the lease timeout |
| `stalled` | `running` | writer, `queue sync` | a new heartbeat of the same attempt |
| `stalled` | `review` | writer, `queue sync` | a late `done` of the same attempt (L1 case) |
| `failed` or `stalled` | `ready` | writer, `queue retry <task>` | a decision of the Architect; the attempt number plus one |
| `pending`, `ready`, `failed` or `stalled` | `held` | writer, `queue hold <task>` | a decision of the Architect (D48) |
| `held` | `pending` | writer, `queue release <task>` | a decision of the Architect |
| any open state | `dead` | writer, `queue retry` or `queue reject` | the next attempt would be the fourth |

- Three rows are not in the D14 table: `review` to `done`, `review` to `ready`, and the late `done`. They come from
  the `@decided` item on `review`. Section 5 asks the user to approve them.
- `stalled` never dispatches the task again by itself (D14). A retry uses a new attempt and its own worktree or branch.
- A signal of an old attempt is recorded as a `signal` event and changes no state.
- A crash between the `dispatch` event and the dispatch (SC-G19): the journal has the `dispatch` event, and no agent
  started. The task stays `dispatched`. At the ack timeout, `sync` makes it `stalled` with the cause `no-ack`. No
  command dispatches it again by itself. The Architect checks that no agent runs for the address, then runs
  `queue retry`. The retry has a new attempt and a new address. So a late agent of the old address changes no
  state.
- The attempt limit is 3 (the Architect's choice). It matches R10, a new tier after two failures. It matches R11,
  where the third rejection goes to the Architect and the user. `dead` goes to the Architect and the user.
- The timeouts are the start values of SC-G6, and L1 measures them. The ack timeout is 2 min. The lease timeout ends
  at the later of two times. They are `busyUntil` plus 5 min, and the last heartbeat plus 15 min. `busyUntil` is the time of
  the heartbeat plus the timeout of the current tool call. That is the `timeout` of a `Bash` call, or 10 min.
- The writer checks the timeouts only when it runs. No daemon runs in 0.3.0. So the Architect runs `queue sync`
  before each dispatch and before it reads the state. `status` shows a `late` mark from the same timeouts, and it
  writes nothing.

### Signals

| Kind | Claude subagent: who writes it (U9) | External run: who writes it | Content |
|---|---|---|---|
| `started` | the SubagentStart hook of the agent | the run wrapper, before the run | `{ "at": "<ISO>" }` |
| `heartbeat` | the PreToolUse hook in the agent (`agent-trace.mjs`) | the run wrapper, at each JSON event of the tool | `{ "at": "<ISO>", "busyUntil": "<ISO>", "tokens": <n or null> }` |
| `done` | the SubagentStop hook (`agent-end.mjs`) at a normal end | the run wrapper at exit code 0 | `{ "at": "<ISO>", "reason": "finished", "usage": <list or null> }` |
| `failed` | the SubagentStop hook at an end with an error | the run wrapper at another exit code or a timeout | `{ "at": "<ISO>", "reason": "error" or "limit" or "timeout", "usage": <list or null> }` |

- `usage` (D35 `@decided`: the token use of each task). It is a list with one item for each model:
  `{ "model": "<model id>", "input": <n>, "cacheRead": <n>, "cacheCreation": <n>, "output": <n> }`. So an end signal
  has the input and the output apart, for each model. For a subagent, the hook sums the transcript (section 4c). For
  an external run, the wrapper reads the usage fields of the JSON events of the tool. When the events give one
  total of the thread (lab `external-agent`: `codex exec resume --json`), the usage of the run is the last total
  minus the total before the run. When each event gives its own usage, it is the sum. Not verified: those fields
  (L2). With no usage data the value is `null`, never a guess.
- The `tokens` field of a `heartbeat` is one total so far, for the panel. The cost record does not use it.
- A stop by the user gives no signal. The task becomes `stalled` with the cause `no-heartbeat` at the lease timeout,
  and the Architect asks the user (SC-G4).
- The run wrapper of 0.3.0 is the `signal` script around the external command:
  `node scripts/signal.mjs <projectDir> run <task> <attempt> -- <command...>`. It writes `started`, then a
  `heartbeat` at each stdout line, then `done` or `failed` from the exit code. Its stdin is `/dev/null` (lab
  `agent-bus`).
- `run` takes `--timeout <seconds>` before the `--`. With no value there is no timeout. At the timeout the wrapper
  sends SIGTERM, then SIGKILL after 5 s, and it writes `failed` with the reason `timeout`. Another exit code that
  is not 0 gives the reason `error`. The reason `limit` needs the event field that names a usage limit. L2 records
  it. Until then such an end is `error`.
- The wrapper also writes `.guilda/logs/<address>.jsonl` for the panel (section 4h). It reads the address of the
  attempt from `state.json`. Each line is `{ "t": "<ISO>", "kind": "<kind>", "text": "<text>" }` (X5). The wrapper
  writes `state` at the start and at the end, with the text `started`, `done` or `failed <reason>`. It writes
  `tokens` for an event with usage fields, with the total as text. It writes `message` for each other stdout line,
  cut at 500 characters. The kinds `command` and `file` need the event fields of each tool. L2 records them. Until
  then the wrapper writes no such line. This log has command text and agent text, so it can hold a secret. The folder is
  git-ignored. R19 does not change in 0.3.0.
- Not verified: which `SubagentStop` input field tells a normal end from an error. L2 checks it. Until then, each end
  is `done` with the reason `finished`, and the Reviewer finds a bad result.

### Lock and recovery

- Each run of the `queue` script creates `.guilda/queue/lock` with the exclusive flag (`wx`). The content (X5):
  `{ "pid": <n>, "session": "<id or null>", "at": "<ISO>" }`. `session` is the `--session` value of the command
  (X2). The script removes its own lock at its end. First it
  reads the file and checks that the `pid` is its own (R20: one exact path, one file).
- A lock exists and its `pid` is alive: the script exits 3 with `queue locked by pid <n>`.
- A lock exists and its `pid` is not alive: the script writes a `takeover` event and its own lock. Then it goes on.
- Recovery at each run (D14 `@proposed`):
  1. Take the lock.
  2. Replay the journal, and skip a last partial line.
  3. Turn each new signal file into a `signal` event.
  4. Check the timeouts.
  5. Write `state.json`.
  6. Remove the lock.
- A failed write of the journal or of `state.json`: the script exits 2 with `io-error: <path>`, and writes no
  dispatch (SC-G13).

### The `queue` command

`node scripts/queue.mjs <projectDir> <command> [args] [--session <id>]`:

| Command | Effect | Output, first line | Exit |
|---|---|---|---|
| `init <plan file> --slots <n> [--part <N>]` | one `plan` event with a new work ID, and `task` events from the `### T<n> — ` tasks of the plan, with their `Dependencies:`, `Uses:` and `Owns:` lines | `queue: <n> tasks, work <work ID>` | 0; 1 |
| `add <task> --title <text> [--deps T1,T2]` | one `task` event | `queue: added <task>` | 0; 1 |
| `sync` | the recovery steps | `queue: <n> events` | 0 |
| `dispatch <task> --role <code> --tool <tool> --tier <tier> [--external] [--check] [--brief <file>] [--base <commit>]` | a `dispatch` event; for a work run also a `state` event | `dispatched <task> attempt <n> address <address>` | 0; 1 |
| `approve <task>`, `reject <task>`, `retry <task>` | `decision` and `state` events | `<task>: <from> → <to>` | 0; 1 |
| `hold <task>...`, `release <task>...` | one `decision` event and one `state` event for each task | one line `<task>: <from> → <to>` for each task | 0; 1 |

- Each command also exits 2 on an I/O error, and 3 on a live lock. The lock and recovery part above has both.
- `--session <id>` is for each command (X2). The script itself runs without it, and then the lock and the
  `dispatch` event have `session: null`: a test, or the L2 fallback. In a session the R32 hook refuses a call with
  no `--session` (section 3a).
- `--part <N>`: `init` reads only the `## Plan: Part N` section of the plan file. Each task ID gets the prefix
  `P<N>`, also in the `deps` lists: `T1` of Part 2 is `P2T1` (X4). So the tasks of two Parts do not collide. The
  `task` event keeps the trace key of the plan task in `key`, for example `login.plan#Part2.T1` (section 4d).
- `init` exits 1 with `queue: the plan has Parts; use --part` for a plan file with `## Plan: Part` headings and no
  `--part`. It exits 1 with `queue: task <id> exists` when the journal has a task with the same ID.
- A command that a state does not allow exits 1 with `<task>: <command> not allowed in <state>`, and writes nothing.
- `dispatch` of a work run for a task that is not `ready`, or with no free slot, exits 1. `dispatch --check` exits 1
  for a role other than `rev`, `qa` or `sec`. It also exits 1 for a task that is not `running`, `review` or
  `stalled`.
- A plan with a dependency cycle: `init` exits 1 and names the cycle (SC-G14).

### The `signal` command

`node scripts/signal.mjs <projectDir> <command> <task> <attempt> [args]`. A worker runs it, never the writer. It
writes only under `.guilda/queue/signals/<task>/<attempt>/`. The `run` command also writes the log file of its run,
`.guilda/logs/<address>.jsonl`.

| Command | Effect | Output, first line | Exit |
|---|---|---|---|
| `started <task> <attempt>` | writes the `started` file | `signal: started` | 0; 1 |
| `heartbeat <task> <attempt> [--busy-until <ISO>] [--tokens <n>]` | writes the `heartbeat` file again, by temp file and rename | `signal: heartbeat` | 0; 1 |
| `done <task> <attempt> [--usage <file>]` | writes the `done` file with `reason: "finished"` and the usage list of the file | `signal: done` | 0; 1 |
| `failed <task> <attempt> --reason <error\|limit\|timeout> [--usage <file>]` | writes the `failed` file | `signal: failed` | 0; 1 |
| `run <task> <attempt> -- <command...>` | the run wrapper of the signals part above | the output of the command | the exit code of the command |

- Exit 1: an invalid ID (X4), a bad argument, or a `started`, `done` or `failed` file that exists
  (`signal: <kind> exists`). Each of these three kinds is written one time. Exit 2: an I/O error.
- The script does not read the journal and does not take the lock. A signal for an attempt that the journal does
  not have is recorded at `sync` and changes no state.

## 4b. Contract: agent identity and questions after the work (D12)

- The identity hook (X3): `scripts/hooks/post-agent.mjs`, PostToolUse with the matcher `Agent`. It reads
  `tool_response.agentId` and the `Address: <address>` line of the prompt. D12 `@proposed` names the `ID / title:`
  line. The address replaces it, because one task can have several runs: each attempt, and each check run.
- It reads `state.json` and finds the `dispatch` event of that address. It writes
  `.guilda/queue/signals/agents/<agentId>/dispatch.json` with
  `{ "address": "<address>", "task": "<task>", "attempt": <n>, "at": "<ISO>" }`. When it cannot read `state.json`,
  `task` and `attempt` are `null`, and `sync` fills them from the journal.
- So each run gets its address at `queue dispatch`, and its `agent` event at the next `sync`. Its task comes from
  the `dispatch` event. This holds for an Executor run and for a Reviewer, QA or Security run (section 4a, check runs).
- In three cases it writes nothing and prints nothing. They are no `Address:` line, an address that does not match
  X4, and no agent ID.
  A dispatch outside the queue stays outside it.
- D12 `@proposed` says that the record goes to the queue journal. The hook does not write the journal, because D14
  `@decided` says that hooks never write the queue. The writer turns the file into an `agent` event at `sync`. So the
  queue journal stays the one owner of agent identity. Section 5 asks the user to approve this reading.
- Questions (D12 `@proposed`): the verdict of the Reviewer can have a `Questions:` section after the `Violations:`
  line. Each question is one list item, `- <question>`. `validateVerdict` accepts a verdict with or without the
  section. The Architect sends each question to the Executor with `SendMessage` and the agent ID of the attempt. It
  adds the answer to the review, and the ledger keeps each question and each answer. On a NO-GO of that part of L2,
  the L2 fallback line of section 2 applies.
- `SendMessage` can resume a finished subagent by its agent ID. It cannot resume a subagent that the user stopped (D12
  research, not verified live; L2). A question to such an agent goes to the Architect, with the transcript path.

## 4c. Contract: the audit log and the token lines (D13, D22)

Security zone: secrets in logs

`.guilda/audit.jsonl`, git-ignored. One JSON object on each line. Only the hooks of a subagent write it. A call of the
main session writes no line.

| `kind` | Written by | Fields |
|---|---|---|
| `tool` | PostToolUse in a subagent (`agent-trace.mjs`) | `t`, `session`, `agentId`, `agentType`, `task`, `tool`, `target` |
| `end` | SubagentStop (`agent-end.mjs`) | `t`, `agentId`, `agentType`, `task`, `transcript`, `copy` |

- A write error of the audit log does not stop the tool call. The hook exits 0 and writes nothing (fail open for a

## 4d. Contract: the block index and the citations (D27)

### Blocks

- A block starts at a heading `### <ID> — <title>`. It ends before the next heading of level 1, 2 or 3. So the
  section header is the anchor (D27 `@proposed`). A heading inside a code fence is not a block.
- An ID matches `^[A-Z][A-Z0-9-]*[0-9]+$`, for example `D14`, `S3`, `T2`, `ARC7`, `SC-G5`. A heading such as
  `### ARC7, ARC8, ARC10 — …` is not a block.
- The indexed files: each Markdown file under `docs/superpowers/specs/`, with its `<feature>.plan.md` files. The
  core rules are in the plugin, not in the project, so they are not indexed.
- Hash (D27 `@proposed`): SHA-256 of the title plus the body, first 8 hex characters. First the code removes the four
  tags with their backticks: `@decided`, `@proposed`, `@open`, `@replaced`. Then it collapses each run of white space
  to one space. So a status change and a new line wrap give no alarm. Any other change raises it (D27 `@decided`).
- The register puts the status of an entry in its body (`Status: …`). So the code removes the tags from the body too
  (the Architect's choice).

### Keys

One key form serves each use: a `Uses:` item, an owner, a citer, an `ack` argument and the `key` of a `task` event.
The form is `[<stem>#][Part<N>.]<ID>`.

- `<stem>` is the file name with no folder and no `.md`, for example `2026-11-10-guilda-0.3.0` or `login.plan`. No
  key has a folder path. Two indexed files with the same stem are an error: `DUPLICATE-FILE <stem>`.
- The key of a block is its bare ID when the ID is unique in the indexed files.
- An ID in two files: each block gets the key `<stem>#<ID>`, and a bare citation of that ID is `AMBIGUOUS`. The
  release specs repeat `S1`, `S2` and so on, so a scenario citation uses this form, for example
  `2026-11-10-guilda-0.3.0#S4`.
- A plan task always has the stem in its key: `login.plan#T2`. A plan task ID can be in two `## Plan: Part N`
  sections of one file. Then the key is `<stem>#Part<N>.<ID>`, for example `login.plan#Part2.T1`. The `task-brief`
  copy of 0.2.0 has `--part` for the same case, and so has `queue init` (section 4a).
- A dispatch as a citer has the key `journal#<address>`, for example `journal#T2-exe-7f2a`.
- Another ID twice in one file: `DUPLICATE <ID> <file>:<line>,<line>`, an error. Such a block cannot be cited.
- An ID that moves to another file keeps its bare key and its hash. The check finds it in the new file and gives no
  alarm (L3).

### Citations

- A plan task: the lines under its heading. `Uses: D14@3f2a9c1b, D27@0b1c2d3e` (D27 `@decided`). `Owns: D14` names the
  items that the task builds (ARC8).
- A plan: one line `Covers: D12, D13, D14` under the `## Plan: Part N` heading, or at the top of a `<feature>.plan.md`.
  It lists the items of the spec that the plan builds (the Architect's choice).
- A brief: the optional field `Uses:`, with the same form. `validateBrief` checks the form of each item,
  `<key>@<8 hex>`, when the field exists. A brief of 0.2.0 has no such field and stays valid.
- A dispatch: the `dispatch` event records the `Uses:` line of its brief. A brief file is in `.guilda/work/`, which git
  ignores (0.2.0, section 3f). So the citer of a brief is its `dispatch` event, not the file.
- Which dispatches count: only the last work-run `dispatch` event of each task whose state is not `done` or `dead`.
  A `dispatch` event of an older attempt is not a citer. A task that is closed has no citer in the journal. So
  a `SUSPECT` line of an old dispatch goes away in two cases. The task gets a new dispatch with the hash now, or
  the task closes.

### `.guilda/trace/index.json`

Generated, never edited by hand (D27 `@proposed`), git-ignored.

```
{ "generator": "guilda 0.3.0", "builtAt": "<ISO>", "head": "<commit>",
  "files": ["docs/superpowers/specs/2026-11-09-guilda-decisions.md"],
```

- The read commit (D27 `@decided`: the index records the commit at which each brief read each block). For a dispatch

  `<key>@<hash>` to the plan file, as in the lab.
- A rebase can remove a read commit from the history. Then `readCommit` is `null`. The check shows the block now with
  the note `the read commit is not in the history` (L3).

### The `trace` command

`node scripts/trace.mjs <projectDir> <command>`:

| Command | Output | Exit |
|---|---|---|
| `index` | `trace: <n> blocks, <n> citations` | 0, or 1 on a `DUPLICATE` |
| `check [--short]` | one line for each finding: `SUSPECT <citer> <key> <cited hash> → <hash now>`, then the block at the read commit and now (only the changed lines with `--short`), then the line `read the change; the task can still match`. `UNKNOWN <citer> <key>`. `AMBIGUOUS <citer> <ID>`. `DUPLICATE …`. `NO-USES <citer>` for a plan task in the R31 scope with no `Uses:` line. `NO-OWNER <plan> <ID>`. `LEGACY <citer>` for a plan task from before the install (section 3a) | 1 on `SUSPECT`, `UNKNOWN`, `AMBIGUOUS`, `DUPLICATE` or `NO-USES`; 0 with only `NO-OWNER` and `LEGACY` |

- `ack` for a brief: the brief is a file in `.guilda/work/`. The Architect writes the new hash in the brief and

## 4e. Contract: the cost record (D35)

- When: at the end of a build. A build is the tasks of one plan in the queue (the `plan` event). The Architect runs
  `node scripts/cost.mjs <projectDir> --prices <file> [--work <work ID>] [--session <transcript>]`.
  `--work` picks the build (X4). Without it the script takes the one work of the journal. With two works or more
  and no `--work`, it exits 1 with `refused: name the work` and lists the work IDs. The date of the record is the
  UTC date of the run.
- Sources (D35 `@proposed`):
  - the `tokens` lines of the audit log, for each agent;
  - the `usage` list of the end signal of each external run (section 4a);
  - the session level, from `analyze-token-usage.py` of `superpowers` (D51).

  The `cswap` usage is a 0.5.0 source (D22). 0.3.0 does not read it (the Architect's choice; section 5 asks it).
- The prices file. D35 `@proposed` says: the current price from the official source at the time of the record, never
  from memory. So the Architect reads the official price page of the model provider on the day of the record. It
  also reads the exchange rate of that day. It writes both in a file, and it gives the file with `--prices`. The
  script makes no network call.

```
{ "priceDate": "2026-11-10", "priceSource": "<URL of the official price page>",
  "models": { "<model id>": { "input": 0, "output": 0, "cacheRead": 0, "cacheCreation": 0 } },
  "usdPerMTok": true, "brlPerUsd": 0, "rateDate": "2026-11-10", "rateSource": "<URL>" }
```

- Each price is in US dollars for one million tokens. The rate source is the PTAX rate of the Banco Central do Brasil
  (the Architect's choice, section 5).
- The script refuses a prices file whose `priceDate` or `rateDate` is not the date of the record (exit 1,
  `refused: prices of <date>, the record is <date>`). It refuses a model of the audit log with no price, and names it.
- The record: `.guilda/costs/<plan name>-<date>.json`. `<plan name>` is the plan file name without `.md` and
  without `.plan`, as in 0.2.0.

```
{ "generator": "guilda 0.3.0", "build": "<plan file>", "from": "<ISO>", "to": "<ISO>",
  "prices": { the prices file },
  "tasks":  { "T3": { "tokens": { "input": 0, "cacheRead": 0, "cacheCreation": 0, "output": 0 }, "usd": 0, "brl": 0, "agentSeconds": 0 } },
  "blocks": { "D14": { "tokens": { … }, "usd": 0, "brl": 0 } },
  "session": { "tokens": { … }, "usd": 0, "brl": 0 } or null,
  "total":  { "tokens": { … }, "usd": 0, "brl": 0, "agentSeconds": 0 } }
```

- A cost is at list price. A subscription does not pay list price. So the record is not an exact share of a
  subscription (D22 `@decided`, #3). The record and its summary line say "at list price".
- Per block (U6): the tokens of a task go to the blocks of its `Uses:` line, in equal parts. So the sum of the blocks
  equals the sum of the tasks that cite blocks.
- Rounding: US dollars and reals with 4 decimals in the file, 2 in the summary line.
- The record holds no account data (D22 `@decided`). It holds model IDs, because each price is for one model (U10).
- `analyze-token-usage.py` needs `python3` and `superpowers`. Without one of them, `session` is `null`, and the summary
  says `session: not measured`. The core file names the script only as an option (O8 of 0.2.0). Its own cost column
  uses fixed prices, so the script reads only its token sums. Not verified: that its output form stays the same in each
  `superpowers` 7.x. The build checks that the file exists, and it fails with a clear text when it does not (D51).
- The summary line, printed by the script: `cost: <plan name>: <tokens> tokens, US$ <n>, R$ <n> at list price (prices of <date>)`.
- The data skill of D25 (the Lab group) turns the records into information (D35 `@proposed`). That is the cost per
  task, per block and per release, and the trend. The AI data engineer skill of D45 reads the records for the estimate before a
  build. Neither skill writes a record.

  address (`T3-exe-7f2a`, U4) and the agent ID.
- `node scripts/status.mjs <projectDir> --agent <name>` prints the facts of that agent, in this order:

```
agent: T3-exe-7f2a (executor, claude, in session, agent a1b2c3)
```

  the role codes (X4). The command takes the two words as one quoted argument or as two arguments. It prints the
  work run of that role for that task. For a check role it prints each check run of that task.
- `<base>` is the `baseCommit` of the `dispatch` event. `<head>` is the `HEAD` of the repository at the time of the
  `done` signal: `sync` records it in the `signal` event as `head`, from `git rev-parse HEAD` in the project
  folder. With no git repository the line is `commits: not measured`.
- A role and a task with more than one attempt: one block of lines for each attempt.
- An unknown name: `status: no agent <name>` and exit 1.
- D32 `@proposed`: the Architect collects these facts, finds the cause and proposes the fix with the owner of each step.
  For the cause, the Architect dispatches a `lab-reader` with the session analysts of `superpowers` (D51). They are

## 4g. Contract: the `status` script (D21)

`node scripts/status.mjs <projectDir> [--json] [--events <n>] [--agent <name>]`. It reads `.guilda/`. It starts no agent and writes
no file. The `queue` script uses the same code to write `.guilda/status.md`.

```
guilda status — 2026-11-10T14:02:11Z
Tasks: pending 2 · ready 1 · dispatched 0 · running 2 · review 1 · done 4 · failed 0 · stalled 1 · held 0 · dead 0
Running:
  T3  executor  T3-exe-7f2a  claude  12m  41,200 tokens
  T5  executor  T5-exe-19cd  codex  31m  9,800 tokens  late: no heartbeat for 16m
Stalled:
  T4  executor  T4-exe-0b2e  claude  no-ack
Last events:
  13:59:40  T4  dispatched → stalled (no-ack)
  13:50:02  T3  dispatched → running (started)
  13:49:12  T3  ready → dispatched (dispatch)
Agent work: 3.4 h
```

- This text is exact for the fixture of S22, with `--events 3`. Each row starts with two spaces, and two spaces
  separate its columns. A section with no row is not printed.
- A `Running` row has the task, the role name, the address and the tool. Then it has the time in `running`, the
  tokens, and the `late` mark when it applies. A `Stalled` row ends with the `cause` of its `state` event (X5).
- `Last events`: the last `state` events, the newest first. `--events <n>` sets the count, default 10. The word in
  brackets is the `cause`.
- `Agent work`: the sum of `agentSeconds` in hours, with one decimal.
- `--json` prints one object with the same parts: `tasks` (a count for each state), `running`, `stalled`, `events`,
  `agentSeconds`.
- `late` is the mark of section 4a: the timeout passed, and the writer has not run `sync` yet.
- Exit 0. With no `.guilda/` folder, the R28 refusal of section 3d. With no queue, `guilda status: no queue yet`, exit
  0.
- Other tools (D21 `@proposed`, U8). The `queue` script writes the same text to `.guilda/status.md`, by temp file
  and rename. It does this after each command that changes a state. `guilda:init` adds one line to `AGENTS.md`: "guilda project status:
  read .guilda/status.md." The line names no plugin path, so no machine path enters the project (R19). Not verified:
  how Codex loads `AGENTS.md` (L5).
- A project that comes from 0.2.0 does not run `guilda:init` again (section 3d). So the line also comes through the
  migration path of 0.2.0. `guilda:update` offers it in its last step, with the write of the migrated config (0.2.0
  spec, section 3d). It writes the line only after the user says yes. A hook never writes `AGENTS.md`.
- `doctor` gets one line: `status line: PASS|UNKNOWN — <evidence>`. PASS: `AGENTS.md` has the line. UNKNOWN: it
  does not, and the evidence is `no status line in AGENTS.md; run guilda:update`.

## 6. Risks

- D14: a hook inside a subagent and a background dispatch are not verified live. L2 checks them. Without `agent_id` in
  a subagent hook, R32 loses its subagent part, and the audit log waits.
- D14: no daemon runs in 0.3.0. A stalled task shows only when the Architect runs `queue sync` or `status`. The
  `watch` of 0.5.0 closes this gap.
- D14: two Claude Code sessions in one project can both run the `queue` script. The lock keeps two runs apart, not
  two sessions. A second session that writes the queue breaks the flow. In 0.3.0 the role check of R32 refuses a
  subagent only (X2). The claim of 0.5.0 names one session.
- D12: a foreground subagent gets its `agent` event only at its end (X3). Until then `status` and the panel show its
  task as `dispatched`, with a `late` mark after the ack timeout.
- D13: a transcript copy (U2) keeps each secret that an agent read on disk. The folder is git-ignored. The risk is
  the same as the transcripts of Claude Code in the home folder.
- D13: each tool call of a subagent starts two more hook processes. The lab of 0.1.0 measured about 0.1 s for a Node
  hook. L2 measures the cost on a wave.
- D27: the hash removes the status tags. A change from `@proposed` to `@replaced` gives no alarm. The `Replaced by:`
  line that the register adds with it changes the body, so that line raises the alarm.
- D27: the lab showed that agents mix "suspect" with "does not match". The check line says "read the change; the task
  can still match", and R31 rejects only a content mismatch.
- D20: the click and the hover work only in a full-screen terminal (lab `agent-panel`). U3 keeps the command for the
  other cases.
- D20: a host with no mod support and a plugin with only a mod module are not verified (section 3c).
- D35: the official price page can change its form. The Architect reads it, and an agent can read a wrong number. The
  prices file names its source, so a person can check it.
- D35: R17 and the model IDs in the record (U10).
- D21: how Codex loads `AGENTS.md` is not verified (L5).
- D51: `analyze-token-usage.py` is a test script of `superpowers`, not a public interface. Its form can change in a
  7.x release.
