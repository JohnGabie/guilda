## 1. Intent

The field use of guilda and the labs of 2026-11-09 showed four problems:

- The flow lives only in the context of one agent. A compaction or a `/clear` loses which task runs, who runs it and
  what is late (D14, D50).
- A change in a spec does not reach the plan and the briefs that used it. Each agent reads the whole spec again to
  find out (D27).
- After the work, nobody can ask an agent why it did something, or see what it did (D12, D13, D32).
- Nobody knows what a task, a block or a build costs in tokens or in money (D22, D35).

0.3.0 puts the state of the flow and its history in files that do not compact. The flow, the block index, the audit
log and the cost record are code and data. A model reads them by ID. A mod shows them to the user (D20, D24).

0.3.0 is a minor release: it adds two core rules, R29 and R30 (0.x rule of `RELEASING.md`). No core rule changes
meaning.

Fallback lines of L1 (`@proposed`):

- `rename` is not atomic: no `state.json`. Each reader replays the journal.
- Two writers are not kept apart by the lock: the `queue` script refuses each run while a lock file exists. The user
  removes a stale lock by hand. No takeover.
- A writer that dies in an append leaves a bad line inside the journal, not only at its end. Then the reader skips
  each bad line and reports its line number.
- Codex heartbeats fail: a Codex task has no lease timeout, only the ack timeout and its end signal.
- Subagent heartbeats fail: a subagent task has no lease timeout. The `stalled` state then comes only from the ack
  timeout.

  state.

## 3a. New rules

R29 and R30 are new, so no rule changes meaning. R29 is the next free core ID after R28. Each block is in the form of
`core/rules.md`. The command: copy the block to a temporary file, then run
`node scripts/lint-rules.mjs --prefix R <file>`.

### R29 — Cite each block that a task uses (D27)

```
### R29 — Cite each block that a task uses
Rule:  Give each plan task and each brief a `Uses:` line that cites each block it uses with its hash.
Why:   A change to a cited block then reaches each task that used it, with no full read of the spec again.
Check: gate — The Reviewer runs the trace check and rejects a task or brief with no `Uses:` line, an unknown or ambiguous ID, or a suspect link whose change it did not read.
```

Linter: pass (exit 0).

- A suspect link is not a defect (D27, a fix from the lab). It asks the Reviewer to read the change. The brief can
  still match. The Reviewer rejects only a brief whose content no longer matches the block.
- The Architect runs the check before each dispatch (D27). A spec edit gets the check as a warning (section 4d).
- Scope: the plan tasks and the briefs written after the 0.3.0 install. A plan of 0.2.0 has no `Uses:` lines. The
  Reviewer does not reject a task of such a plan for R29 (tolerant reader, D40).

### R30 — One writer for the queue (D14)

```
### R30 — One writer for the queue
Rule:  Change the queue only through the queue script in the writer session, and never edit its files by hand.
Why:   A second writer or a hand edit breaks the journal, and then the state of the flow is a guess.
Check: law — PreToolUse refuses a Write, an Edit or a common shell write to the journal, the state file or the lock, and a queue script call from a subagent.
```

Linter: pass (exit 0).

- The files that R30 covers: `.guilda/queue/journal.jsonl`, `.guilda/queue/state.json` and `.guilda/queue/lock`. The
  signal files are not in this list. A worker writes them (section 4a).
- The hook reads the five shell forms of R4 in 0.2.0. They are a redirection (`>`, `>>`), `tee`, `cp`, `mv` and
  `touch`. It also reads `rm` of one of the three files. The hook catches the common forms, not each form. A path from a
  variable passes, as for R4 (S16).
- A subagent: the hook input has an `agent_id`. A queue script call is a `Bash` command whose first program is `node`
  and whose script path ends in `scripts/queue.mjs`. Not verified: the `agent_id` field in a subagent hook. L2 checks
  it. On a NO-GO of L2, the subagent part of the `Check:` line waits, and the line becomes the text below.

  ```
  Check: law — PreToolUse refuses a Write, an Edit or a common shell write to the journal, the state file or the lock.
  ```

  Linter: pass (exit 0) for the block with this line.
- Until 0.5.0 the writer session is the main session, where the Architect runs. From 0.5.0 it is the supervisor
  session (D15). R30 does not change then: the writer session is the session that holds the lock.
- Release: 0.3.0, because a new rule raises the minor number (`RELEASING.md`).

## 3d. Project layer and compatibility (D40)

- `schemaVersion` stays 2 (the Architect's choice, section 5). 0.3.0 adds no config field. The queue timeouts and the
  attempt limit are constants in `scripts/lib/queue.mjs` (section 4a). So no migration runs, and no project runs
  `guilda:init` again.
- Each reader of a new file is a tolerant reader (D40). It accepts the current format and each earlier format. It
  ignores an unknown field and an unknown event type. It uses a default for a missing field. No new file gets its own
  `schemaVersion`. The register replaced "each state file has a schemaVersion" with the contract of 0.2.0, section 3d.
- Generated files: `.guilda/queue/state.json`, `.guilda/trace/index.json` and `.guilda/status.md` record the version
  of guilda that wrote them in a `generator` field. A reader that finds another `generator` value builds the file

- A 0.2.0 install that reads a 0.3.0 project: it does not know the new files and ignores them. Its laws run.
- `.guilda/.gitignore`: `IGNORED` in `scripts/lib/violations.mjs` gets these lines: `queue/`, `audit.jsonl`,

## 4a. Contract: the queue (D14)

Security zone: file paths from IDs

The files (D14 `@proposed`, with one addition):

```
.guilda/queue/journal.jsonl                     append-only, one writer (R30)
.guilda/queue/state.json                        derived from the journal, written by temp file and rename
.guilda/queue/lock                              the writer of the current run
.guilda/queue/signals/<task>/<attempt>/<kind>   written by the worker of an external run
.guilda/queue/signals/agents/<agentId>/<kind>   written by the hooks of a Claude subagent (addition)
.guilda/queue/signals/agents/<agentId>/dispatch.json   written by the identity hook (section 4b)
```

- The addition (the Architect's choice): a hook inside a subagent knows its `agent_id`, not its task. So it writes its
  signals under the agent ID. The identity hook writes the task and the attempt of that agent in `dispatch.json`. The
  writer joins the two at `sync`. So no hook writes the journal (D14 `@decided`: one writer).
- `<kind>` is `started`, `heartbeat`, `done` or `failed`. Each signal file has one writer. `heartbeat` is written again
  by temp file and rename. The other kinds are written one time.
- IDs in paths: a task ID, an attempt number and an agent ID match `^[A-Za-z0-9._-]{1,64}$`. They are not `.` or
  `..`. Each script refuses another value with exit 1, and it writes no file (S17).

### Journal events

One JSON object on each line. Each event has `seq` (1, 2, 3 and so on), `t` (ISO time) and `type`. A line that does not
end with a newline is a partial line: the reader skips it. A line that is not JSON is skipped and reported with its
line number.

| `type` | Fields | Written by the command |
|---|---|---|
| `plan` | `plan` (the plan file path), `slots` (the number of tasks that can run at the same time) | `queue init` |
| `task` | `task`, `title`, `deps` (task IDs), `uses` (the `Uses:` keys), `owns` | `queue init`, `queue add` |
| `dispatch` | `task`, `attempt`, `address`, `role`, `tool` (`claude` or `codex`), `tier`, `session`, `briefFile`, `baseCommit`, `uses` | `queue dispatch` |
| `agent` | `task`, `attempt`, `agentId` | `queue sync`, from a `dispatch.json` |
| `signal` | `task`, `attempt`, `kind`, `at`, `reason`, `tokens` | `queue sync`, from a new signal file |
| `state` | `task`, `from`, `to`, `cause` | each command that changes a state |
| `decision` | `task`, `decision` (`approve`, `reject`, `retry`, `hold`, `release`), `by` | `queue approve`, `reject`, `retry`, `hold`, `release` |
| `takeover` | `oldPid`, `oldSession` | the first command after a stale lock |

- D14 `@decided`: the dispatch event records the address, the agent ID, the tool, the session and the `Uses:` line.
  The agent ID arrives later, in the `agent` event, because the host gives it after the dispatch. The address has the
  form of D17: `<task>-<role code>-<4 hex>`, for example `T3-exe-7f2a`. The role codes: `arc`, `exe`, `rev`, `qa`,
  `sec`, `vc`, `lab`. U4 asks the user about the address in 0.3.0.
- The `held` state has no reason field (D48 `@decided`). No event of the journal says why a task waits. The
  `decision` event of a hold has no text field.

### `state.json`

```
{ "generator": "guilda 0.3.0", "journalSeq": 41, "plan": "docs/superpowers/specs/login.plan.md", "slots": 3,
  "tasks": { "T3": { "state": "running", "attempt": 1, "address": "T3-exe-7f2a", "agentId": "a1b2c3",

```

- `journalSeq` is the `seq` of the last event in the fold. A reader with a journal whose last `seq` is higher folds the

- `agentSeconds` is the sum of the time in `running` of each attempt. The panel and `status` use it for the work hours
  (D20 `@decided`, U5).

### States and transitions

D14 has the table, and the register says that the plan states who sets each state and when. Here is that table. The
plan copies it. In 0.3.0 the writer is the `queue` script that the Architect runs.

| From | To | Who sets it | When |
|---|---|---|---|
| (new) | `pending` | writer, `queue init` or `queue add` | the task enters the queue |
| `pending` | `ready` | writer, `queue sync` | each dependency is `done` |
| `ready` | `dispatched` | writer, `queue dispatch <task>` | a slot is free; the command prints the address and the attempt |
| `dispatched` | `running` | writer, `queue sync` | a `started` signal of that attempt |
| `running` | `review` | writer, `queue sync` | a `done` signal of that attempt (D14 `@decided`: `review` when the agent delivers its report) |
| `review` | `done` | writer, `queue approve <task>` | the written approval of the Reviewer (R24) |
| `review` | `ready` | writer, `queue reject <task>` | a rejection; the attempt number plus one |
| `running` | `failed` | writer, `queue sync` | a `failed` signal |
| `dispatched` or `running` | `stalled` | writer, `queue sync` | no `started` in the ack timeout, or no heartbeat in the lease timeout |
| `stalled` | `running` | writer, `queue sync` | a new heartbeat of the same attempt |
| `stalled` | `review` | writer, `queue sync` | a late `done` of the same attempt (L1 case) |
| `failed` or `stalled` | `ready` | writer, `queue retry <task>` | a decision of the Architect; the attempt number plus one |
| `pending`, `ready`, `failed` or `stalled` | `held` | writer, `queue hold <task>` | a decision of the Architect (D48) |
| `held` | `pending` | writer, `queue release <task>` | a decision of the Architect |
| any open state | `dead` | writer, `queue retry` or `queue reject` | the next attempt would be the fourth |

- Three rows are not in the D14 table: `review` to `done`, `review` to `ready`, and the late `done`. They come from
  the `@decided` item on `review`. Section 5 asks the user to approve them.
- `stalled` never dispatches the task again by itself (D14). A retry uses a new attempt and its own worktree or branch.
- A signal of an old attempt is recorded as a `signal` event and changes no state.
- The attempt limit is 3 (the Architect's choice). It matches R10, a new tier after two failures. It matches R11,
  where the third rejection goes to the Architect and the user. `dead` goes to the Architect and the user.
- The timeouts are the start values of SC-G6, and L1 measures them. The ack timeout is 2 min. The lease timeout ends
  at the later of two times. They are `busyUntil` plus 5 min, and the last heartbeat plus 15 min. `busyUntil` is the time of
  the heartbeat plus the timeout of the current tool call. That is the `timeout` of a `Bash` call, or 10 min.
- The writer checks the timeouts only when it runs. No daemon runs in 0.3.0. So the Architect runs `queue sync`
  before each dispatch and before it reads the state. `status` shows a `late` mark from the same timeouts, and it
  writes nothing.

### Signals

| Kind | Claude subagent: who writes it (U9) | External run: who writes it | Content |

| `started` | the SubagentStart hook of the agent | the run wrapper, before the run | `{ "at": "<ISO>" }` |
| `heartbeat` | the PreToolUse hook in the agent (`agent-trace.mjs`) | the run wrapper, at each JSON event of the tool | `{ "at": "<ISO>", "busyUntil": "<ISO>", "tokens": <n or null> }` |

- A stop by the user gives no signal. The task becomes `stalled` with the cause `no-signal`, and the Architect asks the
  user (SC-G4).
- The run wrapper of 0.3.0 is the `signal` script around the external command:
  `node scripts/signal.mjs run <task> <attempt> -- <command...>`. It writes `started`, then a `heartbeat` at each

- The wrapper also writes `.guilda/logs/<address>.jsonl` for the panel (section 4h). This log has command text and

- Not verified: which `SubagentStop` input field tells a normal end from an error. L2 checks it. Until then, each end
  is `done` with the reason `finished`, and the Reviewer finds a bad result.

### Lock and recovery

- Each run of the `queue` script creates `.guilda/queue/lock` with the exclusive flag (`wx`). The content:
  `{ "pid": <n>, "session": "<id or null>", "at": "<ISO>" }`. The script removes its own lock at its end. First it
  reads the file and checks that the `pid` is its own (R20: one exact path, one file).
- A lock exists and its `pid` is alive: the script exits 3 with `queue locked by pid <n>`.
- A lock exists and its `pid` is not alive: the script writes a `takeover` event and its own lock. Then it goes on.
- Recovery at each run (D14 `@proposed`):
  1. Take the lock.
  2. Replay the journal, and skip a last partial line.
  3. Turn each new signal file into a `signal` event.
  4. Check the timeouts.
  5. Write `state.json`.
  6. Remove the lock.
- A failed write of the journal or of `state.json`: the script exits 2 with `io-error: <path>`, and writes no
  dispatch (SC-G13).

`node scripts/queue.mjs <projectDir> <command> [args]`:

| Command | Effect | Output, first line |
|---|---|---|
| `init <plan file> --slots <n>` | `plan` and `task` events from the `### T<n> — ` tasks of the plan, with their `Dependencies:`, `Uses:` and `Owns:` lines | `queue: <n> tasks` |
| `add <task> --title <text> [--deps T1,T2]` | one `task` event | `queue: added <task>` |
| `sync` | the recovery steps | `queue: <n> events` |
| `dispatch <task> --role <role> --tool <tool> --tier <tier> [--brief <file>] [--base <commit>]` | `dispatch` and `state` events | `dispatched <task> attempt <n> address <address>` |

- A command that a state does not allow exits 1 with `<task>: <command> not allowed in <state>`, and writes nothing.
- `dispatch` of a task that is not `ready`, or with no free slot, exits 1.
- A plan with a dependency cycle: `init` exits 1 and names the cycle (SC-G14).

## 4d. Contract: the block index and the citations (D27)

### Blocks

- A block starts at a heading `### <ID> — <title>`. It ends before the next heading of level 1, 2 or 3. So the
  section header is the anchor (D27 `@proposed`). A heading inside a code fence is not a block.
- An ID matches `^[A-Z][A-Z0-9-]*[0-9]+$`, for example `D14`, `S3`, `T2`, `ARC7`, `SC-G5`. A heading such as
  `### ARC7, ARC8, ARC10 — …` is not a block.
- The indexed files: each Markdown file under `docs/superpowers/specs/`, with its `<feature>.plan.md` files. The
  core rules are in the plugin, not in the project, so they are not indexed.
- Hash (D27 `@proposed`): SHA-256 of the title plus the body, first 8 hex characters. First the code removes the four
  tags with their backticks: `@decided`, `@proposed`, `@open`, `@replaced`. Then it collapses each run of white space
  to one space. So a status change and a new line wrap give no alarm. Any other change raises it (D27 `@decided`).
- The register puts the status of an entry in its body (`Status: …`). So the code removes the tags from the body too
  (the Architect's choice).

### Keys

- The key of a block is its ID when the ID is unique in the indexed files.
- An ID in two files: each block gets the key `<file name without .md>#<ID>`, and a bare citation of that ID is
  `AMBIGUOUS`. The release specs repeat `S1`, `S2` and so on, so a scenario citation uses this form, for example
  `2026-11-10-guilda-0.3.0#S4`.
- A plan task ID can be in two `## Plan: Part N` sections of one file. Then each task gets the key
  `<file name>#Part<N>.<ID>`. The `task-brief` copy of 0.2.0 has `--part` for the same case.
- Another ID twice in one file: `DUPLICATE <ID> <file>:<line>,<line>`, an error. Such a block cannot be cited.
- An ID that moves to another file keeps its bare key and its hash. The check finds it in the new file and gives no
  alarm (L3).

### Citations

- A plan task: the lines under its heading. `Uses: D14@3f2a9c1b, D27@0b1c2d3e` (D27 `@decided`). `Owns: D14` names the
  items that the task builds (ARC8).
- A plan: one line `Covers: D12, D13, D14` under the `## Plan: Part N` heading, or at the top of a `<feature>.plan.md`.
  It lists the items of the spec that the plan builds (the Architect's choice).
- A brief: the optional field `Uses:`, with the same form. `validateBrief` checks the form of each item,
  `<key>@<8 hex>`, when the field exists. A brief of 0.2.0 has no such field and stays valid.
- A dispatch: the `dispatch` event records the `Uses:` line of its brief. A brief file is in `.guilda/work/`, which git
  ignores (0.2.0, section 3f). So the citer of a brief is its `dispatch` event, not the file.

### `.guilda/trace/index.json`

Generated, never edited by hand (D27 `@proposed`), git-ignored.

```
{ "generator": "guilda 0.3.0", "builtAt": "<ISO>", "head": "<commit>",
  "files": ["docs/superpowers/specs/2026-11-09-guilda-decisions.md"],
  "blocks": { "D14": { "file": "docs/superpowers/specs/2026-11-09-guilda-decisions.md", "start": 330, "end": 377,
                       "title": "Agent queue in code", "hash": "3f2a9c1b",
                       "owners": ["docs/superpowers/specs/login.plan.md#T2"],
                       "citers": [ { "citer": "journal#seq=12", "hash": "3f2a9c1b", "readCommit": "<commit>" } ] } },
  "errors": [ { "kind": "DUPLICATE", "id": "S3", "where": ["<file>:<line>", "<file>:<line>"] } ] }
```

- The read commit (D27 `@decided`: the index records the commit at which each brief read each block). For a dispatch
  event, it is the `baseCommit` of the brief (U6 of 0.2.0). For a plan task, it is the oldest commit that added
  `<key>@<hash>` to the plan file, as in the lab.
- A rebase can remove a read commit from the history. Then `readCommit` is `null`. The check shows the block now with
  the note `the read commit is not in the history` (L3).

### The `trace` command

`node scripts/trace.mjs <projectDir> <command>`:

| Command | Output | Exit |
|---|---|---|
| `index` | `trace: <n> blocks, <n> citations` | 0, or 1 on a `DUPLICATE` |
| `check [--brief]` | one line for each finding: `SUSPECT <citer> <key> <cited hash> → <hash now>`, then the block at the read commit and now (only the changed lines with `--brief`), then the line `read the change; the task can still match`. `UNKNOWN <citer> <key>`. `AMBIGUOUS <citer> <ID>`. `DUPLICATE …`. `NO-OWNER <plan> <ID>` | 1 on `SUSPECT`, `UNKNOWN`, `AMBIGUOUS` or `DUPLICATE`; 0 with only `NO-OWNER` |
| `show <key> [--at <commit>]` | only the lines of that block, then its owners and citers | 0, or 1 for an unknown key |
| `ack <citer> <key>` | writes the hash now into the `Uses:` line of that plan task, then builds the index again | 0 |

- `NO-OWNER` counts only the IDs that the plan covers (D27 `@decided`). It names an ID of the `Covers:` line that no
  `Owns:` line of the same plan names. It is a warning.
- `ack` for a brief: the brief is a file in `.guilda/work/`. The Architect writes the new hash in the brief and
  dispatches again. `ack` does not change a journal event.
- The warning after a spec edit (D27 `@proposed`). After a `Write` or an `Edit` of an indexed file,
  `scripts/hooks/post-tool-use.mjs` runs the check. It puts the `SUSPECT` and `UNKNOWN` lines in `additionalContext`. It shows
  at most 15 lines, and it refuses nothing.
- Read by ID (D27 `@decided`). The Architect, the Executor and the Reviewer read a block with `trace.mjs show <key>`.
  They never read the whole spec for one ID.

## 6. Risks

- D14: a hook inside a subagent and a background dispatch are not verified live. L2 checks them. Without `agent_id` in
  a subagent hook, R30 loses its subagent part, and the audit log waits.
- D14: no daemon runs in 0.3.0. A stalled task shows only when the Architect runs `queue sync` or `status`. The
  `watch` of 0.5.0 closes this gap.
- D14: two Claude Code sessions in one project can both run the `queue` script. The lock keeps two runs apart, not
  two sessions. A second session that writes the queue breaks the flow. R30 covers subagents only.
- D13: a transcript copy (U2) keeps each secret that an agent read on disk. The folder is git-ignored, and the R19
  hook refuses a commit of it. The risk is the same as the transcripts of Claude Code in the home folder.
- D13: each tool call of a subagent starts two more hook processes. The lab of 0.1.0 measured about 0.1 s for a Node
  hook. L2 measures the cost on a wave.
- D27: the hash removes the status tags. A change from `@proposed` to `@replaced` gives no alarm. The `Replaced by:`
  line that the register adds with it changes the body, so that line raises the alarm.
- D27: the lab showed that agents mix "suspect" with "does not match". The check line says "read the change; the task
  can still match", and R29 rejects only a content mismatch.
- D20: the click and the hover work only in a full-screen terminal (lab `agent-panel`). U3 keeps the command for the
  other cases.
- D20: a host with no mod support and a plugin with only a mod module are not verified (section 3c).
- D35: the official price page can change its form. The Architect reads it, and an agent can read a wrong number. The
  prices file names its source, so a person can check it.
- D35: R17 and the model IDs in the record (U10).
- D21: how Codex loads `AGENTS.md` is not verified (L5).
- D51: `analyze-token-usage.py` is a test script of `superpowers`, not a public interface. Its form can change in a
  7.x release.

Each question waits for the user or for a lab. The Architect asks them with the question tool (D23) before the task
that needs the answer.

- O1 (D12, D13, D14): the hook input fields of a subagent and of `SubagentStop`, and the transcript fields. L2 answers
  them. The tests of S16, S18, S20 and S21 use the field names that L2 records.

  `done` (section 4a).

  `--session` when it has the ID, and the field is `null` when it does not. Not verified: that a skill can read
  `${CLAUDE_SESSION_ID}`.

  The build checks it.

  is its own plugin. L4 records the answer.
- O6 (D21): how Codex loads `AGENTS.md`. L5 answers it.
- O7 (D35): the official price page and the PTAX page change their form over time. The Architect reads them on the
  record day. A later release can read them with a script, after a lab.
- O8 (D50): the project memory store, JSONL or a database, and a map of the logs. The D50 research waits (register).
  0.3.0 keeps the way open (section 4i).
