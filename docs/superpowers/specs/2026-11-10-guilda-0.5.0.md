## 1. Intent

0.4.0 moves the Architect out of the main session, and it gives agents addresses and a bus. Three problems stay:

- Nobody runs the flow when the Architect waits for the user. A ready task waits, and a stalled agent stays stalled.
- The number of agents does not follow the usage that is left on the accounts. The work passes a limit or stands still.
- The work stops when the usage runs out, and it starts again only when the user comes back.

0.5.0 adds the supervisor and the pace for these problems. It also adds the Security Lead and the Security Executor
with the red team limits as laws (D16, D28, D37). It adds the council (D47) and away mode (D48), with the user's
approval of their release.

The goal (D22, `@decided`): a constant flow that does not pass a limit and does not stand still. The supervisor
runs the work that the Architect designed. It does not own the project (D15).

0.5.0 is a minor release. It adds rules, roles and skills, and no core rule changes meaning (`RELEASING.md`).

Each block has the form of `core/rules.md`. A `Check:` line is one line. The command: copy the block to a temporary

### R32 does not change (D14, X2)

0.5.0 adds no rule for the writer of the queue. R32 keeps its 0.3.0 text. Only the role check of its hook gets the
0.5.0 row of X2. That row is the supervisor session while its claim is live, and the Architect agent with no live

### R36 — Only the user starts the supervisor (D15 G5)

```
### R36 — Only the user starts the supervisor
Rule:  Start the supervisor only on the user's request, and let no hook start it or ask for it.
Why:   A hook that starts the supervisor acts without the user, and after a restart only the user starts the work again (D15 G5).
Check: gate — The hooks test fails when a hook command starts a Claude Code session or a `/loop`, or prints an offer to start the supervisor.
```

Linter: pass (exit 0). G5 is D15 `@decided`.

### R37 — Red team limits (D16, D28)

```
### R37 — Red team limits are laws
Rule:  Run red team work only on this project's code, in a local test environment, after the user approves the task.
Why:   The text of a skill is not a safety control, and an attack on a host that the project does not own harms other people (D16, D28).
Check: law — The `tools` list of the Security Executor and a PreToolUse hook on its `agent_type` refuse an outside host, a credential read, a persistence step and a run with no recorded approval.
```

Linter: pass (exit 0). The limits are D16 `@proposed`. The form "a `tools` list plus a hook on `agent_type`" is D28
`@decided`.

### R38 — Usage is read only (D22)

```
### R38 — Read usage only, never switch accounts
Rule:  Read usage only through the read-only usage command of the `cswap` fork, and never switch or list accounts.
Why:   A switch or a list from an agent acts on the user's accounts and can leak an email or a token (D22).
Check: law — PreToolUse refuses a `Bash` command that runs `cswap switch` or `cswap list`, from each session and each agent.
```

Linter: pass (exit 0). D22 `@decided`: guilda never uses `cswap list --json` and never runs `cswap switch`.

### R39 — The away file (D48)

```
### R39 — Only the Architect reads the away state
Rule:  Keep the away state in its file outside the project, and let no agent except the Architect read it.
Why:   An agent that knows the user is away can act differently, and a compaction can drop the Architect's memory (D48, D39).
Check: law — PreToolUse refuses a read of the away folder, and a run of the away script, from each agent that is not the Architect.
```

Linter: pass (exit 0). The place outside the project and the read refusal are D48 `@proposed`. "Held by code and a
hook" is D48 `@decided`. The hook fails closed (X9): when it cannot parse its input, it refuses the read.

### R40 — The user's actions wait while the user is away (D48)

```
### R40 — Actions that need the user wait
Rule:  While the user is away, refuse each action that needs the user with a neutral reason, and tell the Architect.
Why:   A decision of the user cannot come from an agent, and a reason that names the absence leaks it (D48, R12).
Check: law — PreToolUse refuses a council open, a publish command and a merge to the main branch while the away file is set.
```

Linter: pass (exit 0). D48 `@proposed`. The hook fails closed (X9): a read error of the away file counts as "set",
and the hook refuses the action. A file that does not exist means "not away".

### R41 — The resume trigger is bound to one project (D38)

```
### R41 — A resume runs only in its own project
Rule:  Resume stopped work only in the project folder and for the work ID that the trigger record names.
Why:   A trigger in another folder or for other work starts agents that the user did not ask for (D38).
Check: law — PreToolUse refuses a resume run for another project. The resume script exits with no action when the path or the work ID is not that of the record.
```

Linter: pass (exit 0). D38 `@decided`. The hook part: PreToolUse refuses a `Bash` call of `resume.mjs run` whose
`--project` value is not the main project root of the hook input (X9). The trigger itself runs outside a session,
so there the script check is the one guard. U5-14 asks the user for this line.

### ARC11 to ARC13 — Architect rules (D22, D47, D48)

```
### ARC11 — Set the pace with the user in the plan
Rule:  Set the pace and its policy with the user in the plan, and change them only with the user.
Why:   The pace spends the user's usage, so it is the user's number (D22, R12).
Check: gate — The Reviewer rejects a plan with no pace line, and PreToolUse refuses a write to `.guilda/pace.json` from each agent that is not the Architect.

### ARC12 — Open a council only for a serious problem
Rule:  Refuse a council request that one question to the user answers, and open a council only on the user's yes.
Why:   Each lead in a council is an agent with its own context, so a council costs many tokens (D47).
Check: judgment — The Architect decides the refusal, and the council script refuses an `open` message with no verified user record.

### ARC13 — The same care while the user is away
Rule:  Work with the same care and rigor while the user is away, and hold only the decisions of the user.
Why:   A model can act differently when it knows that nobody watches it (D39, D48).
Check: judgment — A Lab study (D46, D39) tests it, so this rule is text only now.
```

Linter: pass (exit 0) for each block, with `--prefix ARC`. ARC11 is D22 `@decided` ("the Architect sets the pace
with the user"). ARC12 is D47 `@decided`. ARC13 is D48 `@decided` (the explicit instruction).

### SUP1 to SUP3 — Supervisor rules, in `agents/supervisor.md`

```
### SUP1 — One precise question to the Architect
Rule:  Near a limit or under the pace, ask the Architect one question: facts, 2 or 3 options, a recommendation.
Why:   The Architect owns the pace decision, and a question with no facts or options costs a second round (D22).
Check: gate — The supervisor eval rejects a question with no facts, with fewer than 2 or more than 3 options, or with no recommendation.

### SUP2 — Talk to the Architect, never to the user
Rule:  Send each message for the user to the Architect, and never ask the user a question yourself.
Why:   The user talks only to the main session, and a second voice gives the user two sources of truth (D15).
Check: judgment — The supervisor tools have no question tool, and no hook sees a text reply.

### SUP3 — Stop an agent only after a safe save or the Architect
Rule:  Stop an agent only after a safe save, or after the Architect agrees to an extreme stop.
Why:   A stop with no save loses the work of the agent, and that loss is an extreme step (D15 G18).
Check: law — PreToolUse refuses a stop of a run with no `stop` decision. `tick` refuses that decision with no `save-ok` or `architect-ok` decision.
```

Linter: pass (exit 0) for each block, with `--prefix SUP`. SUP1 is D22 `@decided`: one precise question with the
facts, 2 or 3 options and the recommendation. SUP2 is D15 `@proposed`. SUP3 is D15 G18 `@decided`. Its order: the supervisor writes `save-ok` or gets `architect-ok`, then it writes the
`stop` decision, then it stops the agent. The PreToolUse hook refuses `bus.mjs stop --address <a>` from the session
of the claim when the journal has no `stop` decision for the running attempt of that address. For a subagent, the
hook also reads the stop tool of the host, whose name L5-1 (f) records; the matcher of X6 gets that tool then. A
`save-ok` decision has the field `commit`: a commit of the worktree of the task that holds the work of the agent.
`tick` checks that the commit exists, and it refuses a `save-ok` with no such commit. The `save-ok` and
`architect-ok` values of the `decision` event are `@proposed`.

## 5. Contracts

### 5a. The supervisor session (D15)

`@proposed` unless a line says otherwise. L5-1 gates this section.

- Who: a Claude Code session in the project folder, with the agent definition `agents/supervisor.md`. Its group is
  `engineering` (0.2.0 spec, section 3e, `@decided`).
- Start: only the user starts it (G5, `@decided`, R36). The method comes from L5-1 (e). No hook starts it, and no
  hook asks. After a restart of the session or the machine, the user starts it again.
- Not verified: the hook input of a session that `claude --agent` started. It can have an `agent_type` and no
  `agent_id`, or neither. L5-1 (e) records it. This spec tells the supervisor session from others only by its
  session ID and the claim (X2). So it needs no `agent_type`.
- Identity. The session start line `guilda session: <id>` gives the supervisor its session ID (X2). It passes
  `--session <id>` to each call of the queue script, `tick` and `watch`. The R32 hook refuses a call whose
  `--session` is not the `session_id` of the hook input. It also refuses a call with an `agent_id`.
- The claim (X2). At its start the supervisor runs `queue claim --session <id> [--ttl <seconds>]`. The command
  writes `writer.json` and one `claim` event.
  - Who can claim. `claim` is the one queue command that the R32 hook passes for each caller with no `agent_id`,
    with or without a live claim. Its `--session` must be the `session_id` of the hook input. The hook refuses
    `claim` from each agent. The script then decides: with a live claim of another session it exits 3.
  - No hook can tell the supervisor session from the main session: both have no `agent_id`. So the main session
    can run `queue claim`. R36 and `core/main-session.md` tell it not to, and section 7 has the risk.
  - Live. A claim is live while `aliveAt` + `ttlSec` is after now. `ttlSec` is in `writer.json`. Its default is
    600. So each reader can tell a live claim with no other file.
  - Refresh. Each run of the queue script, of `tick` and of `watch` with the `--session` of the claim writes
    `aliveAt` again. `watch` does it at each read (SC-G5). So a turn of the supervisor can last 10 min with no
    call before the claim ends.
  - `pid` is the PID of the last `watch` process, or `null`. It is a fact for the user. It is not part of the test.
  - A second supervisor runs `queue claim`. With a live claim of another session the command exits 3 with
    `claimed by session <id>`, and that supervisor stops and tells the Architect. With a claim that is not live,
    the command takes it over: its `claim` event has `takeover: true`.
- With no live claim (no supervisor), the Architect agent is the writer, as in 0.4.0 (D14 `@decided`, X2).
- No voice of the user. A prompt in the session of a live claim is a `/loop` tick or a resume prompt. So
  `user-prompt-submit.mjs` writes no user record for that session, and the R34 check refuses `--from main` from
  it. 0.5.0 adds both tests to the 0.4.0 code.
- Talk: it never talks to the user (SUP2). It reads the mailbox of `supervisor`, and it sends to `main` and to
  `architect` with `bus.mjs send --from supervisor` (A8, A9). R34 passes `--from supervisor` only for the session of
  the live claim, with no `agent_id`.
- Loop: `/loop` runs `node scripts/tick.mjs <projectDir> --json --session <id>` at each tick. Between ticks the
  session sleeps in `watch`, a background command. A healthy flow costs no tokens (D15, the user's idea).
- Reconcile at start (SC-G5): first the D14 recovery. Then an attempt of a Claude subagent from an ended session
  becomes `stalled`, with the `cause` `session-ended` (X5). A dead process is a fact, so the supervisor runs
  `queue retry` (R9).
- The controller of the queue work. While a claim is live, the supervisor session is the controller of each task
  of the queue: it dispatches each work run and each check run, and it runs each queue command. The Architect
  agent stays the controller of labs, of a council and of each dispatch outside the queue. With no live claim the
  Architect is the controller of all, as in 0.4.0.

  | Queue command | While a claim is live |
  |---|---|
  | `init`, `add` | The Architect sends a `request` to `supervisor` with the plan path, or the task. The supervisor runs the command and replies with its output |
  | `sync`, `dispatch`, `dispatch --check`, `retry`, `slots` | The supervisor runs it by itself, from the facts of the files (R9) |
  | `approve`, `reject` | The supervisor runs it from the written verdict of the Reviewer run that it dispatched (R24). It counts the rejections of a task. A `REJECTED-LARGE` or a third rejection goes to the Architect as one question (R11, SUP1) |
  | `hold`, `release`, and the `hold-all` and `release-all` decisions | The Architect sends the task IDs, and the supervisor runs it (5j) |

- A request to the supervisor is a bus message (A8). The supervisor answers each one with a `reply` (0.4.0 spec,
  section 4e).
- Does: it dispatches the next ready task when a slot is free (`queue dispatch`, D14). It routes each message
  (D17). It finds a stalled agent. It keeps the pace (5c). It asks the Architect one precise question (SUP1).
- Does not: it writes no product code and does no review (R7). It decides no pace and no product question (R12,
  D22). It switches no account (R38). It does not talk to the user (SUP2).
- G10 (`@decided`): when a Codex run fails, the code records where and why it stopped. The record is the `failed`
  signal with its `reason`, the address and the attempt (A12). The log of the run is part of it. The supervisor then
  does one of four things:
  1. It resumes the run: `bus.mjs run` on the same address.
  2. It waits: a `sleep` event until the reset.
  3. It gives the task to a Claude Code agent: `queue retry`, then a dispatch with `--tool claude`.
  4. It queues the task again: `queue retry`.

  When the facts do not pick one, it asks the Architect with these options (SUP1).
- G16 (`@decided`): no reserved slots for the user's own side tasks. The usage percent includes them.
- G18 (`@decided`): it can stop an agent to keep the pace. A stop with no safe save first is extreme, and it asks
  the Architect first (SUP3).
- Model: any model can run it, because the state is in files (D15 `@proposed`). The tier is in section 9 (O5-4).

### 5b. `watch`, `tick` and the `Stop` hook (D15, D24)

`watch` — command: `node scripts/watch.mjs <projectDir> [--until <ISO time>] [--interval <seconds>]`.

- It is a background command of the supervisor session. It reads the queue state, the signal files, the bus and
  `.guilda/pace.json` every `--interval` seconds (default 30). It writes `aliveAt` in `writer.json` at each read,
  through the queue library (X2). It takes `--session <id>`, as `tick` does.
- It prints nothing while nothing changes. On the first new event it prints one line and exits. The end notice
  wakes the supervisor.
- An event is new only once (SC-G1), also across two runs of `watch`. `watch` keeps what it printed in
  `.guilda/queue/watch-seen.json`: the last journal `seq` that it reported, and the key of each one-time line. It
  writes the file by temp file and rename. It is not a queue file (X2). A ready task with no free slot is not an
  event.
- With `--until`, it wakes before that time only for a signal file or a bus line. A `sleep` event in the journal
  gives the time (SC-G1).

| Line | When | Exit |
|---|---|---|
| `ready <task>` | a task became `ready` and a slot is free | 0 |
| `stalled <task> <attempt>` | the ack timeout or the lease timeout passed (D14) | 0 |
| `failed <task> <attempt> <reason>` | a `failed` signal | 0 |
| `done <task> <attempt>` | a `done` signal | 0 |
| `bus <address> <message id>` | a new line in `bus/supervisor.jsonl` | 0 |
| `pace` | `.guilda/pace.json` changed and a slot opens (SC-G17) | 0 |
| `usage-limit` | a pace recommendation of 0 agents (5c) | 0 |
| `no-ready` | no task is `dispatched`, `running` or `ready`, and tasks are `pending` or `held` (SC-G14); printed one time | 0 |
| `outage` | 3 or more attempts of different tasks end with `error` or `limit` in 10 min (SC-G15) | 0 |
| `until` | the `--until` time passed | 0 |
| `io-error <path>` | a read or the `aliveAt` write failed (SC-G13) | 2 |
| `claim-lost` | another session holds the claim (X2) | 3 |
| usage text on stderr | a bad argument | 1 |

`tick` — command: `node scripts/tick.mjs <projectDir> --json --session <id>`, and
`node scripts/tick.mjs <projectDir> --event <file> --session <id>`.

- `--json` prints one JSON object. It writes only `aliveAt` in `writer.json`, and only with the `--session` of the
  live claim. Its keys:

  | Key | Value |
  |---|---|
  | `schemaVersion` | 1 |
  | `now` | ISO time |
  | `slots` | `pace`, `running`, `free` |
  | `ready` | task IDs in plan order |
  | `stalled`, `failed` | attempts |
  | `held` | a count only |
  | `pace` | the result of 5c |
  | `bus` | unread message IDs |
  | `sleepUntil` | ISO time or null |
- `--event <file>` appends one event to the journal through the functions of `scripts/lib/queue.mjs`. So `tick`
  counts as the queue script (X2), and it takes the lock for the command.
- Where `tick` learns its identity. It cannot see its session. The caller gives `--session`. The R32 hook checks
  that value against the `session_id` of the hook input. It refuses a call with an `agent_id`. Then `tick`
  compares `--session` with the `session` of the live claim. On a mismatch, with no `--session`, or with no live
  claim, it exits 1 with `refused: no claim` (R32).
- The fields of the 0.5.0 events. Each one also has `seq`, `t` and `type` (X5):

  | Event | Fields |
  |---|---|
  | `claim` | `session`, `ttlSec`, `takeover` (true or false) |
  | `sleep` | `until` (ISO time), `why` (`limit` or `idle`) |
  | `limit-stop` | `work`, `window` (`fiveHour` or `sevenDay`), `resetsAt` |
  | `question` | `id` (`q-<8 hex>`), `message` (the bus message ID), `tasks` |
  | `answer` | `question`, `message` |
  | `decision` with `stop`, `save-ok` or `architect-ok` | `tasks` (one task ID), `attempt`, `by`; `save-ok` also has `commit` |
  | `decision` with `hold-all` or `release-all` | `by` |
  | `decision` with `slots` | `slots` (an integer from 1 to `max`), `by` |

- A `stop` decision makes the attempt `stalled`, with the `cause` `stop` (X5). The supervisor writes it first.
  Then it ends the agent or the run (`bus.mjs stop --address` for an external run). Then it runs `queue retry`,
  or it leaves the task for the Architect.
- `queue claim` writes the `claim` event. `tick --event` writes the others. `queue slots <n>` writes the `slots`
  decision (5c).
- The events of 0.5.0 (X5). New types: `claim`, `sleep`, `limit-stop`, `question`, `answer`. New values of the
  `decision` event: `stop`, `save-ok`, `architect-ok`, `hold-all`, `release-all`, `slots`. `tick --event` takes only
  these, without `claim` and `slots`.
- For a dispatch, a hold, a release and a retry, the supervisor runs the 0.3.0 commands. They are
  `queue dispatch`, `queue hold`, `queue release` and `queue retry`. 0.5.0 adds no `dispatch-intent` and no `dispatch-ok` event. The
  `dispatch` event and the `agent` event of 0.3.0 are that pair (X5).
- It refuses a `stop` decision with no `save-ok` and no `architect-ok` decision for the same attempt (SUP3).
- Exit codes: 0 done, 1 refused or bad input (the reason on stdout as `refused: <reason>`), 2 I/O error.

`Stop` hook — the supervisor branch of `scripts/hooks/stop.mjs`. 0.4.0 creates the file with the delivery branch.
0.5.0 adds this branch. X6 has the order of the branches.

- The branch runs only on two conditions together. The hook input has no `agent_id`, and its `session_id` is the
  session of the live claim (X2). In each other session the delivery branch of 0.4.0 runs. One call runs one branch at most. So the two
  behaviors never block the same turn end.
- It runs the read-only part of `tick --json`: it writes no `aliveAt`, because a hook never writes a queue file
  (X2). It blocks the end of the turn (`decision: block`) on three conditions together.
  They are: `free` is more than 0, `ready` is not empty, and `now` is after `sleepUntil`.
- The reason text: `A task is ready: <task>. Dispatch it, or write a sleep event.`
- Loop guard: `stop_hook_active` can be true, with the same ready list and slots as at the last block. Then the hook
  does not block again. The last block is in `.guilda/queue/stop-guard.json`. The hook writes that file, and it is
  not a queue file (X2).
- On a read error it does not block (X9: a `Stop` branch fails open). The Stop hook is a pace aid, not a law.
- Not verified: the `Stop` hook in `codex exec`. L5-1 (d) checks it.

### 5c. The pace: computation and policy (D22)

`@proposed`, except the `@decided` items named. L5-7 gates this section. The method text for the Architect is in
`skills/architect/reference/pace.md` (D30). No `guilda:pace` skill (D22, D24).

Command: `node scripts/pace.mjs <projectDir> --json`. It prints the recommendation. It writes nothing.

With fewer than 2 samples the burn rate is unknown. Then `recommend` is the plan pace, the state is `on-pace`, and
`assumptions` has `no burn rate yet`.

Input:

| Input | Source | Note |
|---|---|---|
| usage of each account | the adapter of 5d | percent used and reset time of the 5-hour and 7-day windows |
| pace file | `.guilda/pace.json`, written only by the Architect with the user (ARC11, D22 `@decided`) | `schemaVersion`, `agents` (the plan pace), `max`, `policy`, `hours` (the work hours the user wants), `nearLimit` (default 85) |
| burn rate | the measure of 0.3.0 (A5): percent of a window used per agent hour, from the samples file | the low and high values of the last 6 samples give the range |
| samples file | `.guilda/pace-samples.jsonl`, git-ignored, written only by `watch` at each usage read. `watch` reads the usage at most one time in `usage.readIntervalSec` (default 300), not at each read of the queue | one line: `{ "t", "fiveHourUsed", "sevenDayUsed", "agentSeconds" }`. The two `Used` values are the sums over the accounts. `agentSeconds` is the total of the queue. The burn rate of a window between two samples is the growth of its `Used` value / the growth of `agentSeconds` in hours. A pair with no growth of `agentSeconds` is skipped. `watch` keeps the last 50 lines |
| work left | the queue: ready and pending tasks, with the `Weight:` class (SC-G3) when the brief has it | O5-5 |

Computation, for each window `w` (5-hour, 7-day):

1. `left(w)` = the sum over the accounts of (100 − used percent). The sum assumes that the `cswap` fork switches
   accounts (the fork plan). With no fork switch, `left(w)` is the value of the active account only (O5-6).
2. `hoursLeft(w)` = the hours to the first reset of `w`. A 5-hour reset gives back no 7-day usage (SC-P4).
3. `capacity(w)` = `left(w)` / burn rate, in agent hours. With the low and the high burn rate, a range. `recommend`
   uses the high burn rate, which gives the lower number. The low burn rate gives the high end of `range`.
4. `n(w)` = the floor of `capacity(w)` / `hoursLeft(w)`. When the floor is 0, `n(w)` is 1 while one account or
   more has a `usedPercent` below 100 in `w` (U5-11).
5. `target` = the work left in agent hours / `hours`, rounded up to an integer. It is the number of agents that ends the work in the hours
   that the user wants. D22 says that the pace comes from the usage left and those hours. With no
   `hours`, or with no `Weight:` data for the work left (O5-5), `target` is the plan pace `agents`.
6. The recommendation is the lowest of `target`, `n(5h)` and `n(7d)`, limited to 0 and `max`. The range comes from
   step 3.

Steps 4 to 6 are `@decided` (U5-11, 2026-11-10, the user):

- The pace keeps at least 1 agent while one account or more has usage left in each window. So the
  recommendation is 0, and the state is `at-limit`, only when each account is at 100 percent in one window.
  `near-limit` still asks the Architect before that.
- `hours` sets the target rate: the work left / `hours` (step 5).
- The reason: with a plain floor, a capacity of 0.9 agents gives a pace of 0 while usage is left. The work then
  stands still, against the goal of D22.

Output: `{ schemaVersion, source, fetchedAt, recommend, range: [low, high], plan, assumptions: [...], state }`.
`state` is `on-pace`, `under-pace`, `near-limit`, `at-limit`, `old-data` or `off`.

| State | When | Supervisor action |
|---|---|---|
| `off` | `usage.source` is `"off"`, or no `cswap`, or the adapter fails | uses the plan pace `agents`; no pace question; guilda works as before (D22 `@decided`) |
| `old-data` | `fetchedAt` is older than `usage.maxAgeMin` (default 15) | keeps the current pace; no pace question; tells the Architect "usage data old" one time (SC-G9) |
| `near-limit` | a window is over `nearLimit` percent on each account | dispatches nothing heavy; asks the Architect one question (SUP1, D22 `@decided`) |
| `at-limit` | `recommend` is 0: each account is at 100 percent in one window (U5-11) | dispatches nothing; writes `limit-stop` and `sleep` until the first reset; 5e |
| `under-pace` | `recommend` is more than the plan pace and ready tasks wait | asks the Architect one question (D22 `@decided`) |
| `on-pace` | other cases | nothing |

The states have an order. The first one that applies is the state: `off`, `old-data`, `at-limit`, `near-limit`,

`policy: "auto"`.

apply `recommend` between 1 and `max` with no question. Only the user turns it on (D22 `@proposed`). A lower pace
never stops a running agent; it applies at the next dispatch (SC-G17). A stop to keep the pace follows SUP3.

D22 `@decided`: the code never shows tokens as an exact share of a subscription. The output has percent values of the
fork only, with the assumptions and the range.

### 5d. The `cswap` adapter (D22)

`scripts/lib/usage.mjs`. One function, `readUsage(config)`, with no other entry point.

### 5e. The resume trigger (D38)

D38 `@decided`: the work can stop because the usage ran out. Then a scheduled trigger reads the reset times from the
fork. It waits for an account with usage left, and it resumes the stopped work. It resumes only the project that asked
for the work. The mechanism is `@open`, and L5-2 picks it.

The record — `.guilda/resume/<workId>.json`, written by `scripts/resume.mjs arm`:

```
{ "schemaVersion": 1, "workId": "<the work ID, w-<8 hex>>", "projectPath": "<real path of the main project root>",
  "createdAt": "<ISO>", "notBefore": "<ISO, the first reset>", "supervisorSession": "<session ID>", "state": "armed" }
```

- The work ID is the work ID of the queue (X4): the `work` of the `plan` event whose tasks stopped. The
  `limit-stop` event names it in its `work` field. The record is git-ignored, because it holds a machine path.
- `projectPath` is the real path of the main project root (X9), not of a worktree.
- `node scripts/resume.mjs arm --work <workId> --session <id>`. The supervisor runs it after it writes the
  `limit-stop` event. The command reads that event and takes `notBefore` from its `resetsAt`. It writes the record
  and sets one trigger with the L5-2 method. It prints `armed <workId> <notBefore>` and exits 0. With no `limit-stop`
  event for that work it exits 5 with `refused: not a limit stop`. A bad work ID exits 1 with `invalid ID` (X4). An
  I/O error exits 2.

The run — `node <plugin>/scripts/resume.mjs run --project <path> --work <workId>`. The steps run in this order, and
the first one that fails ends the run:

1. Resolve the main project root of the working folder (X9). Compare its real path with `--project`. On a
   mismatch, or when the root cannot be found, exit 5 with `refused: project mismatch`, and do nothing (R41).
2. Read `.guilda/resume/<workId>.json` in that root. With no record, a record that cannot be read, or a `state`
   that is not `armed`, exit 5 with `refused: no armed record`.
3. Compare the `projectPath` and the `workId` of the record with the real path and `--work`. On a mismatch, exit 5
   with `refused: project mismatch`. This is the case of a record that was copied to another folder.
4. Replay the journal. The work must be open, and its last stop must be a `limit-stop` event with the same `work`.
   Else exit 5 with `refused: not a limit stop`.
5. Read the usage (5d). With no account with usage left, set the trigger again for the next reset, and exit 0.
6. Resume the supervisor session of the record: the session that the user started (R36). The method is from L5-2.
   Set `state: "resumed"`, and remove the trigger with the method's own remove command. The script never starts a
   new supervisor session. When that session cannot be resumed, it sends one `notice` to `architect`
   ("the work can go on; start the supervisor"), sets `state: "waiting-user"`, removes the trigger and exits 0.

- Each refusal starts no process and changes no file. The script fails closed (X9): a read error is a refusal.
- G5 stays (`@decided`): a restart of the session or the machine is not a limit stop. The trigger does not run for it.
- No delete with `rm -f` or `rm -rf`. A record that is done stays, with `state: "resumed"`.
- Conflict to answer (U5-6): D18 says "no daemon, no global install, no change to user settings". A cron entry or a
  systemd user timer is a user-level change. A Claude Code scheduled task may be one too.
