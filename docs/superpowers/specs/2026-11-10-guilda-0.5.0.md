## 1. Intent

0.4.0 moves the Architect out of the main session, and it gives agents addresses and a bus. Three problems stay:

- Nobody runs the flow when the Architect waits for the user. A ready task waits, and a stalled agent stays stalled.
- The number of agents does not follow the usage that is left on the accounts. The work passes a limit or stands still.
- The work stops when the usage runs out, and it starts again only when the user comes back.

0.5.0 adds the supervisor and the pace for these problems. It also adds the Security Lead and the Security Executor
with the red team limits as laws (D16, D28, D37). It adds the council (D47) and away mode (D48), with the user's
approval of their release.

The goal (D22, `@decided`): a constant flow that does not pass a limit and does not stand still. The supervisor
runs the work that the Architect designed. It does not own the project (D15).

0.5.0 is a minor release. It adds rules, roles and skills, and no core rule changes meaning (`RELEASING.md`).

### R?a — The one writer of the queue (D14, D15 G5)

```
### R901 — The supervisor is the one writer of the queue
Rule:  Let only the session with the queue lock write the queue, and start the supervisor only on the user's request.
Why:   Two writers break the replay of the journal, and a hook that starts the supervisor acts without the user (D14, D15 G5).
Check: law — PreToolUse refuses a write to `.guilda/queue/` from each session and agent that does not hold the lock, and no hook starts the supervisor.
```

Linter: pass (exit 0). D14 `@decided`: until the supervisor exists, the Architect writes the queue. So with no live
lock, the Architect takes the lock (section 5a).

### R?b — Red team limits (D16, D28)

```
### R902 — Red team limits are laws
Rule:  Run red team work only on this project's code, in a local test environment, after the user approves the task.
Why:   The text of a skill is not a safety control, and an attack on a host that the project does not own harms other people (D16, D28).
Check: law — The `tools` list of the Security Executor and a PreToolUse hook on its `agent_type` refuse an outside host, a credential read, a persistence step and a run with no recorded approval.
```

## 5. Contracts

### 5a. The supervisor session (D15)

`@proposed` unless a line says otherwise. L5-1 gates this section.

- Who: a Claude Code session in the project folder, with the agent definition `agents/supervisor.md`. Its group is
  `engineering` (0.2.0 spec, section 3e, `@decided`).
- Start: only the user starts it (G5, `@decided`). The method comes from L5-1 (e). No hook starts it, and no hook
  asks. After a restart of the session or the machine, the user starts it again.
- Talk: it never talks to the user (SUP2). It reads `bus/supervisor.jsonl` and writes `bus/main.jsonl` and the
  Architect's address (A8, A9).
- Lock: at start it calls `takeLock()` (A4). The lock gets the field `alive_at`, and `watch` writes it at each tick
  (SC-G5). A second supervisor reads the lock. It takes the lock only when the owner process is dead or `alive_at`
  is older than 3 ticks. It records a `takeover` event. In the other cases it stops and tells the Architect.
- With no live lock (no supervisor), the Architect takes the lock and writes the queue, as in 0.3.0 (D14).
- Loop: `/loop` runs `node scripts/tick.mjs <projectDir> --json` at each tick. Between ticks the session sleeps in
  `watch`, a background command. A healthy flow costs no tokens (D15, the user's idea).
- Reconcile at start (SC-G5): first the D14 recovery. Then an attempt of a Claude subagent from an ended session
  becomes `stalled`, with `reason: session-ended`. A dead process is a fact, so the supervisor writes a `retry` event (R9).
- Does: it dispatches the next ready task when a slot is free (D14). It routes each message (D17). It finds a
  stalled agent. It keeps the pace (5c). It asks the Architect one precise question (SUP1).
- Does not: it writes no product code and does no review (R7). It decides no pace and no product question (R12,
  D22). It switches no account (R?c). It does not talk to the user (SUP2).
- G16 (`@decided`): no reserved slots for the user's own side tasks. The usage percent includes them.
- G18 (`@decided`): it can stop an agent to keep the pace. A stop with no safe save first is extreme, and it asks
  the Architect first (SUP3).
- Model: any model can run it, because the state is in files (D15 `@proposed`). The tier is in section 9 (O5-4).

### 5b. `watch`, `tick` and the `Stop` hook (D15, D24)

`watch` — command: `node scripts/watch.mjs <projectDir> [--until <ISO time>] [--interval <seconds>]`.

- It is a background command of the supervisor session. It reads the queue state, the signal files, the bus and
  `.guilda/pace.json` every `--interval` seconds (default 30). It writes `alive_at` in the lock at each read.
- It prints nothing while nothing changes. On the first new event it prints one line and exits. The end notice
  wakes the supervisor.
- An event is new only once (SC-G1). A ready task with no free slot is not an event.
- With `--until`, it wakes before that time only for a signal file or a bus line. A `sleep` event in the journal
  gives the time (SC-G1).

| Line | When | Exit |
|---|---|---|
| `ready <task>` | a task became `ready` and a slot is free | 0 |
| `stalled <task> <attempt>` | the ack timeout or the lease timeout passed (D14) | 0 |
| `failed <task> <attempt> <reason>` | a `failed` signal | 0 |
| `done <task> <attempt>` | a `done` signal | 0 |
| `bus <address> <message id>` | a new line in `bus/supervisor.jsonl` | 0 |
| `pace` | `.guilda/pace.json` changed and a slot opens (SC-G17) | 0 |
| `usage-limit` | a pace recommendation of 0 agents (5c) | 0 |
| `blocked` | no task is `dispatched`, `running` or `ready`, and tasks are `pending` or `held` (SC-G14); printed one time | 0 |
| `outage` | 3 or more attempts of different tasks end with `error` or `limit` in 10 min (SC-G15) | 0 |
| `until` | the `--until` time passed | 0 |
| `io-error <path>` | a read or the `alive_at` write failed (SC-G13) | 2 |
| `lock-lost` | another session holds the lock | 3 |
| usage text on stderr | a bad argument | 1 |

`tick` — command: `node scripts/tick.mjs <projectDir> --json`, and `node scripts/tick.mjs <projectDir> --event <file>`.

- `--json` prints one JSON object and writes nothing. Its keys:

  | Key | Value |
  |---|---|
  | `schemaVersion` | 1 |
  | `now` | ISO time |
  | `slots` | `pace`, `running`, `free` |
  | `ready` | task IDs in plan order |
  | `stalled`, `failed` | attempts |
  | `held` | a count only |
  | `pace` | the result of 5c |
  | `bus` | unread message IDs |
  | `sleepUntil` | ISO time or null |
- `--event <file>` appends one event to the journal through the queue library (A4). It refuses with exit 1 when
  the session does not hold the lock (R?a). Events of 0.5.0: `dispatch-intent`, `dispatch-ok`, `retry`, `stop`,
  `save-ok`, `architect-ok`, `sleep`, `hold`, `release`, `pause`, `resume-all`, `question`, `answer`, `limit-stop`.
- It refuses a `stop` event with no `save-ok` and no `architect-ok` for the same attempt (SUP3).
- Exit codes: 0 done, 1 refused or bad input (the reason on stdout as `refused: <reason>`), 2 I/O error.

`Stop` hook — `scripts/hooks/stop.mjs`, on the `Stop` event, with no matcher.

- It acts only in the session that holds the queue lock, and only when the hook input has no `agent_type`. In each
  other session it exits 0 and prints nothing.
- It runs the code of `tick --json`. It blocks the end of the turn (`decision: block`) on three conditions together.
  They are: `free` is more than 0, `ready` is not empty, and `now` is after `sleepUntil`.
- The reason text: `A task is ready: <task>. Dispatch it, or write a sleep event.`
- Loop guard: `stop_hook_active` can be true, with the same ready list and slots as at the last block. Then the hook
  does not block again. The last block is in `.guilda/queue/stop-guard.json`.
- On a read error it does not block (fail open). The Stop hook is a pace aid, not a law.
- Not verified: the `Stop` hook in `codex exec`. L5-1 (d) checks it.

### 5c. The pace: computation and policy (D22)

`@proposed`, except the `@decided` items named. L5-7 gates this section. The method text for the Architect is in
`skills/architect/reference/pace.md` (D30). No `guilda:pace` skill (D22, D24).

Command: `node scripts/pace.mjs <projectDir> --json`. It prints the recommendation. It writes nothing.

Input:

| Input | Source | Note |
|---|---|---|
| usage of each account | the adapter of 5d | percent used and reset time of the 5-hour and 7-day windows |
| pace file | `.guilda/pace.json`, written only by the Architect with the user (ARC901, D22 `@decided`) | `schemaVersion`, `agents` (the plan pace), `max`, `policy`, `hours` (the work hours the user wants), `nearLimit` (default 85) |
| burn rate | the measure of 0.3.0 (A5): percent of a window used per agent hour, from the last samples | the low and high values of the last 6 samples give the range |
| work left | the queue: ready and pending tasks, with the `Weight:` class (SC-G3) when the brief has it | O5-5 |

Computation, for each window `w` (5-hour, 7-day):

1. `left(w)` = the sum over the accounts of (100 − used percent). The sum assumes that the `cswap` fork switches
   accounts (the fork plan). With no fork switch, `left(w)` is the value of the active account only (O5-6).
2. `hoursLeft(w)` = the hours to the first reset of `w`. A 5-hour reset gives back no 7-day usage (SC-P4).
3. `capacity(w)` = `left(w)` / burn rate, in agent hours. With the low and the high burn rate, a range.
4. `n(w)` = the floor of `capacity(w)` / `hoursLeft(w)`.
5. The recommendation is the lower of `n(5h)` and `n(7d)`, limited to 0 and `max`. The range comes from step 3.

Output: `{ schemaVersion, source, fetchedAt, recommend, range: [low, high], plan, assumptions: [...], state }`.
`state` is `on-pace`, `under-pace`, `near-limit`, `at-limit`, `old-data` or `off`.

| State | When | Supervisor action |
|---|---|---|
| `off` | `usage.source` is `"off"`, or no `cswap`, or the adapter fails | uses the plan pace `agents`; no pace question; guilda works as before (D22 `@decided`) |
| `old-data` | `fetchedAt` is older than `usage.maxAgeMin` (default 15) | keeps the current pace; no pace question; tells the Architect "usage data old" one time (SC-G9) |
| `near-limit` | a window is over `nearLimit` percent on each account | dispatches nothing heavy; asks the Architect one question (SUP1, D22 `@decided`) |
| `at-limit` | `recommend` is 0 | dispatches nothing; writes `limit-stop` and `sleep` until the first reset; 5e |
| `under-pace` | `recommend` is more than the plan pace and ready tasks wait | asks the Architect one question (D22 `@decided`) |
| `on-pace` | other cases | nothing |

Policy: `policy: "recommend"` is the default. The supervisor then only asks. `policy: "auto"` lets the supervisor
apply `recommend` between 1 and `max` with no question. Only the user turns it on (D22 `@proposed`). A lower pace
never stops a running agent; it applies at the next dispatch (SC-G17). A stop to keep the pace follows SUP3.

D22 `@decided`: the code never shows tokens as an exact share of a subscription. The output has percent values of the
fork only, with the assumptions and the range.

The `cswap` fork plan (D22 `@proposed`): smart switching in the fork keeps the usage of all accounts even. guilda
never switches. The fork plan is the user's work in the fork, outside this repository.

### 5d. The `cswap` adapter (D22)

`scripts/lib/usage.mjs`. One function, `readUsage(config)`, with no other entry point.

- With `usage.source` equal to `"off"`, or no `usage` key, it returns `{ state: "off" }` and runs nothing. The
  default of a new config is `"off"` (`@proposed`). So a project sees no change until the user turns the pace on.
- With `usage.source: "cswap"`, it runs one fixed command with no shell: `cswap <command> --json`. `<command>` is
  O5-1 (the register example is `pace`). The timeout is 10 s.
- It never runs another `cswap` subcommand. R?c refuses `cswap switch` and `cswap list` from each agent.

The requirements to the fork (the user's fork; guilda only reads):

| Field | Type | Rule |
|---|---|---|
| `schemaVersion` | integer | 1 for the first form; a new major form gets a new number |
| `fetchedAt` | ISO 8601 time with a zone | the time of the read from the provider |
| `accounts` | list | one item for each account |
| `accounts[].id` | string | a number or an alias that the user chose; never an email, an organization name or a token |
| `accounts[].provider` | string | `claude`, or `codex` when the fork can read it (G10) |
| `accounts[].fiveHour` | object | `usedPercent` (0 to 100), `resetsAt` (ISO time) |
| `accounts[].sevenDay` | object | `usedPercent` (0 to 100), `resetsAt` (ISO time) |

| Exit code | Meaning | Adapter result |
|---|---|---|
| 0 | the JSON is on stdout | parsed |
| 2 | no account is set up | `state: "off"`, notice "no accounts" |
| 3 | the provider cannot be read (network, login) | `state: "off"`, notice "usage source unavailable" |
| 4 | a usage error | `state: "off"`, notice "usage command error" |
| other | unknown | `state: "off"`, notice with the code |

- Tolerant reader (D40): the adapter ignores unknown fields, and it reads `schemaVersion` 1. A missing required field
  makes that account unknown, not the whole read.
- Data guard (D22 `@decided`): the adapter keeps only the fields of the table. It never writes the raw output to a
  file, a log, a report or the context. An `id` with an `@` in it is replaced with `account-<n>`, with a notice.
- Codex (G10, `@decided`): an account with `provider: "codex"` counts for the Codex pace. With none, the Codex pace is
  unknown. A Codex run that ends with `reason: limit` holds the Codex tasks, and the supervisor asks the Architect.

### 5e. The resume trigger (D38)

D38 `@decided`: the work can stop because the usage ran out. Then a scheduled trigger reads the reset times from the
fork. It waits for an account with usage left, and it resumes the stopped work. It resumes only the project that asked
for the work. The mechanism is `@open`, and L5-2 picks it.

The record — `.guilda/resume/<workId>.json`, written by `scripts/resume.mjs arm`:

```
{ "schemaVersion": 1, "workId": "<the run ID of the journal>", "projectPath": "<real path of the project>",
  "createdAt": "<ISO>", "notBefore": "<ISO, the first reset>", "supervisorSession": "<session ID>", "state": "armed" }
```

- The work ID is the ID of the open run in the queue journal (A1). The record is git-ignored, because it holds a
  machine path.
- `arm` runs only on a `limit-stop` event. It sets one trigger with the L5-2 method, for `notBefore`.

The run — `node <plugin>/scripts/resume.mjs run --project <path> --work <workId>`:

1. Resolve the real path of the working folder. Compare it with `--project` and with `projectPath`. On a mismatch,
   exit 5 with `refused: project mismatch`, and do nothing (R?f).
2. Read the record of `--work`. With no record, or a `state` that is not `armed`, exit 5 with `refused: no armed record`.
3. Replay the journal. The open run must have the same `workId` and a `limit-stop` as its last stop. Else exit 5.
4. Read the usage (5d). With no account with usage left, set the trigger again for the next reset, and exit 0.
5. Resume the supervisor session of the record. The method is from L5-2. Set `state: "resumed"`, and remove the
   trigger with the method's own remove command.

- G5 stays (`@decided`): a restart of the session or the machine is not a limit stop. The trigger does not run for it.
- No delete with `rm -f` or `rm -rf`. A record that is done stays, with `state: "resumed"`.
- Conflict to answer (U5-6): D18 says "no daemon, no global install, no change to user settings". A cron entry or a
  systemd user timer is a user-level change. A Claude Code scheduled task may be one too.

## 7. Risks

- D22: the terms of use of each provider for more than one account are not verified. The pace does not ship
  before U5-1.
- D22: `left(w)` sums the accounts only when the fork switches. Without the fork plan the sum is too high (O5-6).
- D22: the burn rate comes from few samples at the start of a run. The range is wide, and the policy stays
  `recommend`.
- D15: `/loop` ends with the session and expires after 7 days (register research). A supervisor that stops is seen
  only through `alive_at` (status script, A7).
- D15: the token cost of an idle tick is not known. L5-1 (c) measures it.
- D38 and D18: the trigger needs a change outside the project (U5-6). A trigger left behind can start work later. R?f
  and the `armed` state limit this.
- D16: the hook reads command text. It catches common forms, not each form. SX1, the sandbox and the user's approval
  are the other layers.
- D48: hiding the absence can fail. An agent with no answer for hours can guess it (D48 `@open`). L5-4 tests it.
- D47: a council costs one agent context per lead. ARC902 and the user's yes limit it.
- Assumptions A1 to A14: a change in the 0.3.0 or 0.4.0 spec changes this spec in the same step.

## 8. Acceptance scenarios

Each scenario has the ARC7 shape. A part that a lab gates runs its scenarios only after a GO.

### S5-1 — `watch` prints nothing on a healthy flow (D15)

- Given: a fixture queue with 2 `running` tasks, fresh heartbeats, pace 2, no bus line.
- When: `node scripts/watch.mjs <dir> --interval 1` runs for 5 s.
- Then: no line on stdout. The lock `alive_at` changed at least 4 times. The process still runs.
- Tool: `node --test`. Test: `tests/watch.test.mjs`.

### S5-2 — `watch` prints one line for a ready task and exits (D15, SC-G1)

- Given: the fixture of S5-1 with pace 3, and a third task whose dependencies are `done`.
- When: `watch` runs.
- Then: stdout is exactly `ready T3`, and the exit code is 0. A second run with pace 2 prints nothing for T3.
- Tool: `node --test`. Test: `tests/watch.test.mjs`.

### S5-3 — `watch` sleeps until a time (SC-G1)

- Given: a `sleep` event with `until` 3 s later, and a ready task with a free slot.
- When: `watch --until <that time> --interval 1` runs.
- Then: the first line is `until` after about 3 s, not `ready`. A new bus line before that time gives `bus supervisor <id>`.
- Tool: `node --test`. Test: `tests/watch.test.mjs`.

### S5-4 — `watch` reports a blocked queue one time (SC-G14)

- Given: no task `dispatched`, `running` or `ready`; one task `held`, one `pending` that depends on it.
- When: `watch` runs two times.
- Then: the first run prints `blocked` and exits 0. The second run prints nothing in 3 s.
- Tool: `node --test`. Test: `tests/watch.test.mjs`.
