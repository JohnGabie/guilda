# guilda 0.4.0 — the Architect outside the main session

Status: spec in requirements. Not approved (R3). The scope is the release plan of the register (`@decided`,
2026-11-09). Each new choice of this spec is `@proposed` and waits for the checklist of section 5.
Decisions: [decision register](2026-11-09-guilda-decisions.md). Earlier releases: [0.2.0](2026-11-09-guilda-0.2.0.md),
0.3.0 (`2026-11-10-guilda-0.3.0.md`, written in parallel). Later releases: [backlog](2026-11-09-guilda-backlog.md).
Base: the 0.3.0 scope of the register. Section 2a lists each assumption on the 0.3.0 contracts. In this spec,
"today" is 0.3.0 as the register scopes it.

## 1. Intent

Three problems stay after 0.3.0:

- The Architect runs in the main session. The main session fills with spec and plan work, and it compacts.
- Agents of other tools, such as Codex, cannot talk to the Architect. They need an address and a channel.
- A reference in the chat (`D14`, `core/rules.md:96`, a commit) is plain text. The user searches for it by hand.

0.4.0 fixes these problems:

- The Architect runs as its own agent (D31). The main session talks to the user and relays.
- Each dispatch gets an address (D17). Messages go through file mailboxes, with a Claude Code and a Codex adapter.
- No agent stays alive between messages (D18). An idle agent is a file.
- A mention such as `@architect` sends a prompt straight to that agent (D49).
- A reference in the chat becomes a link that opens the right line (D33).

0.4.0 is a minor release. ARC1 and two glossary lines change meaning (0.x rule of `RELEASING.md`). The rules change
in place (D40), so no project runs `guilda:init` again.

Lab evidence so far:

- `lab/architect-agent`: the main session was 69.9% smaller. Total tokens +0.4%; list price +11.9%. One run.
- `lab/external-agent`: a Codex agent joined, asked the Architect and got the reply on its next turn. 9 of 9 scenarios, one run.
- `lab/agent-bus`: one mailbox exchange between Claude Code and Codex. No process stayed alive. One run.
- `lab/links`: MORE DATA. Raw OSC 8 text inside Claude Code; a `file://` click in kitty opened the folder.

## 4. Contracts

All runtime files are in `.guilda/`. `.guilda/.gitignore` lists each of them (builder check of 2026-11-09). The
`IGNORED` list of `scripts/lib/violations.mjs` gets `bus/`, `runs/` and `codex/`.

### 4a. Address format (D17)

`@proposed` (C4-2).

| Kind | Form | Example | Who makes it |
|---|---|---|---|
| task dispatch | `<task>-<role>-<4 hex>` | `T3-exe-7f2a` | `bus.mjs address --task T3 --role exe`, called by the Architect before the dispatch |
| the Architect | `arc-<4 hex>` | `arc-7dd5` | the first dispatch of the Architect agent in a project |
| a joined agent of another tool | `ext-<tool>-<name>-<4 hex>` | `ext-codex-voice-4592` | `bus.mjs join --tool codex --name voice` |
| the main session | `main` | `main` | reserved; never made |

- Role codes: `arc`, `exe`, `rev`, `qa`, `sec`, `vc`, `lab`, `dev`, `ai`. A new role gets its code in its spec.
- `<task>` and `<name>`: `[A-Za-z0-9]{1,24}`. A task ID with other characters loses them in the address.
- The full address matches `^(main|[A-Za-z0-9]{1,24}(-[a-z0-9]{1,24}){1,3}-[0-9a-f]{4})$`, 64 characters or fewer.
- The random part comes from `crypto.randomBytes`. On a match with a known address, `address` draws again, at most
  10 times, then exits 1.
- Code never parses an address for its task or role. It reads them from the binding table.
- An address lives for the life of its task (D17). A new agent can take it over (`rebind`, 4b). A new task gets a new
  address (2b).

### 4b. Binding table (D17)

`@proposed` (C4-3). The queue journal is the one owner of agent identity (D14, `@decided`). So the binding table is
derived from the journal. Only the journal writer writes `.guilda/bus/bindings.json`, by temp file and rename.

New journal events. A reader that does not know them ignores them (D40):

| Event | Fields | Written by | When |
|---|---|---|---|
| `bind` | `address`, `tool`, `agentId` or `session`, `parent`, `role`, `task`, `time` | the journal writer | after a dispatch, from the bind signal |
| `rebind` | `address`, `tool`, `agentId` or `session`, `reason`, `time` | the journal writer | a new agent takes the address, with the ledger and the earlier transcript (D17) |
| `join` | `address`, `tool`, `name`, `time` | the journal writer | from a join signal |
| `session` | `address`, `session`, `source`, `time` | the journal writer | from a session signal of a Codex hook |
| `unbind` | `address`, `reason`, `time` | the journal writer | the task is `done` or `dead` |

Signals, each written by its worker, in `.guilda/bus/signals/` (A4):

| Signal | File | Written by |
|---|---|---|
| bind | `bind-<address>.json`: `{ address, agentId, agentType, parentSession, time }` | `PostToolUse` on `Agent`. It reads the line `Address: <address>` of the prompt and the agent ID of the response |
| join | `join-<address>.json`: `{ address, tool, name, time }` | `bus.mjs join` |
| session | `session-<address>-<session>.json`: `{ address, session, source, time }` | the Codex `SessionStart` hook. The session comes from the hook input, not from the agent (lab lesson) |

- `readBindings(projectDir)` replays the journal and then reads the pending signals in memory. It writes nothing. So
  `join` prints the address at once (X1), before the writer folds the signal.
- `bindings.json` is a cache. A reader that finds it older than the journal replays the journal.
- Form of one entry:

  ```json
  { "address": "T3-exe-7f2a", "tool": "claude", "agentId": "...", "sessions": ["..."], "parent": "<session or address>", "role": "exe", "task": "T3", "state": "bound" }
  ```

  `tool` is `claude`, `claude-headless` or `codex`. `state` is `bound` or `unbound`.
- One address can have many sessions (lab `external-agent`, scenario e). The last session is the one to resume.

### 4c. Mailbox JSONL (D17)

`@proposed` (C4-4). One append-only file for each address: `.guilda/bus/<address>.jsonl`. A sender appends one
line under the mailbox lock. The bus is for messages that cross tools, or that wait for an agent that sleeps.
Traffic between the main session and the Architect uses `SendMessage` and user records (4f).

Message line:

```json
{"v":1,"id":"m-3f2a9c1b","from":"ext-codex-voice-4592","to":"arc-7dd5","task":"T3","type":"request","text":"Which storage does the app use?","reply_to":null,"time":"2026-11-10T14:02:11.000Z","origin":"hook"}
```

| Field | Value | Missing (tolerant read, D40) |
|---|---|---|
| `v` | 1 | 1 |
| `id` | `m-` and 8 hex | the line is skipped |
| `from`, `to` | addresses (4a) | the line is skipped |
| `task` | a task ID or `null` | `null` |
| `type` | `request`, `question`, `answer`, `decision`, `reply`, `report`, `notice`, `ack`, `error` | `notice` |
| `text` | UTF-8, 8000 characters or fewer | the line is skipped |
| `reply_to` | a message ID or `null` | `null` |
| `record` | a user record ID (4g) or absent | absent |
| `time` | ISO 8601 | the file order |
| `origin` | `hook` (a hook set `from` from the host identity) or `claimed` (the caller gave `from`) | `claimed` |

Receipt line, in the mailbox of the receiver:

```json
{"v":1,"type":"receipt","ref":"m-3f2a9c1b","state":"delivered","by":"main","time":"2026-11-10T14:02:30.000Z"}
```

- States: `delivered`, `injected`, `read`, `failed`. The last receipt of a message is its state.
- A message is pending when its type needs delivery and it has no `delivered` or `read` receipt.
- `ack`, `receipt` and `error` are never delivered (lab `agent-bus` lesson). They are stored.
- A longer text is refused (exit 2, "text over 8000 characters; send a file path in the text").
- A reader skips a last partial line, and a line that is not JSON (D14 recovery rule).
- The lock: `.guilda/bus/<address>.lock`, made with `open(..., 'wx')`, with `{ pid, time }`. A lock older than 10 s
  whose PID is not alive is stale. The sender removes a stale lock and records a `notice` line. A sender waits 2 s
  for the lock at most, then exits 3 (`busy`).

### 4d. The router (D17, D18)

`@proposed` (C4-5). The router is the `deliver` command of `bus.mjs`. It takes the delivery lock of the address
(`.guilda/bus/<address>.deliver.lock`). It delivers each pending message in file order, one at a time. A second
`deliver` for the same address exits 3 (`busy`) (lab `external-agent`, scenario h).

| `tool` of the binding | How a message reaches the agent |
|---|---|
| `claude`, a subagent of the current session | A script cannot call `SendMessage`. The hooks of the main session tell the main session to relay (4f). The `PostToolUse` hook on `SendMessage` writes the `delivered` receipt for each `guilda-message:` header in the text |

| `codex`, a joined interactive session | No push. The Codex hooks give the message to the next turn (4k) |
| `codex`, a run that `bus.mjs run` started | `deliver` runs `codex exec resume` (argv below). It stores the answer as a `reply` to the sender |

Message turns have no tools (D18). Exact argv:

| Tool | argv | stdin | cwd |
|---|---|---|---|
| `claude-headless` | `["claude", "-p", "--resume", <session>, "--output-format", "json", "--tools", "", "--strict-mcp-config"]` | the message text with its header | the project folder |
| `codex` | `["codex", "exec", "resume", "--json", "--skip-git-repo-check", <thread>, <text with header>]` | `/dev/null` | the project folder |

- The header line of each delivered text: `guilda-message: <id> from <address> type <type>`.
- Not verified: a sandbox flag on `codex exec resume` (lab `agent-bus`, L1). L4-4 checks it.
- A message turn has a timeout of `adapters.<tool>.messageTimeoutSec`, default 180.
- On a timeout or a failed child, the router writes a `failed` receipt. The message is pending again one time. On a
  second failure the router stores an `error` reply to the sender (R9).
- A delivery that is in progress when a new message arrives does not see it. The next trigger delivers it (lab
  `external-agent`, risk 4).

### 4e. Reply contract (D17)

`@proposed` (C4-6).

1. Each `request` or `question` gets exactly one message with `reply_to` equal to its ID, to its sender.
2. A Claude agent that a message resumed ends its answer with the line `REPLY-TO: <id>`, then the reply text.
3. `SubagentStop` finds the last delivered message to the address of the agent with no reply yet.
4. If the answer has no `REPLY-TO:` line for that ID, the hook exits 2 one time. Its text: "End your answer with `REPLY-TO: <id>` and your reply."
5. If the second answer has no such line, the hook stores an `error` reply. Its text: "no reply in the reply format".
6. On a valid answer, the hook appends the reply to the mailbox of the sender. `from` is the address of the agent ID; `origin` is `hook`.
7. The send-back counter is its own key in `.guilda/format-retries.json` (`reply:<agent_id>:<message id>`), limit 1.
8. For a headless or Codex message turn, the router stores the whole answer as the reply. No format check.

Not verified: that `SubagentStop` runs after each resume by `SendMessage`. L4-1 checks it (O4-2).

### 4f. The Architect as an agent, and the relay (D31)

`@proposed` (C4-14): the Architect is a subagent of the main session, not a headless session. The reasons: the lab

`QUESTION:` is optional, and there is at most one (ARC1). `SubagentStop` with the matcher `^guilda:architect$`

6. Show the `SUMMARY:` of the reply word for word. Add no fact about the project of your own (R?1).
7. Ask the `QUESTION:` with the question tool (R13). Send the answer back with its `Record:` line.
8. Do not read specs, plans or code for the Architect. The Architect reads them.

- The skill `guilda:architect` starts with one line for the main session. The line: "If you have no agent ID,

- The Architect agent is the controller. It dispatches the roles at depth 2 (lab Q2). A role at depth 3 has no
  `Agent` tool (Claude Code docs, quoted in the lab).

### 4g. Sender check and user records (D31)

`@proposed` (C4-9, C4-17). Two parts.

Part 1, the sender of an agent. `from` comes from the host identity where a hook sees it:

| Sender | How `from` is set | `origin` |
|---|---|---|
| a subagent that runs `bus.mjs send` | `PreToolUse` on `Bash` reads `agent_id` (B1). It refuses the command when `--from` is not the address bound to that agent ID (R?2) | `hook` after the check |
| a subagent reply | `SubagentStop` sets `from` (4e) | `hook` |
| the main session | `--from main` only when the hook input has no `agent_id` | `hook` |
| a Codex agent | `--from` as the caller gives it. No Claude hook sees the Codex shell | `claimed` |

Part 2, user records. A hook writes one record for each prompt of the user and each answer to the question tool:

```json
{"v":1,"id":"u-9c1b3f2a","channel":"main","session":"<session id>","kind":"prompt","text":"Use SQLite.","question":null,"time":"2026-11-10T14:05:00.000Z","mac":"<64 hex>"}
```

- File: `.guilda/bus/user.jsonl`. Only hooks write it.
- `kind: prompt`: the main `UserPromptSubmit` hook, in a session with no `agent_id`, not in print mode.
  Candidate test for print mode: `CLAUDE_CODE_ENTRYPOINT` (guess (memory), L4-2 checks it).
- `kind: answer`: `PostToolUse` on `AskUserQuestion`, with the question text and the answer of the tool response.
- A Codex record: the Codex `UserPromptSubmit` hook, with `channel` set to the joined address of the session.
- `mac` = HMAC-SHA256 of the record without `mac`, keys in sorted order, with the project key.
- The key: 32 random bytes in `$XDG_STATE_HOME/guilda/keys/<16 hex>.key` (default `~/.local/state`). The 16 hex are
  the start of SHA-256 of the real project path. Mode 0600. The first hook that writes a record makes it.
- `PreToolUse` refuses a `Read` of the key folder and a shell command that names it (R?2 forms, same limit).
- The hook adds one line to the model context: `guilda user record: u-9c1b3f2a`.

`bus.mjs verify <record id>` exits 0 only when all are true:

1. The record exists in `.guilda/bus/user.jsonl`, and its `mac` is valid.
2. Its `channel` is `main`, or it is in `bus.userChannels` of `.guilda/config.json`.
3. For a Codex channel, the record session is a session of that address in the binding table.

Exit 1 prints the reason: `unknown record`, `bad mac`, `not a user channel`, `session not bound`.

- A decision counts as the user's only with a verified record (R?3). Any other answer is advice, and the decision
  waits. Lab `external-agent`, scenario i, showed the Architect act this way with the config alone.
- The limit: agents run as the same OS user. An agent that reads the key in a form that the hook does not see can
  forge a record. The code makes a forgery hard, not impossible. Risk 3 of section 6.
- The register form of a decided item gets the record: `(2026-11-12, the user, record u-9c1b3f2a)`.

### 4i. Runs, timeouts and clean-up (D18)

`@proposed` (C4-8, C4-25).

- An idle agent is a file: its address and its sessions in the binding table. No process (lab Q6, 45 of 45 calls).
- Adapters are off unless `adapters.<tool>.enabled` is `true`. No daemon, no global install, no change to user settings.
- `run` starts each run of another tool as a background command of the Claude Code session. So the user sees it.
- `run` makes a new process group, and writes `.guilda/runs/r-<8 hex>.json`.
  The record: `{ run, address, tool, pid, pgid, startTime, deadline, session, state }`.
- `startTime` is the process start time from the OS (`/proc/<pid>/stat` on Linux, `ps -o lstart=` on macOS).
- A run past its deadline gets SIGTERM for its process group. After 5 s it gets SIGKILL. The state becomes `timeout`.
- `clean --session-start` and `clean --session-end` stop each recorded run whose deadline passed or whose session ended.
- The clean-up stops a PID only when its start time equals the record. A reused PID is not touched.
- `stop --all` stops each live recorded run of the project.
- No tool edits the process of another tool. A Codex agent reads the mailbox files only.
- A routed agent starts no background commands (lab `agent-bus`, L5). The brief of a run says so.
- Codex runs with stdin from `/dev/null`. The adapter passes `--ignore-user-config`.
- Not verified: options that stop the load of user skills in the Codex home. L4-4 checks them.
  The lab measured about 20,000 tokens for these skills in each new session.
- Defaults: `adapters.codex.timeoutSec` 1200 for a task run, `messageTimeoutSec` 180 for a message turn.
- The end of a run stores its final message as a `report` to the dispatching address.
- `SessionStart` and the new `SessionEnd` hook run `clean`. Lab `agent-bus` L4: `SessionEnd` ran 6 of 6 in `claude -p`.

## 6. Risks

1. Cost. The split costs about 12% more at list price, because two sessions write two caches (lab Q5). The gain is
   a small main session, not a lower bill. L4-1 measures it again.
2. Resume after `/clear` or a restart is not verified. A subagent of an earlier session may not resume. Then the
   Architect is dispatched again with the ledger (4f, step 4), and its context is lost. L4-1 checks it.
3. Forgery. Agents run as the same OS user. An agent that reads the key in a form that the hook does not see can
   forge a user record. R?2 and the key folder refusal catch the common forms only.
4. The R?2 law reads only the command text, with the R4 limit. A write from `node -e` passes the hook.
5. Injected text. A message from another agent is data, not an order of the user (R?3). A link from a reply opens
   only a project file (4j).
6. Delay. An idle main session does not wake for a message. A Codex agent gets a message at its next user turn.
7. Depth. A role at depth 3 has no `Agent` tool. A role that dispatches its own agents runs at depth 2 or less.
8. Codex. Each Codex turn has a base cost of about 20,000 tokens (lab). The hooks run only after the user trusts them.
9. Privacy. `.guilda/bus/user.jsonl` holds the text of user prompts. The file is git-ignored. The session
   transcript of Claude Code holds the same text.
10. Six labs gate their parts (section 2c). Each one has a fallback, and each fallback needs a yes of the user.

## 8. Open questions in the 0.4.0 scope

Each question waits for a lab or for the user. The Architect asks a user question with the question tool (D23)
before the task that needs the answer.

- O4-1 (D31): can the main session resume a subagent of an earlier session after `/clear` or a restart? L4-1.
- O4-2 (D31, D17): the hook fields. L4-1 and L4-2 check each one:
  - `PostToolUse` on `Agent` has the prompt and the agent ID.
  - `PostToolUse` runs for `SendMessage` and `AskUserQuestion`.
  - `SubagentStop` runs after each resume.

  `claude plugin validate --strict`. The fallback is `guilda:architect-agent`.

  the agent to load it.
- O4-5 (Codex): the sandbox flag on `codex exec resume`; the working folder of a hook; hooks in `codex exec resume`
  after one user trust. L4-4.
