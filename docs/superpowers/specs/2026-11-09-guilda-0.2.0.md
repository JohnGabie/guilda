Status: spec in requirements. Not approved (R3). The scope is `@decided` (release plan of 2026-11-09, and the

about the development branch of 0.2.0.

## 1. Intent

Field use of 0.1.0 in three projects showed four problems:

- The law rules did not run in two sessions, and nothing told the user (#2, #11).
- The process is too heavy for small and personal projects (#2, #13).
- Specs and briefs had gaps that the Executor or the Reviewer found late. Each gap cost about one task cycle (#2, #4,
  #5, #8, #9).
- A field report from a project reaches this repository only when someone writes it by hand (#12).

0.2.0 fixes these problems. It is a minor release, because core rules change meaning (0.x rule of `RELEASING.md`).

## 3. Rules that change meaning

The CHANGELOG entry of 0.2.0 lists these rules under "Changed". The rules change in place (D40): the project layer
copies no rule text, so no project runs `guilda:init` again. The user approved each text below on 2026-11-10
(section 5).

Each block is in the form of `core/rules.md`: one heading, then one `Rule:`, one `Why:` and one `Check:` line. A
`Check:` line is one line, also when it is long. The linter result of each block is under the block. The command:
copy the block to a temporary file, then run `node scripts/lint-rules.mjs --prefix <R, ARC or EXE> <file>`.

### R24 — Review cycle by process level (D1)

```
### R24 — One review cycle for each review unit
Rule:  Give each plan task its own Executor ↔ Reviewer cycle at `full`, and one review of the integration at `light`.
Why:   A cycle that covers several tasks hides defects in a large diff, and a `light` project accepts that risk by choice.
Check: gate — At `full`, the Reviewer rejects a diff that holds more than one plan task, and each task closes only on a written approval of the Reviewer. At `light`, the controller closes the integration only on a written approval of the Reviewer.
```

Linter: pass (exit 0). The earlier text had two sentences in `Rule:` and failed.

(2026-11-10, the user) The `Check:` line has again the sentence of 0.1.0: at `full`, each task closes only on a
written approval of the Reviewer. Pass 2 of `agents/reviewer.md` cites R24 for it.

### R11 — Rejections counted for each review unit (D1, D8)

```
### R11 — Small or large rejection; 3 rejections escalate
Rule:  Send small rejections to the Executor, large to the Architect, and the third to the Architect and the user.
Why:   A large fix changes a spec scenario, an Acceptance criterion, a contract or the file list, and only the Architect owns them.
Check: gate — The verdict states `REJECTED-SMALL` or `REJECTED-LARGE`. The controller counts the rejections of each review unit: a task at `full`, the integration at `light`. A verdict with `Stage: spec` does not count. QA sends its report to the Reviewer, never to the Executor.
```

Linter: pass (exit 0). The `Check:` line is now one line.

### R22 — no change

D1 cited R22 for "QA for each task". R22 is QA in two phases. QA at `light` still runs both phases, one time at the
end. The text of R22 stays.

### R13 — Questions through the question tool (D23)

```
### R13 — Decisions through the question tool
Rule:  Ask each decision in the question tool in plain words, with context, 2 to 4 options and the recommended first.
Why:   The context (where, what, a concrete scenario, the effect of each option) lets the user decide; a decision in a long reply was missed five times, and a rule ID with no meaning was not understood.
Check: judgment — No hook and no Reviewer sees the questions, so this rule is text only.
```

Linter: pass (exit 0). Approved 2026-11-10 with the plain-words addition. The earlier text had a `Rule:` of two lines and failed. In Claude Code, the question tool is
`AskUserQuestion`.

### ARC1 — One decision at a time in the question tool (D23)

```
### ARC1 — One decision at a time
Rule:  Ask each decision of the user alone in the question tool, never only in the reply text, and follow R13.
Why:   A list of questions gets partial answers, and a decision in the reply text was not seen five times.
Check: judgment — No hook and no Reviewer sees the questions, so this rule is text only.
```

Linter: pass (exit 0). The earlier `Rule:` had 23 words and failed.

### EXE2 — The new test fails against the old code (D10)

```
### EXE2 — Tests fail first, against the old code
Rule:  Run each new test against the old code, and record its failure output in the final answer.
Why:   A test that never failed on the old code can pass for the wrong reason and proves nothing.
Check: gate — The Reviewer rejects a final answer with no failure output of a new test against the old code.
```

Linter: pass (exit 0). No change to the earlier proposal.

### R4 — A plan section or a plan file (D27)

```
### R4 — One MD per feature; the plan is a section or one plan file
Rule:  Write each plan as a `## Plan: Part N` section of its feature MD, or in `<feature>.plan.md` next to it.
Why:   One place for each plan keeps the spec, its Acceptance scenarios and its plan in step.
Check: law — PreToolUse refuses a new file in `docs/superpowers/plans/`, and a new `*.plan.md` file whose `<feature>.md` is not in the same folder.
```

Linter: pass (exit 0). The `Check:` line is now one line.

The hook reads three tools (the user, 2026-11-10). In 0.1.1 the hook checks only `Write` and `Edit`. In the live
smoke test of 0.1.1, a plan file made through `Bash` passed. An example is `cat > docs/superpowers/plans/x.md`.
0.2.0 closes this gap in the same change of the R4 hook:

- The `Bash` path of `scripts/hooks/pre-tool-use.mjs` reads the command text. It finds each file that the command
  creates in a common shell form. The forms (the Architect's choice): a redirection (`>`, `>>`), `tee`, `cp`, `mv`
  and `touch`.
- The hook refuses the command when such a file is a new file in `docs/superpowers/plans/`, or a new orphan
  `*.plan.md`. The refusal cites R4 and records a violation, as for `Write`.
- This check runs before the R19 commit scan. Today the `Bash` path returns early when the command names no
  `git commit`.
- The limit: the hook reads only the command text. It catches the common forms, not each form. It does not see a
  path that comes from a variable or from a command substitution. It does not see a write from inside a script or an
  interpreter, such as `node -e` or `python -c`. So a plan file can still pass the hook.
- The `Check:` line does not change, because it names no tool.

### R27 — Truth first; only the leads disagree (D46)

```
### R27 — Truth first; only the leads disagree
Rule:  Report the evidence with its limits, never make a result look better, and send each objection to your lead.
Why:   A grader that preferred a fake success to an honest failure built a wrong product (D39), and only a lead argues with the user (D46).
Check: judgment — No check can see truth yet, so a Lab study (D39, D46) refines this rule in a later release.
```

### ARC7, ARC8, ARC10 — Concrete specs (D6, issue #5)

```
### ARC7 — Concrete scenarios
Rule:  Write each Acceptance scenario with its input data, exact expected result, QA tool and test name.
Why:   A vague scenario gives a green test that proves nothing, and QA cannot fail it.
Check: gate — The Reviewer rejects a scenario without an exact result or with a word from the vague list.

### ARC8 — One owner task for each decision
Rule:  Give each `@decided` item exactly one owner task in the traceability table before the briefs ship.
Why:   A decision without an owner is not built, and two owners build it two times in two ways.
Check: gate — The Reviewer rejects a plan whose table misses a `@decided` item or gives it two owners.

### ARC10 — Glossary for each new term
Rule:  Add each new domain term of a spec to `docs/superpowers/specs/GLOSSARY.md` with its forbidden synonyms.
Why:   Two names for one thing give two meanings in the code, the tests and the docs (R16).
Check: gate — The Reviewer rejects a spec that uses a domain term that the glossary does not define.
```

Linter: pass (exit 0) for each block. The texts are the texts of issue #5.

### ARC9 — A mutant for each new test (D7, issue #5)

```
### ARC9 — A mutant for each new test
Rule:  At `full`, name for each new test one change to the product code that makes the test fail.
Why:   A test that no product change can break guards nothing, and it stays green while the product breaks.
Check: gate — At `full`, and at `light` when the brief has a `Mutants:` field, the Reviewer applies each mutant in a temporary copy and classifies it as killed, survived or equivalent with a reason. A survived mutant is a rejection, an equivalent mutant is only noted, and a kill counts only when the failing assertion targets the mutant.
```

Linter: pass (exit 0). The text of issue #5 has no level and no classification. This text adds both from D7: required
at `full`, the Architect's choice at `light`, and the classification of #10.

## 3d. Project layer states, safe defaults and migrations (D40)

### States

### Required and defaulted fields (the Architect's choice)

| Kind | Fields | Missing | Invalid value |
|---|---|---|---|
| required | `guildaVersion`, `languages` (`replies`, `docs`), `tiers` (`master`, `journeyman`, `apprentice`), `writing`, `security`, `checks` (the 0.1.0 `checkSchema`) | broken project layer | broken project layer |
| defaulted | `schemaVersion` (1), `process` (`full`), `explain` (`full`), `scan` (`ignore: []`), `report` (`repo`: the `repository` value of the core manifest) | the default; the layer stays valid | `scan`: broken project layer. `process`, `explain`: fail closed to `full`, the layer stays valid, and one notice. `report.repo`: `scripts/report-send.mjs` saves the report and sends nothing |

The notice for an invalid `process` or `explain`: "guilda: .guilda/config.json has an invalid <field> value; guilda
uses full. Run guilda:update."

The hooks read with tolerance, and the two scripts that the user's flow runs are strict. Two functions keep the two
behaviors apart:

- `checkSchema` stays as it is today. It checks the required fields and `scan`. `loadConfig` calls it in each
  hook. It does not check `process`, `explain` or `report`. So an invalid value of these never gives a broken
  project layer.
- `checkStrict` is new, in `scripts/lib/project.mjs`. It runs `checkSchema`, then it checks the defaulted fields.
  `scripts/config-write.mjs` and `scripts/config-check.mjs` call it. They refuse an invalid `process`, `explain` or
  `report.repo` value and exit 1.
- `projectState` normalizes the value. It changes an invalid `process` or `explain` to `full`. It returns the
  notice text in a `notices` list. Only the session start prints the notices.

A refusal in a project with no `.guilda/` folder records nothing and creates no folder (0.1.1, S14).

### The context line of the level (D1, the Architect's choice)

- Session: `scripts/hooks/session-start.mjs` prints one new line after the `Languages:` line. Its form is

- Subagent: `scripts/hooks/subagent-start.mjs` prints `Docs language: <docs>. Process: <light or full>. Glossary: <path>`.
  Today the line has no `Process:` part.

### Migration contract

- `schemaVersion` lives in `.guilda/config.json`. A 0.1.x config has no `schemaVersion`, and the reader reads it
  as 1. A 0.2.0 config has `schemaVersion: 2`.
- Who writes `schemaVersion: 2` (the Architect's choice): `scripts/config-write.mjs`. It adds the field to each new
  config, as it adds `guildaVersion`. The template `skills/init/references/config-template.json` does not have the
  field. The number is one constant in `scripts/lib/project.mjs`.
- An existing config: `node scripts/config-write.mjs <projectDir> --migrate` reads the config and runs the
  migrations. It writes the result with `schemaVersion: 2` and the installed `guildaVersion`. It changes no other
  value. `guilda:update` runs it after the user approves (S43).
- The migrations from 1 to 2: a missing `process` becomes `full`; a missing `explain` becomes `full`; the
  `schemaVersion` becomes 2. Each migration is safe to run again.
- Each hook is its own process. So `projectState` (on top of `loadConfig`) runs the migrations in memory at each
  call, in each hook. Only the session start prints a notice.
- A migration writes the committed `.guilda/config.json` only through `guilda:update`, or after the user approves the
  write in a conversation.
- A hook never asks a question. A value that no migration can infer becomes one session start notice. The notice
  sends the user to `guilda:update`. Until then, the hook uses the safe default. Each value of 1 to 2 can be
  inferred. So 0.2.0 has no case of this path, and no test.
- The reader may not know the `schemaVersion` of a config. Then the tolerant reader reads it and ignores the
  unknown fields. The layer stays valid. The notice: "guilda: .guilda/config.json has schemaVersion <n>, newer
  than this guilda knows. Run guilda:update."

0.2.0 has one text, for a patch, a minor or a major update:

"guilda updated <configured> → <installed>. The project layer works as it is. Run guilda:update to see the changes
and to save the new version."

- `skills/update/SKILL.md` changes with it. Its steps 6 and 9 stop telling the user to run `guilda:init` again. A

## 4a. Contracts of the internal scripts (the Architect's choice)

### `doctor`

Command: `node scripts/doctor.mjs <projectDir> [--session <id>] [--agents <name,name,...>]`. It prints one line for
each check: `<check>: PASS|FAIL|UNKNOWN — <evidence>`. It exits 1 when a line is FAIL, and 0 in the other cases.

| Check | Evidence source | PASS | FAIL | UNKNOWN |
|---|---|---|---|---|
| core plugin loaded | `.claude-plugin/plugin.json` of the plugin root that holds the script | the name is `guilda`, and the line shows the version | the manifest is not readable | never |
| hooks live | the marker `.guilda/.hooks-live.json` | its `sessionId` is equal to `--session` | no marker in a project that has a `.guilda/` folder | no `--session`, another session ID, or no `.guilda/` folder; the line shows the marker time |
| `guilda:*` agents present | the `--agents` list, against the file names of the core `agents/` folder | the list has each agent of the folder | the list misses one; the line names it | no `--agents` |
| extension plugin loaded | the method of the O1 lab | as the lab decides | as the lab decides | always, on a NO-GO or MORE DATA of the lab; the evidence is "no method" |
| project files present | `projectState`, and `.guilda/rules.md` on disk | a valid project layer and the rules file | no `.guilda/` folder, or a broken project layer; the line shows the reason | never |
| version | the installed version, `guildaVersion` and `schemaVersion` of the config | the config is not older | never | the config is older; the line says "Run guilda:update" |

- The marker: `scripts/hooks/session-start.mjs` writes `.guilda/.hooks-live.json` at each run in a project that
  has a `.guilda/` folder. The content is `{ "sessionId": "<session_id of the hook input>", "version": "<installed>", "at": "<ISO time>" }`.
  With no `.guilda/` folder the hook writes nothing (section 3d).
- The ignore line: `IGNORED` in `scripts/lib/violations.mjs` gets the marker name. The session start calls
  `ensureIgnored` before it writes the marker. Today it does not call it. So a 0.1.x project gets the line in
  `.guilda/.gitignore` at its first 0.2.0 session. It does not commit the marker. If the line cannot be
  written, the hook writes no marker.
- The `--agents` form: each name is as the `Agent` tool lists it, for example `guilda:executor`. `doctor` removes
  the prefix `guilda:`. It compares the rest with each file name of `agents/` without `.md`. It ignores a name with
  no `guilda:` prefix.
- The order: the O1 lab runs before the `doctor` task (section 2, Labs). On a GO, the task builds the extension
  line with the method of the lab. On a NO-GO or MORE DATA, the line is always UNKNOWN.
- The caller: a script cannot see the session. So the caller gives `--session` and `--agents`. The Architect reads
  the agent types of its `Agent` tool for `--agents`. Not verified: that a skill can read the session ID
  (`${CLAUDE_SESSION_ID}`). Without it the hooks line is UNKNOWN with the marker time, and the caller compares the time.
- When: the Architect runs it before the first dispatch of a session (D2). `guilda:init` runs it at its end. Each
  one shows the lines that are not PASS to the user.
- The test fixture for "hooks live" is a temporary project with a valid config. Its marker file has the
  `sessionId` `s1`. The test runs `doctor` with `--session s1`, then with `--session s2`, then with the marker removed.

### `report-send`

Command: `node scripts/report-send.mjs <projectDir> <reportFile> --type <improvement|bug|feature|other> [--repo <owner/name>]`.

- Input: `<reportFile>` is a Markdown file. Its first line is `# <title>`. The title is the text after `# `. The
  body is the rest of the file, without the title line and without the blank lines directly under it. A file with
  another first line is a usage error (exit 1).
- Type: `--type` is required. A value outside the four is a usage error (exit 1).
- Project layer: with no `.guilda/` folder, guilda is not set up (R28). The script prints
  `refused: guilda is not set up`, then the R28 notice text of section 3a, and exits 1. It saves nothing and creates
  no folder. In a broken project layer the script uses the default repository.
- Target repository: `--repo`, then `report.repo` of `.guilda/config.json`, then the default. The default is the
  `repository` value of the core `.claude-plugin/plugin.json`, which is this repository.
- Repository form: a value is `owner/name`, or `https://github.com/owner/name` with or without a last `/` or
  `.git`. The script changes the URL form to `owner/name`, because `gh --repo` takes that form. The default is a
  URL, so it passes through this change. Another value is invalid. An invalid `--repo` is a usage error (exit 1).
  With an invalid `report.repo`, the script saves the report and sends nothing (section 3d).
- Labels: `report-improvement`, `report-bug`, `report-feature`, `report-other`. Each label exists in this
  repository, with one issue template `.github/ISSUE_TEMPLATE/report-<type>.md`.
- Send: `gh issue create --repo <owner/name> --title <title> --body-file - --label <label>`. The script gives the
  body on standard input. So the issue body does not repeat the title line.
- Output, first line: `sent: <issue URL>` (exit 0), `saved: <path>` (exit 0), `refused: R19 <hit>` (exit 1), or
  `refused: guilda is not set up` (exit 1).
- A save goes to `.guilda/reports/<date>-<type>-<slug of the title>.md`. The saved file is the full report file,
  with its title line. The script saves when `gh` is missing, when `gh auth status` fails, and when
  `gh issue create` fails.
- `.guilda/reports/` is git-ignored (the user, 2026-11-10). `IGNORED` gets the line `reports/`, and the script calls `ensureIgnored` before
  a save. A saved report is text for another repository, not project content.
