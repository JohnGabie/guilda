# guilda 0.2.0 — process

Status: spec in requirements. Not approved (R3). The scope is `@decided` (release plan of 2026-11-09).
Decisions: [decision register](2026-11-09-guilda-decisions.md). Earlier release: [0.1.1](2026-11-09-guilda-0.1.1.md).
Later releases: [backlog](2026-11-09-guilda-backlog.md).

## 1. Intent

Field use of 0.1.0 in three projects showed four problems:

- The law rules did not run in two sessions, and nothing told the user (#2, #11).
- The process is too heavy for small and personal projects (#2, #13).
- Specs and briefs had gaps that the Executor or the Reviewer found late. Each gap cost about one task cycle (#2, #4,
  #5, #8, #9).
- A field report from a project reaches this repository only when someone writes it by hand (#12).

0.2.0 fixes these problems. It is a minor release, because core rules change meaning (0.x rule of `RELEASING.md`).

## 3. Rules that change meaning

The CHANGELOG entry of 0.2.0 lists these rules under "Changed" with this note: "Rules changed meaning. Run
`guilda:init` again in each project." Each text below is `@proposed` until the user approves it.

Each block is in the form of `core/rules.md`: one heading, then one `Rule:`, one `Why:` and one `Check:` line. A
`Check:` line is one line, also when it is long. The linter result of each block is under the block. The command:
copy the block to a temporary file, then run `node scripts/lint-rules.mjs --prefix <R, ARC or EXE> <file>`.

### R24 — Review cycle by process level (D1)

```
### R24 — One review cycle for each review unit
Rule:  Give each plan task its own Executor ↔ Reviewer cycle at `full`, and one review of the integration at `light`.
Why:   A cycle that covers several tasks hides defects in a large diff, and a `light` project accepts that risk by choice.
Check: gate — At `full`, the Reviewer rejects a diff that holds more than one plan task. At `light`, the controller closes the integration only on a written approval of the Reviewer.
```

Linter: pass (exit 0). The earlier text had two sentences in `Rule:` and failed.

### R11 — Rejections counted for each review unit (D1, D8)

```
### R11 — Small or large rejection; 3 rejections escalate
Rule:  Send small rejections to the Executor, large to the Architect, and the third to the Architect and the user.
Why:   A large fix changes a spec scenario, an Acceptance criterion, a contract or the file list, and only the Architect owns them.
Check: gate — The verdict states `REJECTED-SMALL` or `REJECTED-LARGE`. The controller counts the rejections of each review unit: a task at `full`, the integration at `light`. A verdict with `Stage: spec` does not count. QA sends its report to the Reviewer, never to the Executor.
```

Linter: pass (exit 0). The `Check:` line is now one line.

### R22 — no change

D1 cited R22 for "QA for each task". R22 is QA in two phases. QA at `light` still runs both phases, one time at the
end. The text of R22 stays.

### R13 — Questions through the question tool (D23)

```
### R13 — Decisions through the question tool
Rule:  Ask each decision in the question tool with its context, 2 to 4 options and the recommended option first.
Why:   The context (where, what, a concrete scenario, the effect of each option) lets the user decide, and a decision in a long reply was missed five times.
Check: judgment — No hook and no Reviewer sees the questions, so this rule is text only.
```

Linter: pass (exit 0). The earlier text had a `Rule:` of two lines and failed. In Claude Code, the question tool is
`AskUserQuestion`.

### ARC1 — One decision at a time in the question tool (D23)

```
### ARC1 — One decision at a time
Rule:  Ask each decision of the user alone in the question tool, never only in the reply text, and follow R13.
Why:   A list of questions gets partial answers, and a decision in the reply text was not seen five times.
Check: judgment — No hook and no Reviewer sees the questions, so this rule is text only.
```

Linter: pass (exit 0). The earlier `Rule:` had 23 words and failed.

### EXE2 — The new test fails against the old code (D10)

```
### EXE2 — Tests fail first, against the old code
Rule:  Run each new test against the old code, and record its failure output in the final answer.
Why:   A test that never failed on the old code can pass for the wrong reason and proves nothing.
Check: gate — The Reviewer rejects a final answer with no failure output of a new test against the old code.
```

Linter: pass (exit 0). No change to the earlier proposal.

### R4 — A plan section or a plan file (D27)

```
### R4 — One MD per feature; the plan is a section or one plan file
Rule:  Write each plan as a `## Plan: Part N` section of its feature MD, or in `<feature>.plan.md` next to it.
Why:   One place for each plan keeps the spec, its Acceptance scenarios and its plan in step.
Check: law — PreToolUse refuses a new file in `docs/superpowers/plans/`, and a new `*.plan.md` file whose `<feature>.md` is not in the same folder.
```

Linter: pass (exit 0). The `Check:` line is now one line.

## 3a. New rules

These rules are new, so no rule changes meaning. Each text is `@proposed` until the user approves it.

### R26 — Labs run in a dispatched agent (D19)

R26 is the next free core ID after R25. The core rule of D19 gets the ID R26.

```
### R26 — Labs run in a dispatched agent
Rule:  Run each lab, experiment or spike in a dispatched agent, never in the controller session.
Why:   The controller writes the hypothesis and gives the verdict, so a lab that it runs itself grades its own work and fills its context.
Check: gate — The Reviewer rejects a lab report that has no agent ID of the agent that ran the lab (D34).
```

Linter: pass (exit 0).

### ARC7, ARC8, ARC10 — Concrete specs (D6, issue #5)

```
### ARC7 — Concrete scenarios
Rule:  Write each Acceptance scenario with its input data, exact expected result, QA tool and test name.
Why:   A vague scenario gives a green test that proves nothing, and QA cannot fail it.
Check: gate — The Reviewer rejects a scenario without an exact result or with a word from the vague list.

### ARC8 — One owner task for each decision
Rule:  Give each `@decided` item exactly one owner task in the traceability table before the briefs ship.
Why:   A decision without an owner is not built, and two owners build it two times in two ways.
Check: gate — The Reviewer rejects a plan whose table misses a `@decided` item or gives it two owners.

### ARC10 — Glossary for each new term
Rule:  Add each new domain term of a spec to `docs/superpowers/specs/GLOSSARY.md` with its forbidden synonyms.
Why:   Two names for one thing give two meanings in the code, the tests and the docs (R16).
Check: gate — The Reviewer rejects a spec that uses a domain term that the glossary does not define.
```

Linter: pass (exit 0) for each block. The texts are the texts of issue #5.

### ARC9 — A mutant for each new test (D7, issue #5)

```
### ARC9 — A mutant for each new test
Rule:  At `full`, name for each new test one change to the product code that makes the test fail.
Why:   A test that no product change can break guards nothing, and it stays green while the product breaks.
Check: gate — At `full`, and at `light` when the brief has a `Mutants:` field, the Reviewer applies each mutant in a temporary copy and classifies it as killed, survived or equivalent with a reason. A survived mutant is a rejection, an equivalent mutant is only noted, and a kill counts only when the failing assertion targets the mutant.
```

Linter: pass (exit 0). The text of issue #5 has no level and no classification. This text adds both from D7: required
at `full`, the Architect's choice at `light`, and the classification of #10.

### Glossary proposals for 0.2.0

`@proposed`. Each line has the format of `core/glossary.md`. The register has the lines for `foreman`, `field report`
and `lab report`.

| Term | Line |
|---|---|
| process level | `- **process level**: the value of the process field in .guilda/config.json, light or full, that sets the review cycle and the gates but never a law. Forbidden: process mode, process profile.` |
| security zone | `- **security zone**: a spec block that the Architect marks because it touches a risk area, and that gets a Security review at each process level. Forbidden: hot spot, sensitive area.` |
| review unit | `- **review unit**: the work that one Reviewer cycle covers and that the rejections count against: a task at full, the integration at light. Forbidden: review batch, review scope.` |
| domain skill | `- **domain skill**: a skill with the knowledge of one area that a brief names in its Skills field, and that the Executor and the Reviewer both load. Forbidden: specialist agent, area agent.` |
| triage | `- **triage**: the step before each brief that sends an open question to the Lab, a risk area to Security, and a decided change to Engineering. Forbidden: task routing, intake.` |
| mutant | `- **mutant**: one named change to the product code that makes a new test fail, classified as killed, survived or equivalent. Forbidden: bug injection, fault seed.` |

The forbidden words are phrases that guilda text does not use for another thing. `ste-check` matches a forbidden
word in any case and in any text, so a common word such as "mode" or "tier" cannot be forbidden.

## 6. Risks

- D28: `skill-creator` is a required dependency. Without the official marketplace, guilda installs but does not
  load. The activation check (D2) must show this, and an Acceptance scenario tests it.
- D3: anonymization by a model is not reliable in a public repository. The R19 scan does not find a domain name or a
  business term. The user approves each field before the send.
- D29: the AI artifact gate costs 3 or more cases, a baseline run and injection tests for each AI artifact. The plan
  states the cost.
- D1: the levels have no evidence yet. E1 runs after the build; its result can change the gates.
- D30, D29: two labs (`@open`) run before their build. A NO-GO moves the item out of 0.2.0.
- Rule changes: projects on 0.1.x must run `guilda:init` again. A project that does not run it keeps the old rules
  text in its layer. A 0.1.0 install that skips 0.1.1 does not see the note (U3).

## 7. Acceptance scenarios

Only for `@decided` items. The other items get their scenarios after approval. Each scenario has the ARC7 shape.

### S1 — `guilda:init` asks for the level (D1)

- Given: a project with no `.guilda/config.json`.
- When: the user runs `guilda:init`.
- Then: `guilda:init` asks "a prototype or personal project, or a product" in the question tool, and writes
  `process: "light"` or `process: "full"`. No default exists.
- Tool: `claude plugin eval` with a scripted answer.
- Test: an eval case for each answer.

### S2 — Laws run at `light` (D1)

- Given: a project with `process: "light"`.
- When: an agent writes a new file in `docs/superpowers/plans/`, or commits an absolute path.
- Then: the R4 hook and the R19 hook refuse the action, as at `full`.
- Tool: `node --test`.
- Test: `tests/pre-tool-use.test.mjs`, the existing cases with a `light` config.

### S3 — A security zone gets a review at `light` (D1)

- Given: a `light` project and a spec block marked as a security zone.
- When: the integration of a task in that zone ends.
- Then: the controller dispatches Security for that task, in the one review at the end.
- Tool: `claude plugin eval` on the Architect with a fixture spec.
- Test: an eval case with a marked zone and one with no zone.

### S4 — A field report with a secret is not sent (D3)

- Given: a draft field report whose text has a token that the R19 scan finds.
- When: the user approves the send.
- Then: `scripts/report-send.mjs` refuses the send, names the hit, and exits 1.
- Tool: `node --test` on `scripts/report-send.mjs`.
- Test: `tests/report-send.test.mjs`, a report fixture with a planted token.

### S5 — A field report without `gh` stays local (D3)

- Given: no `gh` command, or no login.
- When: the user approves the send.
- Then: `scripts/report-send.mjs` saves the report in `.guilda/reports/`, sends nothing, and prints the path.
- Tool: `node --test` on `scripts/report-send.mjs`, with `PATH` without `gh`.
- Test: `tests/report-send.test.mjs`, a case without `gh` and a case without a login.

### S6 — The report type sets the label (D3)

- Given: a field report of type bug.
- When: `scripts/report-send.mjs` sends the report.
- Then: the `gh issue create` command has the label of the bug type.
- Tool: `node --test` on `scripts/report-send.mjs`, with a stub `gh`.
- Test: `tests/report-send.test.mjs`, one case for each type.

### S7 — Mutant classification (D7)

- Given: a `full` task with a new test and a mutant that does not change behavior.
- When: the Reviewer writes its verdict.
- Then: the verdict marks the mutant `equivalent` with a reason, and does not send it to a fix round.
