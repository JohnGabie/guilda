# guilda 0.2.0 — process

Status: spec in requirements. Not approved (R3). The scope is `@decided` (release plan of 2026-11-09, and the
checklist of section 5 that the user confirmed on 2026-11-10).
Decisions: [decision register](2026-11-09-guilda-decisions.md). Earlier release: [0.1.1](2026-11-09-guilda-0.1.1.md).
Later releases: [backlog](2026-11-09-guilda-backlog.md).

## 1. Intent

Field use of 0.1.0 in three projects showed four problems:

- The law rules did not run in two sessions, and nothing told the user (#2, #11).
- The process is too heavy for small and personal projects (#2, #13).
- Specs and briefs had gaps that the Executor or the Reviewer found late. Each gap cost about one task cycle (#2, #4,
  #5, #8, #9).
- A field report from a project reaches this repository only when someone writes it by hand (#12).

0.2.0 fixes these problems. It is a minor release, because core rules change meaning (0.x rule of `RELEASING.md`).

## 3. Rules that change meaning

The CHANGELOG entry of 0.2.0 lists these rules under "Changed". The rules change in place (D40): the project layer
copies no rule text, so no project runs `guilda:init` again. The user approved each text below on 2026-11-10
(section 5).

Each block is in the form of `core/rules.md`: one heading, then one `Rule:`, one `Why:` and one `Check:` line. A
`Check:` line is one line, also when it is long. The linter result of each block is under the block. The command:
copy the block to a temporary file, then run `node scripts/lint-rules.mjs --prefix <R, ARC or EXE> <file>`.

### R24 — Review cycle by process level (D1)

```
### R24 — One review cycle for each review unit
Rule:  Give each plan task its own Executor ↔ Reviewer cycle at `full`, and one review of the integration at `light`.
Why:   A cycle that covers several tasks hides defects in a large diff, and a `light` project accepts that risk by choice.
Check: gate — At `full`, the Reviewer rejects a diff that holds more than one plan task. At `light`, the controller closes the integration only on a written approval of the Reviewer.
```

Linter: pass (exit 0). The earlier text had two sentences in `Rule:` and failed.

### R11 — Rejections counted for each review unit (D1, D8)

```
### R11 — Small or large rejection; 3 rejections escalate
Rule:  Send small rejections to the Executor, large to the Architect, and the third to the Architect and the user.
Why:   A large fix changes a spec scenario, an Acceptance criterion, a contract or the file list, and only the Architect owns them.
Check: gate — The verdict states `REJECTED-SMALL` or `REJECTED-LARGE`. The controller counts the rejections of each review unit: a task at `full`, the integration at `light`. A verdict with `Stage: spec` does not count. QA sends its report to the Reviewer, never to the Executor.
```

Linter: pass (exit 0). The `Check:` line is now one line.

### R22 — no change

D1 cited R22 for "QA for each task". R22 is QA in two phases. QA at `light` still runs both phases, one time at the
end. The text of R22 stays.

### R13 — Questions through the question tool (D23)

```
### R13 — Decisions through the question tool
Rule:  Ask each decision in the question tool in plain words, with context, 2 to 4 options and the recommended first.
Why:   The context (where, what, a concrete scenario, the effect of each option) lets the user decide; a decision in a long reply was missed five times, and a rule ID with no meaning was not understood.
Check: judgment — No hook and no Reviewer sees the questions, so this rule is text only.
```

Linter: pass (exit 0). Approved 2026-11-10 with the plain-words addition. The earlier text had a `Rule:` of two lines and failed. In Claude Code, the question tool is
`AskUserQuestion`.

### ARC1 — One decision at a time in the question tool (D23)

```
### ARC1 — One decision at a time
Rule:  Ask each decision of the user alone in the question tool, never only in the reply text, and follow R13.
Why:   A list of questions gets partial answers, and a decision in the reply text was not seen five times.
Check: judgment — No hook and no Reviewer sees the questions, so this rule is text only.
```

Linter: pass (exit 0). The earlier `Rule:` had 23 words and failed.

### EXE2 — The new test fails against the old code (D10)

```
### EXE2 — Tests fail first, against the old code
Rule:  Run each new test against the old code, and record its failure output in the final answer.
Why:   A test that never failed on the old code can pass for the wrong reason and proves nothing.
Check: gate — The Reviewer rejects a final answer with no failure output of a new test against the old code.
```

Linter: pass (exit 0). No change to the earlier proposal.

### R4 — A plan section or a plan file (D27)

```
### R4 — One MD per feature; the plan is a section or one plan file
Rule:  Write each plan as a `## Plan: Part N` section of its feature MD, or in `<feature>.plan.md` next to it.
Why:   One place for each plan keeps the spec, its Acceptance scenarios and its plan in step.
Check: law — PreToolUse refuses a new file in `docs/superpowers/plans/`, and a new `*.plan.md` file whose `<feature>.md` is not in the same folder.
```

Linter: pass (exit 0). The `Check:` line is now one line.

### R26 — Labs run in a dispatched agent (D19)

R26 is the next free core ID after R25. The core rule of D19 gets the ID R26.

```
### R26 — Labs run in a dispatched agent
Rule:  Run each lab, experiment or spike in a dispatched agent, never in the controller session.
Why:   The controller writes the hypothesis and gives the verdict, so a lab that it runs itself grades its own work and fills its context.
Check: gate — The Reviewer rejects a lab report that has no agent ID of the agent that ran the lab (D34).
```

Linter: pass (exit 0).

### R27 — Truth first; only the leads disagree (D46)

```
### R27 — Truth first; only the leads disagree
Rule:  Report the evidence with its limits, never make a result look better, and send each objection to your lead.
Why:   A grader that preferred a fake success to an honest failure built a wrong product (D39), and only a lead argues with the user (D46).
Check: judgment — No check can see truth yet, so a Lab study (D39, D46) refines this rule in a later release.
```

Linter: pass (exit 0). The leads are the Architect and the lead of each group. Until 0.5.0 the
`security` agent is the lead of Security. R14 (the Architect disagrees) stays.

### R28 — Tell the user when guilda is not set up (D40)

R28 is the next free core ID after R27. The user decided the law and the notice text on 2026-11-10.

```
### R28 — Tell the user when guilda is not set up
Rule:  With no `.guilda/` folder, tell the user that guilda is not set up, and run no other law.
Why:   A plugin that loads and does nothing looks like it works, so the user trusts checks that never ran (#2, #11).
Check: law — SessionStart, and PreToolUse on a guilda skill or a `guilda:*` agent, print the set-up notice.
```

Linter: pass (exit 0). The notice text: "guilda is installed but not set up in this project. If you just installed it,
reload; then run guilda:init. Without it guilda does not work."

- Channel and frequency (the Architect's choice): the session start prints the notice once per session. It prints
  it when the source is `startup` or `clear`. It goes in `additionalContext` for the model and in `systemMessage`
  for the user. The PreToolUse hook prints it in `systemMessage` at each `Skill` call of a `guilda:` skill. The one
  exception is `guilda:init`. It also prints it at each `Agent` call of a `guilda:*` agent. It never refuses a call.
- Not verified: that `systemMessage` of a PreToolUse hook that does not refuse shows to the user. The build checks it
  on the current Claude Code before the task closes.
- Release: 0.2.0, because `RELEASING.md` says that a new rule raises the minor number (0.1.1 spec, Q1).

### ARC7, ARC8, ARC10 — Concrete specs (D6, issue #5)

```
### ARC7 — Concrete scenarios
Rule:  Write each Acceptance scenario with its input data, exact expected result, QA tool and test name.
Why:   A vague scenario gives a green test that proves nothing, and QA cannot fail it.
Check: gate — The Reviewer rejects a scenario without an exact result or with a word from the vague list.

### ARC8 — One owner task for each decision
Rule:  Give each `@decided` item exactly one owner task in the traceability table before the briefs ship.
Why:   A decision without an owner is not built, and two owners build it two times in two ways.
Check: gate — The Reviewer rejects a plan whose table misses a `@decided` item or gives it two owners.

### ARC10 — Glossary for each new term
Rule:  Add each new domain term of a spec to `docs/superpowers/specs/GLOSSARY.md` with its forbidden synonyms.
Why:   Two names for one thing give two meanings in the code, the tests and the docs (R16).
Check: gate — The Reviewer rejects a spec that uses a domain term that the glossary does not define.
```

Linter: pass (exit 0) for each block. The texts are the texts of issue #5.

### ARC9 — A mutant for each new test (D7, issue #5)

```
### ARC9 — A mutant for each new test
Rule:  At `full`, name for each new test one change to the product code that makes the test fail.
Why:   A test that no product change can break guards nothing, and it stays green while the product breaks.
Check: gate — At `full`, and at `light` when the brief has a `Mutants:` field, the Reviewer applies each mutant in a temporary copy and classifies it as killed, survived or equivalent with a reason. A survived mutant is a rejection, an equivalent mutant is only noted, and a kill counts only when the failing assertion targets the mutant.
```

Linter: pass (exit 0). The text of issue #5 has no level and no classification. This text adds both from D7: required
at `full`, the Architect's choice at `light`, and the classification of #10.

### Glossary proposals for 0.2.0

Approved by the user on 2026-11-10 (section 5). Each line has the format of `core/glossary.md`.

| Term | Line |
|---|---|
| process level | `- **process level**: the value of the process field in .guilda/config.json, light or full, that sets the review cycle and the gates but never a law. Forbidden: process mode, process profile.` |
| security zone | `- **security zone**: a spec block that the Architect marks because it touches a risk area, and that gets a Security review at each process level. Forbidden: hot spot, sensitive area.` |
| review unit | `- **review unit**: the work that one Reviewer cycle covers and that the rejections count against: a task at full, the integration at light. Forbidden: review batch, review scope.` |
| domain skill | `- **domain skill**: a skill with the knowledge of one area that a brief names in its Skills field, and that the Executor and the Reviewer both load. Forbidden: specialist agent, area agent.` |
| triage | `- **triage**: the step before each brief that sends an open question to the Lab, a risk area to Security, and a decided change to Engineering. Forbidden: task routing, intake.` |
| mutant | `- **mutant**: one named change to the product code that makes a new test fail, classified as killed, survived or equivalent. Forbidden: bug injection, fault seed.` |

The register has the lines for `field report`, `lab report` and `Lab group`. The `supervisor` line is approved, and
it enters `core/glossary.md` in 0.5.0.

The forbidden words are phrases that guilda text does not use for another thing. `ste-check` matches a forbidden
word in any case and in any text, so a common word such as "mode" or "tier" cannot be forbidden.

## 3c. The core plugin and the extension plugin (D40)

The user decided the split on 2026-11-10. The agents stay in the core plugin `guilda`. So their names
(`guilda:executor`, `guilda:reviewer`, `guilda:qa`, `guilda:security`, `guilda:version-control`) and the hook
matchers of `hooks/hooks.json` do not change. The extension holds only what needs `skill-creator` and `superpowers`.

| Part | Core plugin `guilda` | Extension plugin (name: O3) |
|---|---|---|
| Manifest | `.claude-plugin/plugin.json`, no `dependencies` | `plugins/<extension>/.claude-plugin/plugin.json`, with `skill-creator` and `superpowers` and version ranges |
| Laws and hooks | `hooks/hooks.json`, `scripts/hooks/`, `scripts/lib/` | none |
| Rules | `core/` | none |
| Agents | `agents/`: the five 0.1.0 agents, the DevOps advisor (D42) and the AI lead (D45) | none |
| User skills | `skills/architect`, `skills/init`, `skills/update`, `skills/report` | none |
| Other skills | `guilda:lab`, if O5 makes it a skill | the domain skills of D25, D28, D29, D36, D42 and D45, one folder each under `plugins/<extension>/skills/` |
| Agent creator (D41) | none | the agent creator (skill or agent: O2), because it builds on `skill-creator` |
| Scripts | `scripts/doctor.mjs`, `scripts/report-send.mjs`, and the 0.1.0 scripts | none |

One repository and one marketplace (the Architect's choice):

```
.claude-plugin/marketplace.json   lists "guilda" (source "./") and the extension (source "./plugins/<extension>")
.claude-plugin/plugin.json        the core manifest
agents/  core/  hooks/  scripts/  skills/   the core
plugins/<extension>/
  .claude-plugin/plugin.json      the extension manifest
  skills/<domain skill>/SKILL.md
tests/  docs/  evals/             stay at the root
```

- The core stays at the repository root, so the marketplace source of a 0.1.x install (`./`) does not change.
- The core folder holds `plugins/<extension>/` as a subfolder. Claude Code loads plugin components from the root
  folders of the plugin only. So the core does not load the extension skills. Not verified: the build checks it with
  `claude plugin validate --strict .` and a live load of the core alone (S13).

## 3d. Project layer states, safe defaults and migrations (D40)

### States

| State | How the hook sees it | Laws R4, R18, R19, ARC6 | Session start |
|---|---|---|---|
| no project layer | no `.guilda/` folder | do not run (the user, 2026-11-10) | the R28 notice only; no core rules load |
| broken project layer | a `.guilda/` folder, and `config.json` is missing, unreadable, not JSON, or fails the schema check | run with the safe defaults (fail closed; the fix ships in 0.1.1) | the core rules and `.guilda/rules.md` load, with the safe defaults and one notice |
| valid project layer | the config passes the schema check after the migrations | run with the config | as in 0.1.0, with the migrated config |

A refusal in a project with no `.guilda/` folder records nothing and creates no folder (0.1.1, S14).

### Safe defaults (the Architect's choice)

| Field | Safe value | Reason |
|---|---|---|
| `tiers` | the values of `core/tiers.json` | the default of ARC4 today |
| `languages.replies`, `languages.docs` | `en` | the language of the plugin text |
| `process` | `full` | the stricter level, and the behavior of 0.1.0 |
| `explain` | `full` | a question with its full context is the safer side of D23 |
| `security` | `enabled: true`, `riskAreas: []` | a Security review of a risk area stays on |
| `scan.ignore` | `[]` | the R19 scan reads each staged file |
| `writing`, `checks` | `free: []`, `exceptions: []`; `checks: []` | no exception, and no check command is guessed |

The core rules load in a broken project layer, because the laws run there and the model must know them. The notice
text: "guilda: <reason>. guilda runs with safe defaults. Run guilda:init to fix .guilda/config.json." The notice
shows once per session, as R28 does.

### Migration contract

- `schemaVersion` lives in `.guilda/config.json`. A 0.1.x config has no `schemaVersion`, and the reader reads it
  as 1. A 0.2.0 config has `schemaVersion: 2`.
- The migrations from 1 to 2: a missing `process` becomes `full`; a missing `explain` becomes `full`; the
  `schemaVersion` becomes 2. Each migration is safe to run again.
- The migrations run in memory at each session start, and each hook reads the migrated config.
- A migration writes the committed `.guilda/config.json` only through `guilda:update`, or after the user approves the
  write in a conversation.
- A hook never asks a question. A value that no migration can infer becomes one session start notice. The notice
  sends the user to `guilda:update`. Until then, the hook uses the safe default. Each value of 1 to 2 can be inferred.
- The reader may not know the `schemaVersion` of a config. Then the tolerant reader reads it and ignores the
  unknown fields. A notice sends the user to `guilda:update`.

## 6. Risks

- D28, D40: `skill-creator` and `superpowers` are required dependencies of the extension plugin. Without their
  marketplaces, the extension does not load. The core plugin still loads with the laws on, and the activation check
  (D2) tells the user. S13 tests this.

  business term. The user approves each field before the send.
- D29: the AI artifact gate costs 3 or more cases, a baseline run and injection tests for each AI artifact. The plan
  states the cost.
- D1: the levels have no evidence yet. E1 runs after the build; its result can change the gates.
- D29, D30, D43, O1, O7: five labs gate their parts (section 2, Labs). A NO-GO or MORE DATA stops the part, and the
  part goes to the user.
- Rule changes: the rules change in place (D40). The project layer copies no rule text, and the session start
  migrates a 0.1.x layer in memory (U3, section 3d). A hook never asks a question. A value that no migration can
  infer becomes a notice that sends the user to `guilda:update`.

## 8. Open questions in the 0.2.0 scope

Each question waits for the user or for a lab. The Architect asks them with the question tool (D23) before the
task that needs the answer.

- O1 (D2, D40): how does the core plugin see that the extension plugin did not load? A hook cannot see the list of
  loaded plugins or agents (D2). A lab answers it (section 2, Labs). Candidates: a marker file that the extension
  writes at session start, or `claude plugin list`.
- O2 (D41): is the agent creator a skill or an agent, and what is its name? Its start point is open too: the
  `agent-creator` agent of `plugin-dev`, or a new skill.
- O3 (D28, D29, D36, D42, D45): the names and the folders of the domain skills. The names of the DevOps advisor
  agent, the AI lead agent and the extension plugin.
- O4 (D42): how the production-lock hook sees the explicit approval of the user. A hook sees only the tool call, not
  the conversation.
- O5 (D24, D30): where the lab brief method lives: the reference `lab.md` of the Architect, or the `guilda:lab` skill.
- O6 (D24): a frontmatter field that hides a skill from the user menu is not verified.
- O7 (D42): how the production-lock hook recognizes a production command. A lab of the DevOps group answers it. The
  lab has research and an experiment in a dispatched agent. It comes before the build of the lock (section 2, Labs).
