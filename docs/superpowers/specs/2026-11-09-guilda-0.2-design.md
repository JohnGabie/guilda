# guilda 0.2 — design

Status: draft, in requirements. Not approved (R3).
Version target: 0.2.0, a minor release (new rules, a new skill, no core rule removed).
Sources: issues #2 to #13 of this repository, and the evidence that they cite.

Tags (ARC2): `@decided` = the user approved it. `@proposed` = the Architect's proposal, not approved yet.
`@open` = a question for the user.

## 1. Intent

Field use of 0.1.0 in three projects showed four problems:

- The law rules did not run in two sessions, and nothing told the user (#2, #11).
- The process is too heavy for small and personal projects (#2, #13, the user's notes).
- Specs and briefs had gaps. The Executor or the Reviewer found them late. Each gap cost about one task cycle
  (#2, #4, #5, #8, #9).
- A field report from a project reaches this repository only when someone writes it by hand (#12).

0.2 fixes these problems. It also fixes one parser defect (#6).

### D1 — Process levels `@decided`, values by experiment E1

`.guilda/config.json` gets a field `process`. The user asked for four levels on 2026-11-09, and for an experiment
that sets what each level does (E1).

- `@proposed` The four levels:

  | Level | Use | Review | Mutants | QA |
  |---|---|---|---|---|
  | `sketch` | prototype, work to throw away | one at the end | no | no |
  | `light` | personal project | builder check, one at the end | the Architect's choice | one at the end |
  | `standard` | work that other people use | one for each wave (seams), one at the end | critical tests | one at the end |
  | `full` | product, risk area | one for each task, one for each wave | each new test | each task, and Security |

- `@decided` (2026-11-09) The levels are not decided on paper. They enter a release only after E1 runs on real work
  at each level. The table above is a starting point for E1, not a decision. The `sketch` level overlaps with the
  lab cycle; E1 decides if it stays.
- `@decided` (2026-11-09) R24 (one Executor and Reviewer cycle for each task) and R22 (QA for each task) depend on the
  level. At `full`: for each task. At `light`: one time, at the end of the integration. The laws do not change. The
  Reviewer reads the level from `.guilda/config.json`.
- `@decided` (2026-11-09) Until E1 runs, guilda has two levels: `light` and `full`. E1 runs on the Glasshaus project
  after the weekly usage reset of the user's accounts, because most accounts were near the weekly limit. The way to
  run it (one task in each level, or one task in all levels) is decided then.
- `@decided` The laws (R4, R18, R19, ARC6) run at each level. A level changes the gates and the cycle, never a law.
- `@decided` (2026-11-09, #2 finding 8) How much to verify follows the level. `light` stays as it is: all checks run
  one time, at the end. `full` keeps every check, and it uses the wait time: while the Reviewer and QA check task N,
  an Executor starts task N+1 or another independent part of the project.
- `@decided` (2026-11-09) No default level. `guilda:init` always asks: a prototype or personal project, or a product.
  It writes `light` or `full` from the answer.

- `@proposed` The glossary adds the term "field report" for the output of `guilda:report`, apart from the reports

### D4 — QA report parser `@decided`

A scenario line at column 0 with a colon (`1. Login works: PASSED - ...`) ends the `Scenarios` section, so a valid
report is rejected (#6, `scripts/lib/formats.mjs`). The fix: a line ends the section only if it is not a scenario
line, and an unindented continuation line stays in its scenario.

### D7 — Mutants `@decided`

- `@decided` ARC9 (#5): each new test has one named mutant of the product code that makes the test fail. Required in
  `full`. The Architect's choice in `light`.
- `@decided` Classification (#10): the Reviewer classifies each surviving mutant as killed, survived (weak test) or
  equivalent (with the reason). An equivalent mutant is noted, and it does not go to a fix round. A kill counts only
  if the assertion that fails targets the mutant.

### D8 — Reviewer `@decided`

- `@proposed` A spec review mode (#13). It has its own checklist: testable scenarios, tags, contracts, owners.

### D23 — Decisions go through the question tool `@decided`

The user decided this on 2026-11-09, after a decision asked at the end of long replies was not seen five times.

- `@decided` The Architect asks each pending decision with the question tool of the host. In Claude Code, the
  question tool is `AskUserQuestion`, with options to select or a free answer. One decision at a time (ARC1).
- `@decided` A decision is never only in the text of a long reply. A decision is never in the middle of a
  discussion. The reply can explain; the decision goes in the question tool.
- `@decided` A request for permission to continue is not a decision. The Architect asks the decision itself.
- `@decided` (2026-11-09) Each question carries its context in the question itself, because the question tool can
  hide the reply text:
  1. Where: the part of the system. If the topic changed, the question says so.
  2. What: the problem or the conflict, in plain words.
  3. A concrete scenario: when it happens in practice, with an example.
  4. The effect of each option, in the description of the option.
  5. The recommendation first (R13).
- `@decided` The Architect adapts the question to the level of the user. It explains a technical term the first time,
  or it does not use the term. If an answer shows that the user did not understand, the Architect asks again in
  simpler words. It does not repeat the same question.
- `@proposed` A setting `explain: "brief" | "full"` in `.guilda/config.json`. `brief`: short questions for an
  experienced user. `full`: the full context. `guilda:init` asks it.
- `@proposed` ARC1 changes to this text: "Ask each decision of the user in the question tool, one at a time, and
  follow R13 for the form of each question."

### D12 — Agent identity and questions after the work `@open`

The user proposed this on 2026-11-09. Each agent gets an identifier, and each task records the identifier of its

### D14 — Agent queue in code `@proposed`

The user proposed this on 2026-11-09. The flow must not live only in the context of the agent that orchestrates.

- `@proposed` A state file `.guilda/queue.json`. Each task has its ID, dependencies, owner role, agent ID and state:
  `pending`, `running`, `review`, `done`, `failed`, `stalled`.
- `@proposed` Hooks change the state. A dispatch sets `running` (PostToolUse on the Agent tool). The end of the
  agent sets `review` (SubagentStop). The Architect sets the other states.
- `@proposed` A script reads the queue and prints the next tasks whose dependencies are done.
- Limit: a hook cannot start an agent. The queue is the source of truth and the check of the flow. It does not run
  the agents.
- `@decided` (2026-11-09) One writer: only the orchestrator writes the queue. Until the orchestrator exists (0.3.0),
  the Architect writes it. Hooks and other agents never write it.
- `@decided` (2026-11-09) A state changes only on a signal from the agent: `running` when the agent says that it
  started, `review` when it delivers its report. The writer does not infer a start from a dispatch. This replaces
  the hook-driven states above, and the hook-order question of the builder check.
- `@decided` (2026-11-09) Use the known patterns of job queues (lease, heartbeat, visibility timeout, retry,
  concurrency limit) and, if one fits, an existing tool. Research runs now.
- Research result, 2026-11-09 (SQS visibility timeout, Temporal heartbeats and retries, BullMQ stalled jobs, the
  single-writer principle, event sourcing; tools `nq`, task-spooler, GNU parallel, `node:sqlite`; Claude Code agent
  teams; the user's local agent chat project). Proposal:
  - `@proposed` Files: `.guilda/queue/journal.jsonl` (append-only, the orchestrator is the only writer),
    `.guilda/queue/state.json` (derived, written by temp file and rename), `.guilda/queue/signals/<task>/<attempt>/`
    (`started`, `heartbeat`, `done`, `failed`, each written only by its worker), and a `lock` file (process ID and
    session of the orchestrator).
  - `@proposed` Transitions: `pending` to `ready` when all dependencies are `done`; `ready` to `dispatched` when a
    slot is free; `dispatched` to `running` on the `started` signal; `running` to `done` or `failed` on the signal;
    to `stalled` when no `started` comes in the ack timeout, or no heartbeat in the lease timeout; `stalled` to
    `running` on a new heartbeat; `failed` or `stalled` to `ready` with the attempt number plus one, by a decision;
    to `dead` when the attempts are used up.
  - `@proposed` `stalled` never dispatches the task again by itself. A retry uses a new attempt ID and its own
    worktree or branch, so that a repeated run does not damage the work of the earlier run.
  - `@proposed` Recovery after a restart: take the lock (record a takeover if the old owner is dead), replay the
    journal (skip a last partial line), turn new signal files into events, check the timeouts again.
  - `@proposed` JSONL, not SQLite: `node:sqlite` is still experimental in Node 24.
  - Not used: task-spooler (it starts a server), Claude Code agent teams' task list (many writers, experimental).
  - `@open` Lab before the build: an orchestrator that dies in the middle of an append, a worker that dies with no
    signal, a `done` signal after `stalled`, two orchestrators at the same time, reliable heartbeats from Codex and
    from subagents, atomic `rename` on the project file system.

### D15 — Orchestrator agent `@open`, not in 0.2

The user described the role on 2026-11-09 (second version, it replaces the first):

- `@proposed` The orchestrator comes after the Architect, not above it. The user talks to the Architect first, for
  the spec and the plan. Then the work goes to the orchestrator.
- `@proposed` The user talks only to the main session (plain Claude Code). The main session is the layer for open
  conversation. At the start it acts as the Architect. Later it tells the user what happens.
- `@proposed` The orchestrator runs in the background and does not talk to the user. Agents send their messages to
  the orchestrator, never to the main session. The orchestrator reports to the main session. A decision that belongs
  to the user goes up through the main session (R12).
- `@proposed` The orchestrator routes each message to the correct agent (D17 addresses).
- `@proposed` It keeps the flow running. It dispatches the next ready task of the queue (D14). It finds a stalled
  agent (#7), and resumes or replaces it.
- `@proposed` It runs other agents for the work. It does not write product code and does not review. A decision
  about the product still goes through the Architect and the Reviewer (R7, R12).
- `@proposed` It can run on another model. The queue, the addresses and the logs are in files that any model can
  read.
- `@open` The role name. The glossary forbids "orchestrator" (it means the controller).
- How the flow keeps running. Research on 2026-11-09 (Claude Code and Codex docs; not verified live yet):
  - No official mechanism makes an idle session act without a process or a scheduled trigger.
  - `/loop` (fixed or self-paced, with `ScheduleWakeup`) runs inside the open session, and it ends with the session.
    It expires after 7 days.
  - A `Stop` hook can block the end of a turn with a reason, up to 8 times in a row. It acts only at the end of a
    turn, so it is not a timer.
  - Messages between local Claude Code sessions (`SendMessage`) give an idle session a new turn. They do not reach
    Codex.
  - Codex has hooks (`Stop` can block), `AGENTS.md`, skills, MCP clients and `codex exec resume`. No push to an idle
    Codex was found.
  - Seen in this session: the completion notice of a background subagent started a new turn of the idle interactive
    session.
- `@proposed` The orchestrator is a Claude Code session with `/loop`. Each tick runs `guilda tick`: it reads the
  queue, finds ready and stalled tasks, and dispatches subagents or `codex exec resume`. No extra process. A `Stop`
  hook is a second guard: it blocks the end of a turn while a task is ready.
- `@proposed` Sleep in code, wake the model only for an action (the user's idea, 2026-11-09). A script `guilda watch`
  runs as a background command of the orchestrator session. Each 30 to 60 s it reads the queue, the bindings and the
  logs, with no model call. When the flow is healthy, it prints nothing. When a task is ready, an agent stalled or an
  agent failed, it prints one line and ends. The end notice wakes the orchestrator, which acts and starts the watch
  again. A healthy flow costs no tokens. This also covers the watchdog of #7.
- `@open` Lab before the build:
  - the `Stop` hook in interactive and `-p` mode;
  - `/loop` while the session is idle;
  - the token cost of each tick;

### D22 — Consumption and pace of work `@proposed`

The user asked on 2026-11-09 to set the pace of the work. The pace is the number of agents that run at the same
time. The pace comes from the tokens or the usage that is left on one or more accounts. It also comes from the hours
that the user wants for the work. Related: #3.

- `@proposed` Measure: the logs (D13) record the tokens of each agent and each task. Codex gives them in its
  `--json` output. Claude Code gives them in the transcript of each session.
- `@proposed` The code computes the pace and recommends a number of agents. It compares later samples with the plan
  and recommends a change. A recommendation states its assumptions and its uncertainty.
- `@decided` (from #3) Tokens are not shown as an exact share of a subscription. The plan never switches accounts by
  itself. (The rule "a running agent is never stopped to meet a number" was replaced on 2026-11-09, see D15.)
- `@proposed` By default the code only recommends. An automatic change of the number of agents needs a policy that
  the user turns on.
- `@proposed` A pace setting: fast, normal or slow, an optional deadline in hours, and a reserve. The code uses the work left
  in the queue, the resets and the pace. It recommends the number of agents now, and when to raise or lower it. It
  also gives an estimate of agent hours to finish.
- `@decided` The Architect sets the pace with the user, in the plan of the feature. The question is the same as for
  the process level (D1). It is: a prototype or a product, and how fast it must finish.
- `@decided` The orchestrator only executes the pace and tries to keep it. It does not decide the pace.
- `@decided` When an account reaches its limit, or comes near it, the orchestrator asks the Architect what to do. The
  Architect decides, for example: wait until an account resets, go slower, or pause work that is not urgent. The
  orchestrator executes the decision.
- `@decided` For this decision, the minimal `cswap` output gives two values for each account. The values are the
  usage in percent and the time to the next reset. Both values are for the 5-hour and the 7-day windows.
- `@decided` Before it asks, the orchestrator assesses the risk. It reads the tasks that run: how much of each is
  done and how heavy each is. It also reads the agent time that is left. It reads the usage and the reset times of the accounts.
  Then it asks the Architect one precise question, with the facts, two or three options and its recommendation.
- `@decided` The orchestrator asks in both directions:
  - Near a limit: for example, a heavy task is near its end and the accounts are near their 5-hour limit.
  - Under the pace: for example, the accounts will reset at 70% of their 5-hour limit, so capacity is lost. The
    Architect can then raise the pace.
- `@decided` guilda only monitors the accounts. It never asks `cswap` to switch. `cswap` keeps the usage values
  current by itself.
- `@proposed` Plan of the `cswap` fork, item "smart switching": keep the usage of all accounts even. Then one
  account does not reach its weekly limit while another stays at 30%. With smart switching, the orchestrator looks
  at the total capacity of all accounts up to each reset. It does not look at one account.
- `@proposed` Scenarios to specify (section 6), first list:
  1. A heavy task is near its end, with about 1 hour of agent work left. The accounts are near the 5-hour limit.
  2. A heavy task starts, and the accounts are near the limit.
  3. The accounts will reset at 70% of the 5-hour limit: the work is under the pace.
  4. All accounts are at the weekly limit, and only a 5-hour reset is near. A 5-hour reset does not give back
     weekly usage.
  5. One account resets in 40 minutes, and the others are near the limit.
  6. Uneven use, seen by the user in the week of 2026-11-09. Two accounts carried the light work of the week. Then
     heavy work used up the remaining accounts and left several at the weekly limit.
  7. The `cswap` data is old (its age is over a limit), or `cswap` is off.
- `@proposed` The panel (D20) shows the estimate of agent hours, with its range of uncertainty.
- The first estimate is rough. The plan price gives only an approximate ratio. Providers do not publish exact
  token limits (not verified). The estimate improves with the measured cost of each task.
- `@open` The terms of use of each provider for the use of more than one account. Not verified.
- `@decided` Usage source: the user's fork of `cswap` (claude-swap). The fork gets a separate plan, in its own
  repository. It adds one minimal command for guilda, for example `cswap pace --json`. guilda never uses
  `cswap list --json`, because that output has too much personal data.
- `@proposed` The minimal output has these values for each account:
  - the slot number or alias;
  - the 5-hour and the 7-day usage in percent, with the reset time;
  - ahead of pace (yes or no);
  - lasts to the reset (yes or no);
  - the projected end time;
  - the age of the data;
  - the `auto` and threshold settings.

  No email, no organization name or ID, no login data, no token.
- `@decided` guilda keeps only these values. It never writes account data to a log, a report or a field report
  (D3).
- `@decided` The goal of the orchestrator with these values: a constant flow of work. It does not pass a limit,
  and it does not stand still. It does not use less than it can to finish the work in the time that the user wants.
  The user's intent (fast, normal, slow, deadline) sets the target.
- `@decided` guilda never runs `cswap switch`. Switching stays with `cswap` and the user's settings.
- `@decided` Without `cswap`, or with the setting `usage.source: "off"` in `.guilda/config.json`, the function is off.
  guilda does not ask for values and does not warn about pace. It works as 0.1.0 does. There is no manual account list.
- `@proposed` A skill (for example `guilda:pace`) talks with the user about pace and deadline with these values.
- `@open` A usage source for Codex accounts. Its `--json` output gives tokens for each run, not a share of a limit.
- `@proposed` The limit of agents that run at the same time counts every agent. It counts each role, each external
  tool, and each side task that the user starts (a fork). From #11: the user set a limit of 3 that counted all of them, and the
  load became predictable.

### D17 — Agent addresses and messages outside the runtime `@proposed`

The user proposed this on 2026-11-09. Messages between agents do not depend on one runtime, so that agents of other
tools and models can take part.

- `@proposed` **Address.** Each dispatch gets a code, for example `T3-exe-7f2a`: task, role, short random part. The
  agent receives the code in its brief, and it is that code for the life of the task.
- `@proposed` **Binding table.** A file maps each code to the agent that runs now. The entry is the Claude Code agent ID,
  or the session of another tool. The code stays the same when the agent changes. If an agent stopped and cannot
  resume, a new agent takes the code. The new agent gets the ledger and the earlier transcript as its context.
- `@proposed` **Mailbox.** One append-only JSONL file for each code in `.guilda/bus/`. A message has: ID, from, to,
  task, type, text, and the ID of the message that it answers.
- `@proposed` **Router.** An agent does not wake up on a new message. A router reads the mailbox and resumes the bound
  agent. For Claude Code, the router uses `SendMessage` or `claude --resume`. For another tool, it uses an adapter. A busy agent gets its
  messages one at a time, in order.
- `@proposed` **Reply contract.** Each message gets a reply to its sender. A `SubagentStop` hook checks that the final
  answer has the reply format. If the answer does not have the format, the hook sends the agent back once. The exit
  code is 2, as for the verdict format.
- `@proposed` 0.2 builds the format, the file mailbox and the Claude Code adapter. Adapters for other tools come with
  D15.
- Known cost: each resume makes the context of the agent larger. After many messages, a new agent takes the code.
  E2 measures this.
- `@open` A local MCP server as the bus, in place of files or on top of them. Not verified: MCP support in other tools.
- `@open` Prior work of the user: a local project that connects agents through an MCP server. Read how it solves
  addresses and delivery before the D17 build.

### D18 — Agent life cycle: no agent left running `@proposed`

The user asked on 2026-11-09 for four things. Start and stop each agent under control. Leave no process of any tool
running. Keep the queue and the messages in one system. Make no change that a user of plain Claude Code can see.

- `@proposed` **An idle agent is a file, not a process.** An agent runs as a process only while it works on a
  message. Then the process ends. Between messages, the agent is its address and its session ID in `.guilda/`. A new
  message resumes that session.
- `@proposed` **One store.** One system in `.guilda/` holds the queue (D14), the addresses and the binding table
  (D17). It also holds the mailboxes and the audit log (D13). Git ignores `.guilda/`.
- `@proposed` **No daemon and no change outside the project.** No service, no global install, no change to user
  settings. Adapters for other tools are off unless `config.json` turns them on.
- `@proposed` **A limit for each run.** Each run of an external agent has a timeout. The binding table records each
  process. A clean-up at session start and at session end stops each process whose run is over. One command stops all
  agents of the project.
- `@proposed` **Visible runs.** Claude Code subagents show as now. A run of another tool starts as a background
  command of the Claude Code session. Then the user sees the run, and the session gets a notice when the run ends.
- `@proposed` **No tool edits the process of another tool.** Agents of other tools use the mailbox files.
- Lab result, 2026-11-09 (`docs/labs/2026-11-09-agent-bus.md` on branch `lab/agent-bus`): the concept is viable.
  It is not approved for the build yet, because most checks ran one time and no failure case ran.
  - Single run and resume: PASS for Codex (`codex exec resume`) and Claude Code (`claude -p --resume`). No process
    stayed alive.
  - Message exchange through the file mailbox: PASS in one exchange, Claude to Codex and back.
  - Session-end hook: PASS, 6 of 6 `claude -p` runs. Interactive sessions not tested.
  - Background command at session end: `claude -p` waits for its background commands, and stops them on SIGTERM.
    SIGKILL not tested, so the D18 clean-up stays.
  - Visible run in the user interface: partial. The user saw a Claude agent. Nothing showed that Codex ran (D20).
- `@proposed` From the lab lessons:
  - A routed turn starts the agent with no tools (`--tools "" --strict-mcp-config`). Local message tools can take
    the place of the router.
  - A routed agent does not start background commands, because they block the delivery until the timeout.
  - A message of type `ack` is stored, but the router does not deliver it.
  - Codex runs with stdin from `/dev/null`.
- `@open` Before the build: more runs and the failure cases. Two messages at the same time, a timeout, a failed
  child, Codex as the sender, an interactive session, SIGKILL.
- `@proposed` A lesson from the panel lab: a Codex run read extra files by itself. It used about 115,000 tokens
  for a task of 3 commands. The Codex adapter runs Codex with options that stop extra loads, for example `--ignore-rules` or
  `--ignore-user-config`. Verify their effect in a lab.

## 4. Experiments

The user asked on 2026-11-09 to decide these items by experiment, not by preference. Each experiment runs in
`guilda:lab` or with the Reviewer evaluation of planted defects (design section 7).

### E1 — Process levels

- Run the same feature at each level of D1.
- Measure: defects found before merge, defects found after merge, tokens, time, user interventions.
- Output: the gates of each level, and the default level.

### E2 — Persistent agent identity

Question: compare an address bound to the same agent (D17), with the same context ("Reviewer-1" for many tasks), with
a fresh agent for each task. Does the bound agent give better quality or a smaller context cost?

- Run the same wave with a pool of reused Reviewers and with fresh Reviewers. Use planted defects in the tasks and
  between the tasks (seams, helper drift).
- Measure: planted defects found in tasks and in seams, tokens, time, context compactions.
- Known risks of reuse: less cold reading, one error repeated in all tasks, a full context window, less parallel work.
- Output: keep fresh agents, use a pool, or a mix. No claim of a gain before the result.
