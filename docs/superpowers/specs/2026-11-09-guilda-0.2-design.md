# guilda 0.2 — design

Status: draft, in requirements. Not approved (R3).
Version target: 0.2.0, a minor release (new rules, a new skill, no core rule removed).
Sources: issues #2 to #13 of this repository, and the evidence that they cite.

Tags (ARC2): `@decided` = the user approved it. `@proposed` = the Architect's proposal, not approved yet.
`@open` = a question for the user.

## 1. Intent

Field use of 0.1.0 in three projects showed four problems:

- The law rules did not run in two sessions, and nothing told the user (#2, #11).
- The process is too heavy for small and personal projects (#2, #13, the user's notes).
- Specs and briefs had gaps. The Executor or the Reviewer found them late. Each gap cost about one task cycle
  (#2, #4, #5, #8, #9).
- A field report from a project reaches this repository only when someone writes it by hand (#12).

0.2 fixes these problems. It also fixes one parser defect (#6).

## 3. Decisions

### D1 — Process levels `@decided`, values by experiment E1

`.guilda/config.json` gets a field `process`. The user asked for four levels on 2026-11-09, and for an experiment
that sets what each level does (E1).

- `@proposed` The four levels:

  | Level | Use | Review | Mutants | QA |
  |---|---|---|---|---|
  | `sketch` | prototype, work to throw away | one at the end | no | no |
  | `light` | personal project | builder check, one at the end | the Architect's choice | one at the end |
  | `standard` | work that other people use | one for each wave (seams), one at the end | critical tests | one at the end |
  | `full` | product, risk area | one for each task, one for each wave | each new test | each task, and Security |

- `@decided` The laws (R4, R18, R19, ARC6) run at each level. A level changes the gates and the cycle, never a law.
- `@open` The default value that `guilda:init` writes.

### D2 — Activation check `@decided`

A hook cannot warn when the plugin did not load, so the warning comes from a file that loads without the plugin.

- `@proposed` `guilda:init` adds a short block to the project `CLAUDE.md`: "This project uses guilda. If no
  `guilda:*` agent exists in this session, stop and tell the user that guilda is off."
- `@proposed` A `guilda:doctor` skill reports: plugin loaded, hooks live, `guilda:*` agents present, project files
  present, version. Each item is PASS, FAIL or UNKNOWN with its evidence.
- `@proposed` The README says that a project-scope install loads only when Claude Code starts in that project folder.
- `@proposed` The Architect confirms that the `guilda:*` agents exist before the first dispatch of a session.

### D3 — `guilda:feedback` `@decided`

The user runs `/guilda:feedback`. A subagent collects the evidence and drafts a field report in the format of #2 and
#11. The skill asks the user for their own text, shows the final report, and sends it to this repository only after
the user approves. Full behavior in #12.

Safety, required (`@decided`):

- This repository is public. Anonymize by default: replace project names, routes, domain terms, paths, people and
  business data with generic terms. The user can turn this off for one report.
- Run the R19 scan on the final text. A hit blocks the send.
- No whole files, transcripts, logs or diffs in a report.
- Show each issue and each comment in full. Send it only after the user says yes (R12).
- Without `gh`, without a login, or on an error: save the report in `.guilda/feedback/` and send nothing.

### D4 — QA report parser `@decided`

A scenario line at column 0 with a colon (`1. Login works: PASSED - ...`) ends the `Scenarios` section, so a valid
report is rejected (#6, `scripts/lib/formats.mjs`). The fix: a line ends the section only if it is not a scenario
line, and an unindented continuation line stays in its scenario.

### D5 — Brief check and brief fields `@decided`

- `@proposed` The ARC6 hook also validates a brief file. For a prompt with a `Brief file: <path>` line, the hook
  checks the text of that file.
- `@proposed` The hook also checks a dispatch of another agent type when the prompt has a `Role: executor` line.
- `@proposed` New brief fields: `Decisions:`, `Mutants:`, `Conflict cases:` (#5) and `Base commit:` (#13). They are
  optional in 0.2, so that existing briefs stay valid.
- `@open` Is the new field `Base commit:` required, or optional?

### D6 — Concrete specs `@decided`

- `@proposed` ARC7, ARC8 and ARC10 as written in #5. They ask for exact scenarios, one owner task for each
  `@decided` item, and a glossary entry for each new term. The EF-system project used the same rules as a project rule, with evidence of value.
- `@proposed` A builder check before approval (#4): a fresh subagent reads the spec cold and lists its guesses. The
  Architect sorts them into three piles: answered already, minor, the user's.
- `@proposed` A ruling that changes behavior enters the spec in the same step, before the Executor continues. The
  ledger only points to it (#2 finding 4).
- `@proposed` Rule IDs and decision IDs are unique in a project. In one project, "P5" named a rule and a spec decision.
- `@proposed` `guilda:init` writes a skeleton `GLOSSARY.md`.

### D7 — Mutants `@decided`

- `@decided` ARC9 (#5): each new test has one named mutant of the product code that makes the test fail. Required in
  `full`. The Architect's choice in `light`.
- `@decided` Classification (#10): the Reviewer classifies each surviving mutant as killed, survived (weak test) or
  equivalent (with the reason). An equivalent mutant is noted, and it does not go to a fix round. A kill counts only
  if the assertion that fails targets the mutant.

### D8 — Reviewer `@decided`

- `@proposed` Checklist additions from #10:
  - No secret stays in a client cache, the URL, storage or logs.
  - Assertions are anchored.
  - Fixtures have a record that each filter must reject.
  - The diff has no generated artifacts.
  - The Executor report gives the exit code.
- `@proposed` A spec review mode (#13). It has its own checklist: testable scenarios, tags, contracts, owners.
  Its verdict has the line `Stage: spec`. It does not count toward the R11 rejection limit.

### D9 — Parallel waves `@decided`

Text rules in the Architect procedure, with no new script in 0.2:

- `@proposed` The plan has a producer/consumer table. Each interaction between tasks is one row. Each row names
  the task that writes the join test (#8).
- `@proposed` A foundation-fix path (#8). A task can find a bug in a shared part that it does not own. Then it
  makes no local workaround. The Architect decides where the fix goes and the merge order.
- `@proposed` A shared-helper forecast before a wave, and a `guilda:consolidate <name>` marker for a temporary copy
  (#9).
- `@proposed` The foundation task adds the ignore entries of each tool that it adds (#8).
- `@proposed` Each brief asks for a `timeout` on long commands and a commit for each green item (#7).

### D10 — Role fixes `@decided`

- `@proposed` Merges and conflicts go to `version-control`, after the user approves the merge (#2 finding 6).
- `@proposed` `QA: covered by review` when each Acceptance scenario names a check that the Reviewer already ran
  (#2 finding 7).
- `@proposed` The Executor, QA and the Reviewer never publish or share anything outside the worktree (#2 finding 9).
- `@proposed` EXE2 becomes "show the new test failing against the old code" (#13 finding 5).
- `@proposed` Each dispatch states the reply language of `config.languages` (#13 finding 6).
- `@proposed` ARC4 fallback (#13 finding 4). If the model of a tier is not available, use one tier lower.
  Tell the user.

### D11 — `lint-rules` and formatters `@decided`

- `@proposed` `lint-rules` accepts a blank line after a rule title and between the `Rule:`, `Why:` and `Check:`
  lines.
- `@proposed` `guilda:init` detects a formatter in the project and proposes an ignore entry for `.guilda/`.

### D12 — Agent identity and questions after the work `@open`

The user proposed this on 2026-11-09. Each agent gets an identifier, and each task records the identifier of its
Executor. The Reviewer and the Architect can then ask that Executor why it did something.

Research on 2026-11-09, from the Claude Code docs (hooks, sub-agents). Not verified live yet:

- The `PostToolUse` input of the Agent tool has `tool_response.agentId`, also for a background dispatch. The
  `PreToolUse` input does not have it.
- `PreToolUse` and `PostToolUse` inside a subagent get `agent_id` and `agent_type`. `SubagentStop` also gets
  `agent_transcript_path`.
- `SendMessage` with the agent ID resumes a finished subagent with its full history.
- A subagent can send a message to another subagent if it has the `SendMessage` tool. It can address only the names
  that existed when it started.
- A subagent that the user stopped cannot be resumed.

Proposal:

- `@proposed` A `PostToolUse` hook on the Agent tool records the task ID and the agent ID in `.guilda/agents.jsonl`.
  The task ID comes from the `ID / title:` line of the brief.
- `@proposed` The Reviewer writes its questions in a `Questions:` section of the verdict. The Architect sends each
  question to the Executor with `SendMessage`, and adds the answer to the review. No agent sends a message to another
  agent directly, so the ledger keeps each question and each answer.
- `@open` Direct questions from the Reviewer to the Executor, without the Architect. Possible, but the record is
  then only in the transcripts.

### D13 — Audit log of the agents `@open`

The user proposed this on 2026-11-09. A record of what each agent did: the tool calls, the files it changed, the
commands it ran.

Research on 2026-11-09, from the Claude Code docs. Not verified live yet:

- Claude Code keeps the full transcript of each subagent. It deletes it after `cleanupPeriodDays`, 30 days by
  default.
- OpenTelemetry can export each tool call with `agent_id`. It needs telemetry settings and an exporter.

Proposal:

- `@proposed` A `PostToolUse` hook writes one line for each tool call of a subagent to `.guilda/audit.jsonl`.
  The line has the time, the agent ID, the task ID, the tool, and the changed file path or the first word of the
  command. No command text and no file content, so
  no secret enters the log (R19).
- `@proposed` On `SubagentStop`, the hook records the path of the agent transcript, so a reader can find the full
  record.
- `@open` Copy the transcripts of a task into the project before the 30 days end, or not.

### D14 — Agent queue in code `@proposed`

The user proposed this on 2026-11-09. The flow must not live only in the context of the agent that orchestrates.

- `@proposed` A state file `.guilda/queue.json`. Each task has its ID, dependencies, owner role, agent ID and state:
  `pending`, `running`, `review`, `done`, `failed`, `stalled`.
- `@proposed` Hooks change the state: a dispatch sets `running` (PostToolUse on the Agent tool), the end of the agent
  sets `review` (SubagentStop). The Architect sets the other states.
- `@proposed` A script reads the queue and prints the next tasks whose dependencies are done.
- Limit: a hook cannot start an agent. The queue is the source of truth and the check of the flow. It does not run
  the agents.

### D15 — Orchestrator agent `@open`, not in 0.2

The user proposed this on 2026-11-09: an agent one level above the Architect. It tells the user what happens and what
is done, and it can talk to other agents. It can be another model, for example one with a voice interface.

- `@proposed` 0.2 builds the base: the queue (D14) and the audit log (D13) in a format that any model can read.
- `@open` The role name. The glossary forbids "orchestrator" (it means the controller). The new role sits above
  the controller, so it needs its own glossary term.
- `@open` A separate spec for the orchestrator, after 0.2. Not verified: whether an agent of another tool can send a
  message to a Claude Code subagent.
- `@proposed` The orchestrator can report without review. A decision about the product still goes through the
  Architect and the Reviewer (R7, R12).

### D16 — Security team `@proposed`

The user proposed this on 2026-11-09. The Security role becomes `security-lead`, with two new roles.

- `@proposed` `security-lead`: the current Security role. It points, never edits, and gives work to the two teams.
- `@proposed` `red-team`: shows that a weakness can be used. Its output is a failing test that reproduces the attack.
- `@proposed` `blue-team`: fixes the weakness and hardens the code, as an Executor in the risk area.
- `@proposed` Red team rules, as laws where a hook can check them:
  - Only the code of this project, in a local test environment.
  - Never an outside target: no host, address or service that the project does not own.
  - Never a real credential, and no persistence or data copy out of the test environment.
  - Only for a task whose brief has a risk area, and only after the user approves.
- `@proposed` Only at the levels `standard` and `full`.

### D17 — Agent addresses and messages outside the runtime `@proposed`

The user proposed this on 2026-11-09. Messages between agents do not depend on one runtime, so that agents of other
tools and models can take part.

- `@proposed` **Address.** Each dispatch gets a code, for example `T3-exe-7f2a`: task, role, short random part. The
  agent receives the code in its brief, and it is that code for the life of the task.
- `@proposed` **Binding table.** A file maps each code to the agent that runs now: the Claude Code agent ID, or the
  session of another tool. The code stays the same when the agent changes. If an agent stopped and cannot resume, a
  new agent takes the code, with the ledger and the earlier transcript as its context.
- `@proposed` **Mailbox.** One append-only JSONL file for each code in `.guilda/bus/`. A message has: ID, from, to,
  task, type, text, and the ID of the message that it answers.
- `@proposed` **Router.** An agent does not wake up on a new message. A router reads the mailbox and resumes the bound
  agent: `SendMessage` or `claude --resume` for Claude Code, an adapter for another tool. A busy agent gets its
  messages one at a time, in order.
- `@proposed` **Reply contract.** Each message gets a reply to its sender. A `SubagentStop` hook checks that the final
  answer has the reply format, and sends the agent back once if it does not (exit 2, as for the verdict format).
- `@proposed` 0.2 builds the format, the file mailbox and the Claude Code adapter. Adapters for other tools come with
  D15.
- Known cost: each resume makes the context of the agent larger. After many messages, a new agent takes the code.
  E2 measures this.
- `@open` A local MCP server as the bus, in place of files or on top of them. Not verified: MCP support in other tools.

### D18 — Agent life cycle: no agent left running `@proposed`

The user asked on 2026-11-09: start and stop each agent under control, leave no process of any tool running, keep
the queue and the messages in one system, and make no change that a user of plain Claude Code can see.

- `@proposed` **An idle agent is a file, not a process.** An agent runs as a process only while it works on a
  message. Then the process ends. Between messages, the agent is its address and its session ID in `.guilda/`. A new
  message resumes that session.
- `@proposed` **One store.** The queue (D14), the addresses and the binding table (D17), the mailboxes and the audit
  log (D13) are one system in `.guilda/`, which git ignores.
- `@proposed` **No daemon and no change outside the project.** No service, no global install, no change to user
  settings. Adapters for other tools are off unless `config.json` turns them on.
- `@proposed` **A limit for each run.** Each run of an external agent has a timeout. The binding table records each
  process. A clean-up at session start and at session end stops each process whose run is over. One command stops all
  agents of the project.
- `@proposed` **Visible runs.** Claude Code subagents show as now. A run of another tool starts as a background
  command of the Claude Code session, so that the user sees it and the session gets a notice when it ends.
- `@proposed` **No tool edits the process of another tool.** Agents of other tools use the mailbox files.
- Lab result, 2026-11-09 (`docs/labs/2026-11-09-agent-bus.md` on branch `lab/agent-bus`): the concept is viable.
  It is not approved for the build yet, because most checks ran one time and no failure case ran.
  - Single run and resume: PASS for Codex (`codex exec resume`) and Claude Code (`claude -p --resume`). No process
    stayed alive.
  - Message exchange through the file mailbox: PASS in one exchange, Claude to Codex and back.
  - Session-end hook: PASS, 6 of 6 `claude -p` runs. Interactive sessions not tested.
  - Background command at session end: `claude -p` waits for its background commands, and stops them on SIGTERM.
    SIGKILL not tested, so the D18 clean-up stays.
  - Visible run in the user interface: partial. The user saw a Claude agent. Nothing showed that Codex ran (D20).
- `@proposed` From the lab lessons:
  - A routed turn starts the agent with no tools (`--tools "" --strict-mcp-config`). Local message tools can take
    the place of the router.
  - A routed agent does not start background commands, because they block the delivery until the timeout.
  - A message of type `ack` is stored, but the router does not deliver it.
  - Codex runs with stdin from `/dev/null`.
- `@open` Before the build: more runs and the failure cases. Two messages at the same time, a timeout, a failed
  child, Codex as the sender, an interactive session, SIGKILL.

### D20 — Agent panel as a terminal mod `@proposed`

The user proposed this on 2026-11-09, after lab check L6: a Codex run showed only as a Claude agent.

- `@proposed` A Claude Code mod reads the queue (D14) and the binding table (D17) on a timer, and shows:
  - a pane with each agent: address, tool (Claude or Codex), state, time since the last activity;
  - a band above the prompt with a short count, for example "2 Claude, 1 Codex running";
  - a short notice when an agent ends or stalls;
  - a label on the tool row of an external run, with the name of the tool.
- `@proposed` The mod is a second plugin in the guilda marketplace (`guilda-panel`). Not verified: whether one plugin
  can hold both command hooks and a mod module.
- Limits from the mod docs of Claude Code 2.1.321: a pane opens without a request only in a wide terminal (about 110
  to 144 columns or more). The mod API has a timer and file reads, but no file watch.
- `@proposed` A user without the mod sees no change.
- Lab result, 2026-11-09 (`docs/labs/2026-11-09-agent-panel-mod.md` on branch `lab/agent-panel`): viable. The user
  saw a live row for a Codex agent and accepted the layout.
  - `@decided` Rows under the prompt with a dim heading `other models`, marker `◇`, label `guilda:<role>-<tool>`
    (for example `guilda:executor-codex`), the task title, and on the right the time, the state and the tokens.
  - `@decided` Only agents from outside the conversation. Claude subagents of the session show in the native list.
  - `@decided` The address shows only in the detail view (`/guilda-agents`).
  - Limit: Claude Code 2.1.321 has no mod component inside or after the native agent list, so the rows show above
    it. A pane opens without a request only in a wide terminal.
  - Not verified: the hide after `done`, mouse hover and click (full screen only), the label on a tool row.

### D19 — Labs run in an agent `@decided`

The user decided this on 2026-11-09, for each place in guilda: a lab, an experiment or a spike always runs in a
dispatched agent. It never runs in the controller session.

- `@decided` The controller writes the hypothesis and the PASS criteria. Then it dispatches an agent with the lab
  brief. The agent runs the steps and writes the evidence. The controller reads the report and gives the verdict.
- `@proposed` A core rule with this text, cited by the Architect procedure, `guilda:lab` and the experiments of
  section 4.
- `@proposed` Check: a hook cannot see if a command is part of a lab, so the rule is a gate. The Reviewer rejects a
  lab report that has no agent ID of the agent that ran it.

## 4. Experiments

The user asked on 2026-11-09 to decide these items by experiment, not by preference. Each experiment runs in
`guilda:lab` or with the Reviewer evaluation of planted defects (design section 7).

### E1 — Process levels

- Run the same feature at each level of D1.
- Measure: defects found before merge, defects found after merge, tokens, time, user interventions.
- Output: the gates of each level, and the default level.

### E2 — Persistent agent identity

Question: does an address bound to the same agent (D17), with the same context ("Reviewer-1" for many tasks) give better quality or a smaller
context cost than a fresh agent for each task?

- Run the same wave with a pool of reused Reviewers and with fresh Reviewers. Use planted defects in the tasks and
  between the tasks (seams, helper drift).
- Measure: planted defects found in tasks and in seams, tokens, time, context compactions.
- Known risks of reuse: less cold reading, one error repeated in all tasks, a full context window, less parallel work.
- Output: keep fresh agents, use a pool, or a mix. No claim of a gain before the result.
