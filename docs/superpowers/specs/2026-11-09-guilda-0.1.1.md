## Branch

0.1.1 is a patch of 0.1.0. Cut its branch from the tag `guilda--v0.1.0`, not from `feat/0.2`. `feat/0.2` holds
0.2.0 work that must not reach a 0.1.x install. Take each 0.1.1 change onto the new branch as its own commit.

### Files from `feat/0.2`

Only two files go from `feat/0.2` to the 0.1.1 branch:

| File | Take | Adapt |
|---|---|---|
| `scripts/changelog.mjs` | the dual-format parser: both `HEADING` forms, `versionOf`, `OTHER_HEADING`, `LINK_REFERENCE` | no change |
| `tests/changelog.test.mjs` | the tests of both heading forms and of the mixed form | the test "CLI defaults to the CHANGELOG.md of the plugin" expects the old heading form `## 0.1.1 — <date>`, because the 0.1.1 CHANGELOG keeps the old form |

With this change, `npm test` passes on the 0.1.1 branch with the old-form CHANGELOG.

These `feat/0.2` changes must not go to the 0.1.1 branch:

- `README.md`: the `skill-creator` dependency and the official marketplace line. The dependency is 0.2.0 (D28).
- `tests/manifest.test.mjs`: the "Keep a Changelog" heading match and the dependency tests. On 0.1.1 they fail.
- `CHANGELOG.md`, `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`: the 0.1.1 branch writes its own
  version and its own entry in the old heading form.

The README note of D2 is new text. The 0.1.1 branch writes it, and copies nothing from the `feat/0.2` README.

### The way back to `feat/0.2`

1. The user approves the merge of the 0.1.1 branch to `main` and the tag `guilda--v0.1.1`.
2. Merge `main` into `feat/0.2`.
3. On a conflict in `scripts/changelog.mjs`, `tests/changelog.test.mjs` or `.claude-plugin/plugin.json`, keep the
   `feat/0.2` text. The parser is the same, and the `feat/0.2` test expects the new heading form.
4. In `CHANGELOG.md` of `feat/0.2`, convert the 0.1.1 entry to the new form. The heading is `## [0.1.1] - <date>`.
   The changes go under `### Fixed`. Add a link reference `[0.1.1]`.
5. Run `npm test` on `feat/0.2`. `tests/manifest.test.mjs` and `tests/changelog.test.mjs` pass with the new form.

## Acceptance scenarios

Each scenario has the ARC7 shape: Given, When, Then, the QA tool, and the automatic test.

### S1 — A scenario line with a colon stays in the section (D4) `@decided`

- Given: a QA report whose `Scenarios:` section has the line `1. Login works: PASSED - the form logs in`.
- When: `scripts/lib/formats.mjs` validates the report.
- Then: the validation returns no error, and the scenario count is 1.
- Tool: `node --test`.
- Test: `tests/formats.test.mjs`, a case with a colon in the scenario title.

### S2 — An unindented continuation line stays in its scenario (D4) `@decided`

- Given: a QA report with a scenario line and a next line at column 0 that is not a scenario line and not a heading.
- When: the parser reads the report.
- Then: the continuation line belongs to the scenario above it, and the next section starts only at its own heading.
- Tool: `node --test`.
- Test: `tests/formats.test.mjs`, a case with an unindented continuation line.

### S3 — A real section heading still ends the section (D4) `@decided`

- Given: a QA report with a `Scenarios:` section and then an `Out of scope:` line.
- When: the parser reads the report.
- Then: the `Out of scope:` line is not part of any scenario.
- Tool: `node --test`.
- Test: `tests/formats.test.mjs`, the existing valid report cases still pass.

### S4 — `lint-rules` accepts blank lines from a formatter (D11) `@decided`

- Given: a rules file where a formatter put a blank line after each rule title and between the three rule lines.
- When: `node scripts/lint-rules.mjs` reads the file.
- Then: the exit code is 0, and each rule has its `Rule:`, `Why:` and `Check:` lines.
- Tool: `node scripts/lint-rules.mjs` on a fixture.
- Test: `tests/lint-rules.test.mjs`, a formatted fixture.

### S5 — `lint-rules` still rejects a missing line (D11) `@decided`

- Given: a formatted rules file where one rule has no `Why:` line.
- When: `node scripts/lint-rules.mjs` reads the file.
- Then: the exit code is not 0, and the output names the rule ID.
- Tool: `node scripts/lint-rules.mjs` on a fixture.
- Test: `tests/lint-rules.test.mjs`.

### S6 — The README states when a project-scope install loads (D2) `@decided`

- Given: the README of 0.1.1.
- When: a reader opens the install section.
- Then: the section says that a project-scope install loads only when Claude Code starts in that project folder.
- Tool: `grep` on `README.md`.
- Test: none. The Reviewer checks the text.

### S7 — The parser reads both heading forms `@decided`

- Given: a CHANGELOG with an entry `## 0.1.1 — <date>` and an entry `## [0.2.0] - <date>`.
- When: `changesBetween(changelog, "0.1.0", "0.2.0")` runs.
- Then: the result has both entries, newest first. `## [Unreleased]` and link references end an entry.
- Tool: `node --test`.
- Test: `tests/changelog.test.mjs`.

### S8 — A 0.1.0 install reads the 0.1.1 entry `@decided`

- Given: the `guilda:update` code of the tag `guilda--v0.1.0`, and the CHANGELOG of 0.1.1.
- When: the 0.1.0 parser reads the CHANGELOG.
- Then: it finds the 0.1.1 entry, because the 0.1.1 CHANGELOG uses the old heading form.
- Tool: `node` with the 0.1.0 `scripts/changelog.mjs` from `git show guilda--v0.1.0:scripts/changelog.mjs`.
- Test: a one-time check by QA; the result goes in the QA report.

### S9 — The laws run with no `.guilda/` folder (D40) `@decided`

- Given: a git project with no `.guilda/` folder, and a staged file with a token that the R19 scan finds.
- When: the pre-tool-use hook reads a `git commit` command.
- Then: the hook refuses the commit with the R19 reason. It prints one notice: "guilda without init: laws on,
  default process".
- Tool: `node --test`.
- Test: `tests/pre-tool-use.test.mjs`, a case with no `.guilda/` folder and a case with an invalid
  `.guilda/config.json`.

## Fail-closed laws (D40) `@decided`

The user approved this fix in the 0.1.1 scope on 2026-11-10. Today `scripts/hooks/pre-tool-use.mjs` returns early when
`.guilda/config.json` is missing or invalid, so the R19 scan is off when `guilda:init` failed. The fix uses safe
defaults and shows one notice. The 0.1.1 branch writes this fix itself; it takes no file from `feat/0.2`. Scenario: S9.
Files: `scripts/hooks/pre-tool-use.mjs`, `tests/pre-tool-use.test.mjs`.
