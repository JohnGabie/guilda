## Acceptance scenarios

Each scenario has the ARC7 shape: Given, When, Then, the QA tool, and the automatic test.

### S1 — A scenario line with a colon stays in the section (D4) `@decided`

- Given: a QA report whose `Scenarios:` section has the line `1. Login works: PASSED - the form logs in`.
- When: `scripts/lib/formats.mjs` validates the report.
- Then: `validateQaReport` returns an empty list. The 0.1.0 code returns `Scenarios section has no scenario` for
  the same report, because the colon line ends the section.
- Tool: `node --test`.
- Test: `tests/formats.test.mjs`, a case with a colon in the scenario title.

A section heading is a line at column 0 that starts with one label of the QA output format (`agents/qa.md`). The
labels are fixed. They are `Environment:`, `Tools:`, `Scenarios:`, `Phase 2 plan:`, `Phase 2 findings:`,
`States checked:`, `Persistence after reload:`, `Logs:`, `Out-of-scope notes (for the Architect):`,
`User must look:` and `Limits of this check:`. Any other line is not a heading. The parser keeps this list as one constant.

### S2 — An unindented continuation line stays in its scenario (D4) `@decided`

- Given: a QA report whose `Scenarios:` section has the line `1. Login works ->` and then, at column 0, the line
  `PASSED — output: 3 tests pass`. The second line has a colon, and it starts with no label of the list above.
- When: `validateQaReport` reads the report.
- Then: it returns an empty list, because the result on the second line belongs to scenario 1. The 0.1.0 code
  returns an error for scenario 1, because the second line ends the section.
- Tool: `node --test`.
- Test: `tests/formats.test.mjs`, a case with an unindented continuation line.

### S3 — A real section heading still ends the section (D4) `@decided`

- Given: a QA report whose `Scenarios:` section has the line `1. Login works ->` with no result, and then the line
  `Out-of-scope notes (for the Architect): PASSED — not a scenario`.
- When: `validateQaReport` reads the report.
- Then: it returns `Scenario 1: needs PASSED, FAILED or NOT VERIFIED, then a dash and evidence`. So the label line
  ended the section and did not give its result to scenario 1.
- Tool: `node --test`.
- Test: `tests/formats.test.mjs`, this case. The existing valid report cases still pass.

### S4 — `lint-rules` accepts blank lines from a formatter (D11) `@decided`

- Given: a rules file where a formatter put a blank line after each rule title and between the three rule lines.
- When: `node scripts/lint-rules.mjs` reads the file.
- Then: the exit code is 0, and each rule has its `Rule:`, `Why:` and `Check:` lines.
- Limit (the Architect's choice): at most one blank line before each of `Rule:`, `Why:` and `Check:`. So a block
  ends at most 6 lines after its heading. Two blank lines in a row are an error. `lintRules` in
  `scripts/lint-rules.mjs` skips these blank lines. Its `inBlock` set held the lines `i+1` to `i+3`. Now it holds
  the real lines of the block, at most `i+1` to `i+6`.
- Tool: `node scripts/lint-rules.mjs` on a fixture.
- Test: `tests/lint-rules.test.mjs`, a formatted fixture.

## Project layer states (D40) `@decided`

The user decided these states on 2026-11-10. In 0.1.0, `scripts/hooks/pre-tool-use.mjs` (line 122),
`scripts/hooks/pre-compact.mjs` (line 30) and `scripts/hooks/pre-agent.mjs` (line 10) return early when
`.guilda/config.json` is missing or invalid. So R4, R18, R19 and ARC6 are off exactly when `guilda:init` failed. A
law must fail closed. The 0.1.1 branch writes this fix itself; it takes no file from `feat/0.2`.

| State | How the hook sees it | Laws R4, R18, R19, ARC6 | Notice |
|---|---|---|---|
| no project layer | no `.guilda/` folder | do not run, as in 0.1.0 | none in 0.1.1 (R28 in 0.2.0) |
| broken project layer | a `.guilda/` folder, and `config.json` is missing, unreadable, not JSON, or fails `checkSchema` | run with the safe defaults | the session start notice |
| valid project layer | `loadConfig` returns `ok: true` | run with the config, as in 0.1.0 | as in 0.1.0 |

- Safe defaults: `scan.ignore` is `[]`, so the R19 scan reads each staged file. The four law hooks read no other
  config field (checked in the 0.1.0 code). (The Architect's choice.)
- `scripts/lib/project.mjs` gets one function, `projectState(projectDir)`. It returns `none`, `broken` with the
  reason and the safe defaults, or `valid` with the config. The three law hooks and the session start use it.
- Notice channel and frequency (the Architect's choice): the session start prints the notice in `additionalContext`.
  It prints it once per session, when the source is `startup` or `clear`. A law hook speaks only when it refuses: its deny reason
  or its stderr, as in 0.1.0. A hook prints nothing on a call that passes.
- The session start in a broken project layer loads no core rules, as in 0.1.0. The 0.2.0 spec changes this.
- `appendViolation` in `scripts/lib/violations.mjs` writes only when the `.guilda/` folder exists. It never creates
  that folder. A refusal in a project with no `.guilda/` folder records nothing.
- The gate hooks (`post-tool-use`, `subagent-start`, `subagent-stop`) keep the 0.1.0 behavior.
