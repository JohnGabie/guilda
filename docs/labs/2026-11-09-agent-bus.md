# Lab: agent bus and agent life cycle

Date: 2026-11-09. Branch: `lab/agent-bus`. Spec: `docs/superpowers/specs/2026-11-09-guilda-0.2-design.md`, D17 and D18.

## Hypothesis

Agents of two tools (Claude Code and Codex) can exchange messages through files in `.guilda/bus/`. A router
delivers each message by resuming the session of the agent. No agent process stays alive between messages, and a
session-end clean-up can stop what remains.

## PASS criteria (written before the run)

| ID | Check | PASS |
|---|---|---|
| L1 | Codex single run, then resume of the same session | The resumed run gives back a word that only the first run received. After each run, no new Codex process is alive. |
| L2 | Claude Code single run (`claude -p`), then resume of the same session | Same as L1, for Claude Code. |
| L3 | Message exchange through the file mailbox | A Claude agent sends a question to a Codex agent through `.guilda/bus/`. The router delivers it and the reply. Each message has its ID and the ID of the message that it answers. No new agent process is alive at the end. |
| L4 | Session-end hook | A `SessionEnd` hook of a plugin runs at the end of a `claude -p` session, 3 runs out of 3. |
| L5 | Background command and session end | A command that a `claude -p` session starts in the background is not alive after the session ends. If it is alive, record it: then the clean-up of D18 is required. |
| L6 | Visible run | A Codex run started as a background command of an interactive Claude Code session shows in the user interface. The user confirms. |

Processes of other projects that were alive before the run are not counted.

## Method

Run by a dispatched agent (D19). The controller ran L1, L2, L4 and the first L5 run. The dispatched agent ran L5
again and L3.

- All runs use a new lab directory, `<labdir>`, made with `mktemp -d`. No file is deleted.
- Models: `claude -p --model haiku` (L2, L3), `claude -p --model sonnet` (L5, it needs reliable tool use), Codex
  default model (L1, L3).
- Process checks compare PID sets before and after a run, not names. Two processes of another project were alive
  before the run. They are not counted and were not touched.
- L3 uses `labs/agent-bus/router.mjs` (Node, no dependencies). Commands: `create`, `deliver`, `show`.
  - Mailbox: `<labdir>/.guilda/bus/<address>.jsonl`, append-only. Message:
    `{id, from, to, task, type, text, reply_to, time}`.
  - Bindings: `<labdir>/.guilda/bindings.json`, address -> `{tool, session}`.
  - `deliver` takes the oldest pending message (no message has `reply_to` = its id), resumes the bound session
    with it, and appends the answer as a reply to the mailbox of the sender. Only the router writes files.
  - Each child has a 180 s timeout. The router records the child PID and checks that it is gone after the exit.
  - Claude agents run with `--tools "" --strict-mcp-config`: no tools, no MCP servers. Codex runs with
    `-s read-only`.

## Evidence

### L1: Codex run, then resume

- `codex exec --json --skip-git-repo-check -s read-only -C <dir> "Remember this code word: ZEBRA-41. Reply with only: OK"`
  -> `thread_id` 01a1c21a-…, reply `OK`, exit 0. Usage: 15509 input tokens (12288 cached).
- `codex exec resume --json --skip-git-repo-check <thread_id> "What code word..." < /dev/null` -> `ZEBRA-41`,
  same `thread_id`.
- No new Codex process after each run. 1 run.

### L2: Claude Code run, then resume

- `echo "<prompt>" | claude -p --model haiku --output-format json` -> `session_id` e0f7e5d7-….
- `claude -p --resume <id>` -> `HERON-77`, same session id. 0 new `claude` processes. 1 run.

### L3: message exchange through the file mailbox

Scenario, 1 run, addresses `T1-exe-a00f81` (Codex) and `T1-arc-a00f81` (Claude, haiku):

1. `router.mjs create <labdir> T1-exe-a00f81 codex "<address, role: executor> ... reply with only: READY"`
   -> `READY`, session 01a1c229-2e6a-…, child pid gone after.
2. `router.mjs create <labdir> T1-arc-a00f81 claude "<address, role: architect, ask T1-exe this question,
   confirm a reply with RECEIVED <number>>" --post-to T1-exe-a00f81 --task T1` -> the agent wrote the question.
   The router posted it as message `c227555e-…` (`reply_to: null`).
3. `router.mjs deliver <labdir> T1-exe-a00f81` -> Codex resumed (same session), answer `391`. Reply
   `2148e69d-…` with `reply_to: c227555e-…` in the mailbox of T1-arc.
4. `router.mjs deliver <labdir> T1-arc-a00f81` -> Claude resumed (same session), answer `RECEIVED 391`. Reply
   `7df14684-…` with `reply_to: 2148e69d-…` in the mailbox of T1-exe.

Mailboxes at the end (text cut):

{"id":"7df14684-…","from":"T1-arc-a00f81","to":"T1-exe-a00f81","task":"T1","type":"reply","text":"RECEIVED 391","reply_to":"2148e69d-…"}

- 4 child processes (2 Codex, 2 Claude). Each one: exit 0, not alive after its exit.
- PID set after the run, compared with before: no new `claude`, `codex` or `node` process.
- Each Codex turn took about 4 s.
- An earlier attempt failed (kept as evidence in `<labdir>/l3`). Without `--tools ""`, the Claude agent had a
  built-in peer-message tool of the local setup. It tried to send the question itself, did not find the address,
  and wrote an explanation. The router posted that text as the question. Fix: the Claude agent gets no tools.
  `--tools ""` then gave `tools: []` and `mcp_servers: []` in the init event.

### L4: SessionEnd hook

- Plugin `labs/agent-bus/end-plugin`: a `SessionEnd` hook appends `{reason, session}` to
  `$CLAUDE_PROJECT_DIR/session-end.log`.
- 3 valid `claude -p --plugin-dir` runs, plus 3 runs that failed on a bad CLI argument. The hook ran 6 of 6.
  `reason` was `other` each time.

### L5: background command and session end

Prompt (sonnet, `--allowedTools Bash`): step 1, start `sh -c 'echo $$ > bg.pid; exec sleep N'` with
`run_in_background`. Step 2, in a separate Bash call: `kill -0 $(cat bg.pid) && echo ALIVE-INSIDE-<pid>`. Step 3,
reply with that output. After the session ends, check the PID.

| Run | N | Alive inside | Session end | Alive after |
|---|---|---|---|---|
| Controller run | 600 | not proven | ended | no (3 s after) |
| 1 | 600 | yes (`ALIVE-INSIDE-653738` in transcript) | did not end. Killed by `timeout 240` (exit 124) | no |
| 2 | 600 | yes (`ALIVE-INSIDE-656401` in transcript) | did not end. Killed by `timeout 240` (exit 124) | no |
| 3 | 45 | yes (`ALIVE-INSIDE-658511`) | ended by itself after 55 s, exit 0 | no |

- Runs 1 and 2: the model replied `ALIVE-INSIDE-…` in about 10 s. Then `claude -p` waited for the background
  task. On SIGTERM it stopped the task: the transcript has a task notification with `<status>killed</status>`.
- Run 3: `claude -p` waited until `sleep 45` ended, took the task notification as a new turn, answered again, then
  exited. The final `result` is the answer to the notification, not the answer to the prompt.
- No `kill` by the lab was needed.

### L6: visible run

Not run by the dispatched agent. It needs an interactive session and the user.

## Verdict

| ID | Verdict | How proven | Not tested |
|---|---|---|---|
| L1 | PASS | 1 run and 1 resume | More runs. Codex `resume` with `-C` or a sandbox flag. |
| L2 | PASS | 1 run and 1 resume | More runs. |
| L3 | PASS | 1 full exchange, both ways. IDs and `reply_to` correct. No new agent process at the end. | Two messages at the same time. A timeout. A failed child. Codex as the sender. |
| L4 | PASS | 6 of 6 runs (3 valid, 3 failed on CLI arguments), `reason: other` | Interactive sessions. `/exit`, Ctrl-C, other reasons. |
| L5 | PASS, with a condition | 3 runs by the agent + 1 by the controller. The command was alive inside (3 runs) and not alive after the process ended (4 runs). | Interactive sessions. SIGKILL of `claude`. A command that ignores SIGTERM or starts its own process group. |
| L6 | PARTIAL | 1 run (about 66 s) by a dispatched agent. The user saw the run as a Claude agent in the interface. Nothing showed that Codex ran. | Labels for the tool. Desktop and other surfaces. |

The L5 condition: `claude -p` does not end while a background command runs. It waits for the command, or it stops
the command when it gets SIGTERM. So a router timeout (SIGTERM) also cleans up. A long background command blocks the
router until its timeout.

## Lessons

- `claude -p` waits for its background commands. A delivery with a long background command takes up to the router
  timeout. The final `result` can be the answer to a task notification. Agents that the router resumes must not
  start background commands, or the router must allow for this.
- A `SIGTERM` to `claude -p` stops its background commands. A `SIGKILL` was not tested. The D18 clean-up is still
  useful for that case.
- Give router agents no tools for a pure message turn (`--tools "" --strict-mcp-config`). Local tools for peer
  messages can take the place of the router and change the answer.
- `--tools` takes many values. Put it before another option, or give the prompt on stdin.
- An acknowledgment (`RECEIVED 391`) was stored as type `reply`, so it is pending for the other agent. Use a type
  such as `ack` that the router does not deliver.
- Codex prints "Reading additional input from stdin..." and waits unless stdin is `/dev/null`.
- A Codex run in the background shows only as a Claude agent and a background command. The user cannot see which
  tool runs. A terminal mod can label it (spec D20).
